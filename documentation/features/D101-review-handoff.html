Review handoff

/d101-review writes its findings to a sibling D101-<slug>.review.md, so they survive past the chat session that produced them. A later /d101-feature-design run reads it, offers it as input, and deletes it once used. The file is a disposable cache, never a record: it carries no state a re-run of the review couldn't reproduce, and it is safe to lose.

Scope: The Design stage of the L3 pipeline (D100 §3, stage 1). This D101 covers a convention spanning two existing commands — it adds no new command. It is the writing half of what D101 — /d101-review does and the consuming half of what D101 — /d101-feature-design does; the contract itself lives in d101-feature-design-definition.md §4.10.

§2Purpose & audience

A review's findings are only as useful as the developer's ability to act on them, and today that ability ends with the chat session that produced them.

  • Findings don't survive a closed session. Run /d101-review, close the terminal, come back tomorrow to run /d101-feature-design — the findings are gone, and the developer either remembers them by hand or reviews again from memory.
  • The one working case trained the wrong habit. Running review then design back-to-back in the same session works today because the chat context still holds the findings — so the fix looks unnecessary until the moment the two commands are used the way most tooling actually gets used: apart.
  • Re-reading a report to extract action items is manual translation. A finding written as a Fail row with a one-sentence reason has to be turned back into "go fix this" by a human, every time, even though the review already did the turning-into-findings step once.
  • Findings addressed out of order get lost track of. Without a working list, a developer fixing three of five findings in one sitting has no record of which three, and the next review re-derives all five from scratch anyway — which is fine, but only if nothing capable of tracking partial progress was ever promised.
Audience. Primary: developers running /d101-review and /d101-feature-design across separate sessions on the same D101. Secondary: anyone reading either command's source, who needs to understand why one writes a file it doesn't own the format of and the other deletes a file it didn't create.
Not for. Recording review history — that stays out of scope (D101-d101-review.html OOS7). This file is a cache of one review's findings, not a log of every review that ever ran. It is also not a substitute for the Accepted mechanism (D101-accepted-deviations.html): a finding the team has decided to live with belongs in the D101 itself, permanently; a finding still awaiting a fix belongs here, temporarily.

§3Requirements

Functional — 14
R1
/d101-review MUST write its findings to a .review.md sibling of the target D101 — same directory, same slug — after emitting the same findings to chat. The sibling location is derived from wherever the target actually resolved to, never fixed to documentation/features/.
R2
The review-notes file MUST carry a fingerprint of the target D101 at review time: its meta-strip Last updated date, its phase-chip value, and its status-chip's literal text including its version number (e.g. Draft v0.3), not a normalised Draft / Approved.
R3
The review-notes file MUST carry every finding that was emitted to chat for the reviews the developer picked, kept distinct by review the way the chat output keeps them distinct.
R4
/d101-review MUST NOT write to any path other than the review-notes sibling — never the target D101, never any other file.
R5
When a review-notes file already exists for the target's slug, /d101-review MUST overwrite it wholesale rather than merge with or append to it.
R6
On invocation against an existing D101, /d101-feature-design MUST check for a sibling review-notes file and, if one exists, offer to use it as input once the target file is pinned (after the continue-or-fresh and phase-routing questions) and before the first content question of the phase.
R7
Before offering the notes, /d101-feature-design MUST compare the notes' recorded fingerprint against the target's current meta-strip date, phase chip and status chip.
R8
When the fingerprint matches, /d101-feature-design MUST offer the notes as current, with no caveat.
R9
When the fingerprint does not match, /d101-feature-design MUST name what changed before offering the notes.
R10
When the developer accepts the notes, /d101-feature-design MUST fold each finding into the session's agenda as it would a finding raised in chat — never by transcribing the notes file's wording into the D101.
R11
/d101-feature-design MUST delete the review-notes file in, and only in, the same run that both consumed it as input and wrote the D101.
R12
When the developer declines the offered notes, /d101-feature-design MUST NOT delete the file.
R13
A run of /d101-feature-design that writes no file (Phase A) MUST NOT delete an existing review-notes file, whether or not it was offered.
R14
The review-notes file MUST be named <target-basename>.review.md and sit in the resolved target's own directory. The documentation/features/ literal enters only through the .gitignore pattern and CLAUDE.md hard rule 9 — a fork that relocates the D101 convention moves that literal, not the sibling rule.
Non-functional — 4
NF1
Disposable, not authoritative. The file carries no state a re-run of the review couldn't reproduce from the D101 alone. Losing it costs one re-run, never a decision — this is what makes deleting it safe.
NF2
A cache, not a log. It holds the most recent review's findings, not a history of every review that ran. Overwriting on re-review (R5) is deliberate, not a gap.
NF3
Write scope is prompt discipline, not a sandboxed guarantee. Claude Code's tool grant controls which tools a command may call, not which paths a given tool may target — so R4's scope is enforced by the command's own hard rule and by an acceptance criterion on git diff, the same category of promise the never-move-either-axis rule already relies on.
NF4
No product-specific assumptions. The convention names no product entity and works in any repo that follows the documentation/features/ convention.
Out of scope — 5
OOS1
A review-history log. Reason: already out of scope for /d101-review itself (D101-d101-review.html OOS7) for the same cause — it would be new document state on top of the two existing axes, for an advisory and iterative activity.
OOS2
Partial-consumption tracking (marking some findings addressed, others deferred). Reason: the review is stateless — anything not fixed resurfaces on the next run regardless, so tracking which findings were "done" would duplicate information the D101 and a re-run already carry.
OOS3
Committing the review-notes file to version control. Reason: it is working state between two commands, not a design artifact; committing it would duplicate a PR's own review thread with a second, unlinked copy. It is gitignored at the standard location (documentation/features/*.review.md); a target outside it leaves the notes untracked, and the repo owning that location adds its own ignore entry.
OOS4
A merge tool for two review-notes files (e.g. combining findings from two reviewers). Reason: only one reviewer runs /d101-review at a time in the intended flow, and a merge policy for concurrent reviews is a distinct, harder problem this D101 doesn't need to solve to deliver cross-session handoff.
OOS5
Automatic staleness resolution. Reason: the fingerprint mismatch is surfaced to the developer, who decides whether to use, discard, or re-review — the command never silently picks a side of that judgement call.
4
Business design
The principles that keep the file a cache rather than a record, the vocabulary of a fingerprint and a match, the handoff sequenced across two commands and two possible sessions, the rules that decide when to offer and when to delete, and the decisions with their rejected alternatives.

§4.1Design principles

1
A cache, never a record. The file holds exactly what a re-run of the review would produce again — nothing it carries is authoritative, which is what makes losing it harmless.
2
Statelessness is the safety net. The mechanism is only as safe as the gap review is stateless. If a future review ever grew memory of its own prior runs, this cache would stop being disposable and this design would need revisiting.
3
Deleted on consumption, not on discovery. Finding the file is not using it — only a run that folds its findings in and writes the D101 has earned the right to remove it.
4
Staleness is surfaced, not resolved. A fingerprint mismatch is the developer's call; the command's job stops at naming what changed.
5
Same convention, same lockstep. The file sits beside the D101 it annotates, wherever that D101 is — its location is derived from the target, never configured. The documentation/features/ literal enters only through the .gitignore pattern and hard rule 9, so a fork that relocates the folder moves that one literal and nothing else.
6
The tool grant is honest about its limits. /d101-review gaining Write is a real capability change, stated as what it actually is — a prompt-level scope, backed by a hard rule and an AC, not a sandboxed guarantee.

§4.2Model / concepts

Three terms this convention adds. Everything else — the bars, the phases, the reviews themselves — it inherits unchanged from d101-feature-design-definition.md and the two commands' own designs.

Concept
What it means
Review notes
The sibling D101-<slug>.review.md file — every finding from the developer's picked reviews, plus a fingerprint of the D101 they were checked against.
Fingerprint
Three values recorded at review time — the target's Last updated date, phase, and the status chip's literal text including its version number (Draft v0.3, not just Draft) — cheap enough to need no new tooling, and the version number is what catches a same-day edit the date alone would miss.
Match / mismatch
Whether the fingerprint recorded in the notes still equals the target's current values. A mismatch does not discard the notes; it names the risk and lets the developer decide.

§4.3Flow

Trigger. A developer runs /d101-review, then — in the same session or a much later one — runs /d101-feature-design against the same D101. Outcome: the second command finds the first one's findings waiting on disk, offers them as input, and clears them away once used. Nothing is exchanged that a fresh review couldn't reproduce.

Developer — entry actor The two commands — processing components On disk — the data store (D101 + review notes) Accent 1 — the cache is created Accent 2 — the cache is consumed and cleared

Notation: UML sequence, per plugins/asimov-plugin/resources/diagrams/sequence-template.svg. The two accented messages are the pair this whole design exists to connect — a review notes file is written once, and deleted once, and everything else is either producing it or acting on it. The dashed session-gap divider between messages 4 and 5 is the one deliberate addition beyond the standard notation: it stands for the fact that these two calls may be seconds or months apart, which the fixed-height gap of a normal sequence diagram cannot otherwise convey.

3

§4.4Rules / constraints

Four conditional rules decide when the file is written, offered, and cleared. Each is stated with the case where it fires and the adjacent case where it does not, per d101-feature-design-definition.md §6.3.

BR1 — write scope

One path, never the D101. /d101-review's new write capability is bounded to exactly one file.

  • Fires when the write targets a .review.md file beside the target that was just reviewed, wherever that target actually lives (R1, R4).
  • Stays quiet when anything — the developer, a finding, a habit from other tools — points the write anywhere else, including the target D101 itself. The command declines (R4, NF3).
BR2 — offer, don't assume

Found is not accepted. Discovering a sibling file is information for the developer, not a standing instruction.

  • Fires when a sibling exists — the developer is asked, once, whether to use it (R6).
  • Stays quiet when no sibling exists, or the developer declines: the session proceeds exactly as it would with no notes at all, and the file (if any) is left untouched (R12).
BR3 — fingerprint before offer

A stale offer says so. The offer names what it's built from before the developer decides.

  • Fires when the recorded date/phase/status match the target's current values — the notes are offered as current, no caveat needed (R8).
  • Stays quiet when any of the three differ: the offer still happens, but names the mismatch first, because a stale finding presented as current is worse than no finding at all (R9, OOS5).
BR4 — delete on consumption only

Earned by use, not by discovery. The file's disposability is conditional on having actually been used.

  • Fires when a run both accepted the notes as input and wrote the D101 — the file is deleted at that point (R11).
  • Stays quiet when either half is missing — declined, or accepted but the run ends without writing (Phase A) — the file survives untouched for a later run (R12, R13).

§4.5Decisions and alternatives

A decision recorded without its rejected alternative is one that gets re-litigated.

Decided
Alternative considered
Why this won
Give /d101-review Write, scoped by prompt discipline to one sibling path (R1, R4, NF3)
Keep the review fully read-only and require the developer to carry findings manually between sessions
The manual-carry cost is exactly the friction that prompted this design — the developer already does it today and finds it worth automating. Claude Code has no path-scoped tool permission to lean on instead, so the honest choice is a real capability with a stated, hard-rule-enforced limit, not a fictional read-only guarantee stretched to cover a write.
The file is a disposable cache, not a record (NF1, NF2)
A persistent review log the D101 or a separate index accumulates over time
The gap review is stateless — every run derives its findings from the D101 alone. A cache that can only ever be reproduced by a re-run carries no risk when lost or deleted; a log implies history worth keeping, which nothing here actually needs or was asked for (D101-d101-review.html OOS7).
Fingerprint from the meta-strip and chips already in every D101 (R2, R7)
A content hash of the whole D101; the file's on-disk modification timestamp
A hash needs a hashing step neither command's tool list otherwise requires, and a filesystem mtime isn't reliably read by these commands' existing tools. The meta-strip date plus the two chips are already read on every invocation of both commands. The status chip's version number — bumped on every write — was folded into the fingerprint rather than left out: it costs nothing new to read, and it is what catches two edits made on the same calendar day, which the date field alone cannot distinguish.
Overwrite wholesale on re-review, never merge (R5)
Append new findings to the existing file; merge by finding identity
A merge needs a notion of "the same finding across two runs" that the stateless gap review doesn't produce — it has no ids, only freshly-derived rows. Overwriting is simple, correct, and matches the file's own nature as a snapshot of the most recent review, not an accumulating history.
Delete only on consumption, gated on both accept and write (R11, R12, R13, BR4)
Delete as soon as it is offered, whether or not the developer uses it; delete as soon as it is read, before the developer answers
Either alternative destroys the developer's only cross-session copy on a "not now" — exactly the loss this file exists to prevent. Gating on both halves means the file survives every path except the one where its job is actually done.
Gitignored, never committed (OOS3)
Commit it alongside the D101, as a record of review history
A committed file would duplicate a PR's own review thread with a second, disconnected copy that drifts from the actual conversation the moment either one changes. Working state between two commands isn't a design artifact and doesn't belong in git history.
Sibling location tracks the resolved target, not a fixed convention (R1)
Always write to documentation/features/D101-<slug>.review.md, matching the repo-wide path convention
Both commands already accept a target path outside the standard convention (Step 2 of /d101-review explicitly does). A fixed write location would either miss the sibling entirely for such a target or, worse, write notes beside an unrelated file that happens to share a slug under documentation/features/. Deriving the sibling from wherever the target actually resolved to is the same amount of work and has no failure mode the fixed version doesn't. Found by Copilot's review on PR #16.

§6.8Known constraints & gotchas

  • The write-scope promise is discipline, not sandboxing. Nothing stops a differently-prompted invocation from writing elsewhere except the hard rule itself — this is stated in §6.1 rather than hidden, because it is the one place this design is honest about being softer than it sounds.
  • The fingerprint is coarse by construction. It catches every edit that goes through /d101-feature-design, because that command bumps the version and the date together on every write. What it cannot catch is a hand-edit made outside either command — someone editing the HTML directly in a text editor without touching the chips — which is accepted as a known gap (§4.5 decision row) rather than solved with a hash the tools don't otherwise need.
  • Safety depends on the gap review staying stateless. If a future version of /d101-review ever gained memory of its own prior runs, this file would stop being a harmless cache and this design's core argument (NF1) would need revisiting.
  • Committed by accident is still possible. The gitignore entry prevents git add -A from picking it up, but an explicit git add of the exact filename still works — the convention relies on the ignore rule being present, not on the file being unaddressable. The rule covers documentation/features/ only; notes beside a target elsewhere are plain untracked files until that location gets its own entry.

§7.1What is genuinely new to build

Everything not listed here arrives by reuse. The section sits outside both bars (d101-feature-design-definition.md §4.8) — it gates no verdict and moves neither chip.

§7.4Cross-cutting — shared by both commands

  • One definition, referenced by path. Both commands point at §4.10 rather than restating it (hard rule 3).
  • The path convention travels together. The review-notes naming is a fork-point literal alongside the existing documentation/features/D101-* convention (CLAUDE.md hard rule 9).
  • Neither command's own contract changes. /d101-review still emits the same chat report it always did; /d101-feature-design's phases, bars, and stop-between-B-and-C discipline are untouched. This is a side channel between them, not a redesign of either.
  • The write-scope hard rule is the load-bearing part. Without it, giving /d101-review Write would be a much larger change than intended.

§9Open questions

Open: none.

Resolved:

Q1Resolved 2026-09-15
Should the review-notes file be human-editable — a developer striking out findings they've already handled by hand before the next /d101-feature-design run — or is that scope creep toward the review-log this design deliberately excludes (OOS2)?
Decision: Not editable. d101-feature-design-definition.md §4.10 fixes the file as "read-only findings a review would have produced anyway — never something an author edits by hand". Hand-struck findings would be partial-consumption tracking (OOS2); the next /d101-review re-derives the true set regardless.
Q2Resolved 2026-08-31
If a stronger staleness signal becomes cheap later (e.g. a tool that can read file mtimes reliably), should the fingerprint be upgraded, or does the day-granularity date remain good enough given how rarely a same-day edit-then-review-then-edit sequence actually happens?
Decision: Upgraded without waiting for a new tool — the status chip already carries a version number that advances on every write, so recording its literal text (Draft v0.3, not just Draft) closes the same-day gap at zero new cost. Found during the first real test of this mechanism, which exercised exactly the scenario the open question anticipated.
