Artifact maturity

Each artifact carries one maturity level: assess, trial, adopt or hold. It is recorded in the artifact's definition, shown as one chat line by the command that produces the artifact, and moved by a maintainer on evidence of use.

§2Purpose & audience

New artifacts are about to land, and nothing tells a reader whether a definition is a first draft or a proven standard.

  • Every definition reads with the same authority. The D101 definition has nine documents behind it; the S101 definition will have none, and the files look alike.
  • The developer is not warned. A command applies a new artifact's rules as if they were settled.
  • Promotion is a gut feeling. There is no criterion for when an artifact stops being experimental.
Audience. Developers about to run a producing command, and maintainers editing a definition. Not the readers of the produced document (OOS1).

§3Requirements

Functional — 10
R1
Every artifact carries exactly one level from the set assess, trial, adopt, hold.
R2
The level is recorded as YAML frontmatter in the artifact's definition, with the fields artifact, maturity and since.
R3
Every artifact has a definition; the block lives there and never in a template.
R4
since is the date (YYYY-MM-DD) the current level was entered.
R5
A producing command reads the level at run-time and prints one chat line before its first question when the level is assess, trial or hold.
R6
When the level is adopt, the command prints nothing about maturity.
R7
When the level is missing or invalid, the command reports that in one line and continues without assuming a level.
R8
The produced document carries no maturity mark.
R9
No command changes a level or writes to the file that records it.
R10
A level change lands in one commit with the matching D100 §4.5 column and, at trial or above, any migration note.
Non-functional — 2
NF1
No new config mechanism. The level lives in a file the commands already read.
NF2
Evidence, not time. Every criterion is an event someone can point to.
Out of scope — 4
OOS1
A mark in the produced document. Reason: its readers judge the feature, not the toolkit.
OOS2
Overviews (landing page column, a status command). Reason: deferred until there are enough artifacts to list.
OOS3
Per-artifact version numbers. Reason: nothing consumes them; the plugin has one version and since gives the context.
OOS4
Automatic promotion. Reason: the evidence is not observable from inside a product repo; it is a maintainer's call in a commit.

Business design
Vocabulary, the four levels, the rules that move a level, and the decisions.

§4.1Concepts

Concept
What it means
Artifact
Something the toolkit writes into a product repo; a definition and a template in one folder. Three artifacts had no definition and get one here.
Level
One of the four values; how far to trust the rules and what a change comes with.
Producing command
A command that writes an artifact: /d101-feature-design, /persona-new, /asimov-init.

§4.2The four levels

Level
Entry criterion
Promise
assess
Definition and template exist. No artifact produced in a product repo, or only by the definition's author.
Rules may change without notice. Feedback wanted.
trial
At least one artifact produced in a product repo and reviewed by a named person who is not the author.
The form holds. Incompatible changes may come with a migration note.
adopt
Used in at least two repos, and the definition revised at least once on feedback from use.
Changes to the bar go through a D101.
hold
Superseded or being retired. The definition's first paragraph names the successor, or says there is none.
Do not start new documents from it.
Notice text
Level
Line printed
assess
<Artifact> is an assess-level artifact: the definition is untried and may change without notice. Feedback is welcome.
trial
<Artifact> is a trial-level artifact: the form holds, but incompatible changes may come with a migration note.
adopt
Nothing.
hold
<Artifact> is on hold. Start new documents from <successor>.

§4.3Rules

Rule
Description
Promotion needs a non-author
A level rises only on evidence from someone other than the definition's author, named in the commit. The author's own use does not count.
Rewriting the bar demotes
When the rules change so that existing documents would no longer pass, the artifact returns to assess with a new since. Editorial changes do not move it.
Recurring deviation changes the rule
Below adopt, a rule declined by accepted deviation on three documents is reworded. At adopt the same signal opens a D101 instead.

§4.4Decisions

Decided
Alternative considered
Why rejected
Technology Radar rings: assess / trial / adopt / hold.
experimental / stable; alpha / beta / stable.
Two levels leave everything in the lower bucket. Alpha/beta implies versions artifacts do not have and has no word for retirement.
Frontmatter in the definition.
An artifact.json per folder; a column in D100 only.
A manifest is a new config mechanism for one field. D100 is outside install scope, so no command could read it.
One chat line from the producing command.
A third chip in the D101 top bar; a footer note.
Both put the toolkit's self-assessment in front of readers judging the feature.
Initial levels: D101 trial; persona review assess until Q1 names a reviewer; site, asimov.md, read-list, S101 assess.
Start everything at assess.
The D101 artifact meets the trial criterion today (nine documents, merged through PRs by more than one author); stating otherwise would be false on day one.

Technical design
Where the level lives and the exact shape of the block and the notice.

§6.1Platform

Prose in eleven files, three of them new: every artifact folder gets a definition with a maturity block, three commands gain one step, D100 §4.5 gains a column, CLAUDE.md gains a convention and a hard rule, and the PR workflow gains a presence check for the block (2026-09-15). No code beyond that check, so no code map, API or configuration sections; the file list is §7.

No escalation gate. The change is prose in files the maintainer already owns. The one operational step is /plugin marketplace update asimov-marketplace, because the installed plugin is a copy and reads its own definitions, not the clone's.
