D101 · Feature design · Asimov plugin

asimov-init

Bootstrap a product repo to use the Asimov toolkit — scaffolds the documentation/conventions/<stack>/README.md read-lists the build subagents depend on, generates the documentation/ landing site, and marks the repo with asimov.md, whose presence makes the installed plugin's hooks inject the Asimov context into every session and subagent, in Claude Code and Codex alike, cut to the entry points the marker enables; the Codex subagent shells are copied into .codex/agents/ — every target in one run, whichever tool runs it. Supersedes /docs-init. Ships as one asimov-skill both tools read: /asimov-init in Claude Code, $asimov-plugin:asimov-init in Codex.

Archetype
Greenfield (evolves /docs-init)
Scope: The Asimov setup entry point shipped by asimov-plugin: the asimov-skill asimov-init, one file both tools read (/asimov-init in Claude Code, $asimov-plugin:asimov-init in Codex). Run once in a product repo to make it Asimov-ready for both tools: it writes the asimov.md marker, scaffolds detected-stack convention read-lists under documentation/conventions/, asks for the project info, writes the documentation site and copies the plugin's agents/*.toml shells into .codex/agents/ — whichever tool it runs in. The Asimov context itself is not a file in the repo: the plugin's SessionStart and SubagentStart hooks inject the using-asimov skill wherever the marker is, at the plugin's installed version (since 2026-11-13; until then the context was an asimov.md imported from CLAUDE.md and a region in AGENTS.md, which a run now migrates away). Read-only on every other file in the repo. Renames and absorbs the former /docs-init; since 2026-11-12 it also absorbs the /asimov-init slash command and the Codex-only codex-asimov-init skill that shipped one entry point per tool, each writing only its own tool's context. §2–§5 are tool-neutral; §6.1 holds what still differs per tool (how the plugin is found, which model binds, how the hook is launched).

§2Why this exists

Installing asimov-plugin makes the commands and subagents available, but a freshly-installed repo is not yet ready for them. The build subagents read convention files that don't exist; Claude has no repo-level memory of the L3 taxonomy; and the documentation landing page has to be hand-built. Before it, /docs-init solved only the last of these. asimov-init closes the whole gap in one guided run, for both tools at once.

01
Subagents read files that aren't there
Giskard, Daneel, and Calvin load documentation/conventions/<stack>/README.md as a load-bearing read-list (D100 §7.2.1). In a fresh repo that file is absent, so the convention overlay is silently empty.
02
No repo-level Asimov memory
Claude opening the repo has no standing context about the L3 taxonomy, where D101s live, or which Asimov commands exist — so it can't orient or auto-delegate without being told each session.
03
Setup spread across steps
Before this command a developer ran /docs-init, then hand-edited CLAUDE.md, then hand-created convention folders. Three manual steps, each easy to skip, with no single "you are now Asimov-ready" moment.
04
Hand-edited CLAUDE.md is risky to touch
A command that rewrites a developer's existing CLAUDE.md can clobber hand-written context. Asimov context needs a home that is neither the developer's file nor a copy of it.
05
A context file goes stale
An asimov.md written at setup described the toolkit as of that day, and every plugin release left it behind until someone re-ran the setup; Codex needed the same text copied into AGENTS.md, so it stood twice. The context belongs to the plugin, and only the switch belongs to the repo.
Audience. A developer adopting asimov-plugin in a product repo for the first time (or refreshing an existing setup), who wants the repo wired for the L3 commands and subagents in one run — plus the Asimov repo itself, which dogfoods the skill.

§3Requirements

Functional 25
Non-functional 9
Out of scope 6
R1
The skill writes asimov.md at the repo root from the plugin's asimov-md-template.md: a marker whose frontmatter carries one key per entry point — asimov-design, asimov-spec, asimov-build, asimov-project, each enabled or disabled — and a three-line body for people. It carries no context and nothing imports it.
R2
On re-run, the skill regenerates asimov.md wholesale — it is an Asimov-owned file, not a developer-edited one; only its enabled/disabled values carry over, as the default answer to R25.
R3
When a CLAUDE.md at the repo root holds a line that is exactly @asimov.md — the import an earlier Asimov wrote — the skill removes that line (MIGRATE) and changes nothing else; otherwise it leaves the file as it is (SKIP). It never adds a line and never creates the file.
R4
When an AGENTS.md at the repo root holds exactly one intact Asimov-managed region (<!-- asimov:start … <!-- asimov:end -->), the skill removes the region, markers included (MIGRATE), deletes the file when nothing but whitespace remains and says so; otherwise it leaves the file as it is (SKIP). It never adds a region and never creates the file.
R5
The skill never modifies any line of an existing CLAUDE.md or AGENTS.md other than the one line and the one region of R3 and R4; it does not rewrite, reorder, or summarise the developer's content, and it never writes Asimov context into either file.
R6
The skill detects which stacks the repo uses by scanning for stack markers (the §6.4 detection table) and reports the detected set.
R7
For each detected stack, the skill scaffolds documentation/conventions/<stack>/README.md from the plugin's conventions-readme-template.md when that file is absent.
R8
When a stack's README.md already exists, the skill offers to merge/update the Asimov-managed region of it rather than skipping silently or overwriting it wholesale.
R9
When no stack is detected, the skill creates no conventions/<stack>/ folders and reports that no stack was detected (it does not guess a stack).
R10
The skill writes documentation/index.html from the index template, carding the docs found under documentation/ by the six-bucket taxonomy (§6.4).
R11
The skill writes documentation/_chrome.css as a verbatim copy of the plugin's chrome stylesheet, applying the absent/identical/differs special-case (§4.4).
R12
The skill emits exactly one index doc card per unique doc (base name without extension), drops buckets with zero docs, and excludes the defined non-document files (§6.4).
R13
The skill reads every template it uses (asimov-md-template.md, conventions-readme-template.md, site-template.html, _chrome.css) from the plugin root at run-time, before writing — and, since D101 — artifact maturity, the three artifact definitions beside them (asimov-md-definition.md, conventions-definition.md, site-definition.md) for their maturity level. From each definition's YAML block it prints one chat line per level present, before its first question (Step 1b); nothing is printed for adopt, and no level is ever written into a generated file.
R14
The skill derives the repo name from its input ($ARGUMENTS in Claude Code; the text after the invocation in Codex) when non-empty, otherwise from the git remote origin URL, otherwise from the working-directory folder name.
R15
The skill presents a single consolidated write plan listing every target (the marker, the CLAUDE.md and AGENTS.md migrations when there is something to migrate, each .codex/agents/ shell, each convention README, the project info, the site, .gitignore) with its action drawn from one canonical set — NEW · OVERWRITE · MIGRATE · APPEND · MERGE · SKIP · ASK — and waits for explicit confirmation before writing anything.
R16
After writing, the skill reports each target written/skipped with the reason, the set of stacks detected, a one-line site stat (<N> docs across <K> sections; <H>/<T> hand-crafted HTML), and any files under documentation/ that fit no bucket with a suggested target.
R17
When the architecture doc describes a named pipeline or dataflow (per the §6.4 detection rule), the skill MAY add a flow band to the index between hero and catalogue, with each node typed by a repo-defined kind and a legend mapping colour → kind.
R18
When the repo ships 3+ sibling docs of one category (per the §6.4 detection rule), the skill MAY add an entity gallery to the index, one tile per sibling linking to that sibling's doc.
R19
When no pipeline and no sibling cast is detected, the skill emits no showcase block and never invents one; an omitted flow band is recorded in the report as a suggested manual enhancement (§4.4, §6.4).
R20
When the repo has an orientation source — the README.md intro, else a charter/overview doc under documentation/, else the D100 Purpose section — the skill MAY add 2–3 short overview paragraphs to the index between hero and catalogue, naming the source used in the write plan and report; with no source it emits none.
R21
The plugin's SessionStart hook injects the body of skills/using-asimov/SKILL.md into the session wherever asimov.md is at the working directory's root, in Claude Code and Codex alike, with {{INVOKE:…}} spelled as /<skill> or $asimov-plugin:<skill> for the harness that runs it, the repo name from the folder and the stacks from documentation/conventions/*/. Where no marker is, it injects nothing.
R22
The hook keeps only the blocks of the enabled parts — a block between <!-- part: X --> and <!-- /part --> in the skill, X one of design, spec, build, project — and drops the marker lines; a key absent from the marker counts as enabled, a marker without frontmatter (the old context file) as all enabled, and all four disabled injects one line saying so. The SubagentStart hook injects skills/using-asimov/subagent.md the same way.
R23
When the AGENTS.md markers are broken or duplicated (a start without an end, an end without a start, more than one pair), the skill writes nothing to that file, labels the migration ASK, and asks the developer to repair or delete the region by hand.
R24
The skill copies each agents/*.toml shell in the plugin byte for byte into the product repo's .codex/agents/ — NEW when absent, OVERWRITE when present — using a file copy, never a read-and-rewrite; when the plugin's agents/ holds no .toml, the target is skipped and the plan says so.
R25
The run asks one question — which entry points this repo uses — with the current marker's values as the default (all enabled on a first run), and writes the answer as the marker's four keys; none disables all four.
NF1
The skill is read-only on every file in the repo except its declared write targets; it never calls Write on a source doc, and its only edits to an existing file are the managed region of an existing convention README, the Asimov-owned .codex/agents/*.toml copies, and the two migrations of R3 and R4, which only take back what an earlier Asimov wrote. It writes every target in whichever tool it runs in, so a repo set up from one tool opens in the other without a second run.
NF2
The migrations are idempotent: re-running the skill when the @asimov.md line and the AGENTS.md region are gone writes nothing to either file and reports SKIP.
NF3
The generated index.html is pure static HTML + CSS — no JavaScript, no client-side behaviour — and links to _chrome.css rather than inlining it.
NF4
All templates are re-read at the start of every invocation; the file in the plugin is the run-time source of truth.
NF5
The skill's first output is a one-sentence narration of what it will do, emitted before any tool call.
NF6
The skill's frontmatter pins claude-opus-5-5, matching its row in model-choice.md §1; Claude Code binds it, Codex ignores the key and runs the session's model.
NF7
The Asimov-managed region in an existing convention README is delimited by explicit <!-- asimov:start -->/<!-- asimov:end --> markers so a re-run refreshes exactly that region. The same markers delimited the AGENTS.md region until 2026-11-13; a run now recognises them only to remove it (R4).
NF9
The context hook is bash with builtins only, started through run-hook.cmd (and run-hook.ps1 where the hook shell is PowerShell); it reads the marker and the conventions folders and nothing else, never waits on stdin longer than five seconds, always exits 0, and prints nothing where no marker is.
NF8
The skill is model-invocable: its frontmatter carries no disable-model-invocation and its agents/openai.yaml no allow_implicit_invocation: false; the write plan of Step 6 precedes every write, whoever started the run (reversed 2026-11-13).
OOS1
Authoring the full repo CLAUDE.md / analysing the codebase to describe the product. Why: that is Claude's own /init; /asimov-init writes the marker, and the Asimov layer reaches the agent from the plugin.
OOS2
Authoring the convention content (the actual coding rules). Why: the skill scaffolds the read-list skeleton; the team fills in the rules. Guessing rules would bake wrong conventions into the subagents' overlay.
OOS3
Authoring doc bodies (D100/D101 content). Why: that is the job of asimov-design and siblings; /asimov-init only indexes and scaffolds.
OOS4
A config mechanism for the documentation/ path taxonomy. Why: the layout is intentionally a code fork point shared across the D101 commands, not a one-toggle config (D100 hard rule 9).
OOS5
Installing or verifying the plugin itself. Why: marketplace install is a developer step done before the skill runs; the skill assumes the plugin is present.
OOS6
Writing L3 process-rule docs or configuring PR / Copilot settings. Why: process enforcement lives in product-repo settings, not in the toolkit (D100 §3); deferred out of this command's scope.
4
Business design
The principles the skill holds to, its vocabulary, the targets it writes — the marker the plugin's hooks read, the Codex shells, the read-lists, the project info, the site, the gitignore patterns, all written on every run — the migration of the two carriers the context used to have, the conditional generation rules with counter-examples, and the decisions taken with their rejected alternatives.

§4.1Principles

1
One run to Asimov-ready. A single guided command takes a fresh repo from plugin-installed to fully wired — context, conventions, and docs site — instead of three manual steps.
2
Own what you write, touch nothing else. The marker asimov.md is Asimov's and regenerated freely; the context comes from the plugin's hooks and lives in no file of the repo. CLAUDE.md and AGENTS.md are the developer's: the only edits to them are migrations that take back the @asimov.md line and the region an earlier Asimov wrote.
3
Scaffold structure, never invent content. The skill creates the convention read-list skeleton and the import wiring; it never guesses coding rules or product context.
4
Detect, don't assume. Stacks are discovered from real repo markers; an undetected stack yields no folder and an explicit report line, not a guessed default.
5
Read-only on everything else; confirm before writing. The skill shows one consolidated write plan and waits; outside its declared targets it never mutates a file.
6
Plugin templates are the run-time source of truth. Every template is re-read each invocation so the wiring and visual language can't drift — and the context itself lives in the plugin, so a plugin update changes what every session is told without a run.

§4.2Vocabulary

The domain terms the skill and this design share. Green = an artefact the skill produces; amber = a derived value; cyan = an input structure or mechanism it relies on.

asimov.md

The Asimov marker the skill writes at the repo root. Its presence switches the plugin's hooks on; its four keys say which entry points the repo uses. Three lines of body for people. Regenerated wholesale on every run; the hook reads nothing else from the repo but the conventions folders.

Context hook

hooks/asimov-context, fired by the plugin at SessionStart and SubagentStart in both tools. Where the marker is, it injects the using-asimov skill (the session) or its subagent note, cut to the enabled parts, with the harness's invocation syntax. Until 2026-11-13 the context reached Claude Code through an @asimov.md import and Codex through a region in AGENTS.md.

Convention read-list

A documentation/conventions/<stack>/README.md that @-references every convention file in its stack. The build subagents read it to load the local overlay (D100 §7.2.1).

Stack detection

Inferring which stacks a repo uses from marker files (*.csproj → dotnet, angular.json → angular). Drives which convention read-lists are scaffolded.

Managed region

A marker-delimited block (<!-- asimov:start --> … <!-- asimov:end -->) the skill refreshes inside a file it doesn't own, so a re-run updates exactly that block (NF7): an existing convention README. AGENTS.md carried one with the Asimov context until 2026-11-13; a run now removes it (R4), as it removes the @asimov.md line from CLAUDE.md (R3).

Codex subagent shells

The plugin's agents/*.toml files — one per Asimov subagent. The skill copies them byte for byte into the product repo's .codex/agents/ on every run, from either tool; they are Asimov-owned there and overwritten on every run (R24).

Part

One of design, spec, build, project: a block of the using-asimov skill the hook keeps or drops by the marker's key for that entry point. Design carries the D101 entry points and the personas, spec the planning, build the agents and the delegation rule, project the project pages and pm-advisor.

Write plan

The single consolidated list of every target and its action (NEW · OVERWRITE · MIGRATE · APPEND · MERGE · SKIP · ASK) shown for confirmation before any write (R15).

§4.3.1CONV
Convention read-lists
"What do the build subagents load as their local overlay?"
For each detected stack, scaffold conventions/<stack>/README.md from the template when absent; offer a managed-region merge when present (R6–R9).
  • Skeleton only — a read-list with placeholders, not real rules (OOS2)
  • No stack detected → no folder, explicit report line (R9)
§4.3.2SITE
Documentation site
"Where do the repo's docs live as a browsable landing page?"
Invoke artifact-site-authoring, which writes documentation/index.html, _chrome.css, _site/ and the nav block of every indexed document, whole (R10–R12 as redefined in site-definition.md, 2026-11-10). When project/info.html is missing, the project info's method file project-info-authoring.md writes it first, from the person's answers.
  • One card per unique doc; empty buckets dropped; sources never edited
  • Optionally fronted by an intro zone — overview prose / flow band / entity gallery — when the repo supports it (R17–R20, §6.4)
  • _chrome.css identical to template → left untouched
The marker — read by the plugin's hooks in both tools — and the CLAUDE.md migration
§4.3.3asimov.md
asimov.md (repo root)
"How does the plugin know this repo uses Asimov, and which parts?"
Asimov-owned. Written from the plugin template: four keys, asimov-design … asimov-project, each enabled or disabled from the run's one question, and three lines for people. Regenerated wholesale on re-run, the values kept (R1, R2, R25).
  • Its presence switches the plugin's hooks on; its keys cut the context to the parts in use (R21, R22)
  • Carries no context: the hook reads the keys and nothing else, and nothing imports the file
  • Not for developer edits beyond the values — repo context belongs in CLAUDE.md or AGENTS.md, which the skill never writes into
§4.3.4CLAUDE
CLAUDE.md migration
"What about the @asimov.md line an earlier setup wrote?"
Remove the one line that is exactly @asimov.md; otherwise leave the file as it is. Never add a line, never create the file (R3, R5).
  • Idempotent: re-run after the migration writes nothing and reports SKIP (NF2)
  • Does not author the rest of CLAUDE.md — that's Claude's /init (OOS1)
The AGENTS.md migration, and the shells Codex reads — written on every run, from either tool
§4.3.5AGENTS
AGENTS.md migration
"What about the Asimov region an earlier setup wrote for Codex?"
Remove the region between <!-- asimov:start and <!-- asimov:end -->, markers included; delete the file when nothing but whitespace remains and say so. Otherwise leave the file as it is. Never add a region, never create the file (R4, R5).
  • Codex gets its context from the plugin's hook now, like Claude Code (R21)
  • Everything outside the markers is the developer's and is never touched
  • Markers broken or duplicated → nothing written to the file; the plan shows ASK and the developer repairs it by hand (R23)
§4.3.6.codex
Codex subagent shells
"How do the plugin's Codex shells get into the product repo?"
Copy each agents/*.toml in the plugin byte for byte into .codex/agents/ — NEW when absent, OVERWRITE when present. Asimov-owned, regenerated wholesale like asimov.md (R24).
  • A file copy, never a read-and-rewrite — encoding and line endings stay as shipped
  • Hand edits to a copied shell are lost on the next run; no .toml in the plugin → target skipped and said so in the plan

§4.4Generation rules

The conditional rules that govern what the skill writes. Each carries a positive example and a counter-example — the adjacent case where the rule does not fire.

asimov.md regeneration
Overwrite
As an Asimov-owned file, asimov.md is regenerated wholesale every run; its enabled/disabled values are the default of the run's question, so they survive unless the person changes them.
  • Existing marker → replaced with the freshly rendered version, same values unless answered otherwise
  • The old full context file (no frontmatter) → replaced by the marker, all four enabled; the plan labels it MIGRATE
  • Developer notes placed in asimov.md are lost — they belong in CLAUDE.md or AGENTS.md
CLAUDE.md and AGENTS.md migration
Remove-once
Take back the @asimov.md line and the Asimov region an earlier run wrote; otherwise leave both files exactly as they are, and never create either.
  • CLAUDE.md with a bare @asimov.md line → that line removed, every other line kept (MIGRATE)
  • AGENTS.md with one intact region → the region removed; an otherwise empty file deleted and reported
  • Nothing of Asimov's in a file → nothing written, action reported as SKIP (NF2)
Stack detection
Marker-driven
Scaffold a convention read-list only for stacks whose marker files are found in the repo.
  • A *.csproj present → conventions/dotnet/README.md scaffolded
  • No angular.json anywhere → no conventions/angular/ folder created (R9)
Existing convention README
Merge / Ask
When a stack README already exists, offer to refresh only the Asimov-managed region; never overwrite the whole file silently.
  • Existing README with a managed region → region refreshed wholesale; the read-list and notes below the end marker are never written
  • Read-list found inside the markers (pre-2026-10-29 scaffold) → moved below the end marker before the refresh, no line dropped
  • Existing README without a managed region → command asks before inserting one
_chrome.css special-case
Skip / Ask
Write when absent; leave untouched when byte-identical to the template; prompt overwrite/keep/diff when it differs.
  • Existing file identical to template → not rewritten, mtime preserved
  • Existing file differs → command asks first, never overwrites silently
Index de-duplication
1 card
A doc is identified by base name; if both formats exist, emit one card with the HTML badge only (inherited from /docs-init).
  • D101-foo.md + D101-foo.html → one card, HTML badge
  • Only D101-foo.md exists → one card, MD badge (no collapse of a lone file)
Index intro-zone showcase
Opt-in
Between hero and catalogue, optionally emit overview prose, a typed flow band (each node typed by a repo-defined kind, with a legend) and/or an entity gallery — derived only from a real source, never invented (R17–R20; detection rule in §6.4).
  • README intro / overview doc / D100 Purpose present → 2–3 overview paragraphs; architecture doc describes a named pipeline → flow band; 3+ sibling docs of one category → entity gallery linking each
  • No documented pipeline / no sibling cast → block omitted (flow band noted as a suggested manual enhancement) — a wrong diagram is worse than none
Marker keys
Enabled by default
A key absent from the marker counts as enabled; all four disabled is the opt-out; no frontmatter at all, the old context file, counts as all enabled (R22).
  • asimov-build: disabled, the other keys absent → the session gets design, spec and project; no agents, no delegation rule
  • All four disabled → the hook injects one line saying so and nothing else; a subagent gets nothing
.codex/agents/ shells (Codex only)
Overwrite
Asimov-owned copies of the plugin's agents/*.toml, regenerated wholesale every run like the marker (R24).
  • Existing .codex/agents/baley-the-code-reviewer.toml → replaced with the plugin's current file, byte for byte
  • Plugin agents/ holds no .toml → no copy made and nothing deleted; the target is skipped and the plan says so

§4.5Decisions

A decision recorded without its rejected alternative is one that gets re-litigated.

Decided
Alternative considered
Why rejected
Asimov context in a standalone asimov.md, wired via @asimov.md import (2026-09-15; superseded 2026-11-13 by the hook, below)
A marker-delimited Asimov block written inside CLAUDE.md
A standalone file is Asimov-owned and regenerated wholesale with no marker parsing and zero risk to the developer's own CLAUDE.md content. It also mirrors the convention-overlay's own @-reference mechanism (D100 §7.2.1), so the repo uses one consistent wiring pattern.
asimov.md at the repo root, next to CLAUDE.md
.claude/asimov.md (tucked under the Claude config folder)
Root keeps the file discoverable beside CLAUDE.md and AGENTS.md, and it is where the hook looks: the payload's working directory. A .claude/ location would hide a file both tools depend on under one tool's folder (Q1, resolved).
Only wire the Asimov layer into CLAUDE.md; defer full repo context to Claude's /init
/asimov-init authors the entire CLAUDE.md by analysing the codebase
Repo-context authoring is exactly what Claude's built-in /init already does well; duplicating it would risk clobbering hand-written context and put two tools in charge of one file. Asimov owns only its layer.
Detect stacks from marker files; scaffold only what's found
Always scaffold a fixed set (dotnet + angular + test) regardless of repo
Empty folders for stacks a repo doesn't use are noise that reads as "forgot to fill in". Detection keeps the scaffold honest and the report meaningful.
Offer a managed-region merge for an existing convention README
Skip an existing README entirely (the /docs-init read-only stance)
A pure skip leaves a repo that pre-dates the read-list convention permanently un-upgraded. A managed region lets the skill add or refresh the Asimov read-list scaffolding while preserving the team's hand-written rules.
The read-list lives below the end marker, user-owned; the managed region holds only the heading and the explanation
The read-list inside the managed region, merged line by line on refresh
The read-list is the team's content and the load-bearing index the subagents read, so a refresh that regenerates the region wiped it silently (issue #3). §6.8Known constraints & gotchas

01
asimov.md is not for hand edits, except the values
Because it is regenerated wholesale (R2), anything a developer types into asimov.md is lost on the next run — except enabled/disabled, which the run reads back as its default. Repo-specific context belongs in CLAUDE.md or AGENTS.md, which the skill never writes into.
02
The context arrives at session start, not mid-session
The hook runs on startup, resume, clear and compact in Claude Code and at every start in Codex; a marker written by this run reaches the agent on the next session, not retroactively this one. The convention READMEs keep their own caveat: the Read tool expands no @-references, the role skills follow them by hand (D100 §7.2.1).
03
Taxonomy is a multi-command fork point
The documentation/ layout is shared with the D101 commands. Changing it here without the others breaks lockstep (D100 hard rule 9).
04
Convention READMEs are skeletons, not rules
A scaffolded read-list references convention files that may not exist yet. Until the team fills it in, the subagents' overlay is structurally present but empty — that's by design (OOS2), not a bug.
05
Codex: where you are is not where the plugin is
The working directory is the product repo; the skill and its templates sit in Codex's plugin cache under the home directory. A relative plugin path resolves from the working directory and misses, so every plugin path is built absolute from the derived <plugin-root> (§6.1).
06
The shells update on re-run; the context on plugin update
The .codex/agents/ copies are snapshots taken when the skill runs, so a newer plugin's shells reach a repo only on the next run. The context is the opposite: it is read from the plugin at every session start, so a plugin update changes what every marked repo is told with no run at all.
07
Codex runs Windows hooks in PowerShell, and trusts per hash
A hook command of the form "path" arg fails silently under PowerShell, which is why hooks-codex.json carries a commandWindows through run-hook.ps1. Every change to a hook changes its hash and asks the developer to trust it again, and the app keeps the registrations it loaded until it restarts — the three things that cost the first Codex run a day. Codex also clamps a SessionEnd hook to three seconds.
08
Codex subagents get the session text too
A Codex subagent inherits the parent's injected session context and then gets the SubagentStart note on top; Claude Code's Explore gets the note alone, its custom subagents the note plus CLAUDE.md. Harmless, but the note repeats the layout for that reason.

§8Open questions

Q1Allan Borup
Should asimov.md live at the repo root (current decision, §4.5) or under .claude/asimov.md? Resolved 2026-11-13: the root. The file is a marker both tools' hooks look for at the working directory, and a .claude/ location would hide it under one tool's folder.
Q2Allan Borup
As new build subagents (new stacks) land, which additional test-framework markers should count toward the test stack — e.g. Vitest, Playwright, or a non-*Tests.csproj naming? The current markers (§6.4) are settled; this tracks only forward extension. Resolution: extend the §6.4 marker set per new build subagent.
Q3Allan Borup
Should /docs-init survive as a thin alias for muscle memory during the transition, or be removed outright on rename? Resolved 2026-09-15: clean rename, no alias — no docs-init.md ships; /asimov-init supersedes it.
Q4Allan Borup
Does asimov.md need a "do not edit — regenerated by /asimov-init" banner to stop developers treating it like CLAUDE.md (gotcha §6.8.01)? Resolved 2026-09-15: yes — asimov-md-template.md opens with a "do not edit" banner naming the generation date; since 2026-10-01 it reads "Generated content" and sends the developer's own context to CLAUDE.md (Claude Code) or outside the markers in AGENTS.md (Codex), because one render fills both carriers.
Q5Allan Borup
On macOS and Linux the hook is plain bash in both tools, and Codex's hook shell there is assumed to be a POSIX shell, so command alone should do; nothing of it has run outside Windows. Resolution path: one run on a Mac with the plugin installed, in each tool, before the first non-Windows user.
Q6Allan Borup
opencode reads no hooks.json. Does it get the marker through a hook form of its own, or the old AGENTS.md region after all? Resolution path: decided in D101-opencode-support.html (PR 37), which must align with the marker before it merges.
