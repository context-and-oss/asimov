D101 · Feature design · Asimov plugin

/asimov-init

Bootstrap a product repo to use the Asimov toolkit — scaffolds the documentation/conventions/<stack>/README.md read-lists the build subagents depend on, generates the documentation/ landing site, and gives the coding agent its Asimov context: in Claude Code an Asimov-owned asimov.md wired into CLAUDE.md via an @-import, in Codex a managed region in AGENTS.md plus the Codex subagent shells copied into .codex/agents/. Supersedes /docs-init. Ships once per tool: the /asimov-init slash command for Claude Code and the codex-asimov-init skill for Codex.

Archetype
Greenfield (evolves /docs-init)
Scope: The Asimov setup entry point shipped by asimov-plugin, in two forms with one purpose: the /asimov-init slash command (Claude Code) and the codex-asimov-init skill (Codex). Run once in a product repo to make it Asimov-ready: both scaffold detected-stack convention read-lists under documentation/conventions/ and write documentation/index.html + documentation/_chrome.css. The Claude Code command writes asimov.md and ensures CLAUDE.md imports it; the Codex skill instead writes an Asimov-managed region in AGENTS.md and copies the plugin's agents/*.toml shells into .codex/agents/. Neither writes the other's targets. Both are read-only on every other file in the repo. Renames and absorbs the former /docs-init. §2–§5 are tool-neutral except where a target is marked Claude Code-only or Codex-only; §6.1 holds the per-tool split.

§2Why this exists

Installing asimov-plugin makes the commands and subagents available, but a freshly-installed repo is not yet ready for them. The build subagents read convention files that don't exist; Claude has no repo-level memory of the L3 taxonomy; and the documentation landing page has to be hand-built. Before this command, /docs-init solved only the last of these. /asimov-init closes the whole gap in one guided run.

01
Subagents read files that aren't there
Giskard, Daneel, and Calvin load documentation/conventions/<stack>/README.md as a load-bearing read-list (D100 §7.2.1). In a fresh repo that file is absent, so the convention overlay is silently empty.
02
No repo-level Asimov memory
Claude opening the repo has no standing context about the L3 taxonomy, where D101s live, or which Asimov commands exist — so it can't orient or auto-delegate without being told each session.
03
Setup spread across steps
Before this command a developer ran /docs-init, then hand-edited CLAUDE.md, then hand-created convention folders. Three manual steps, each easy to skip, with no single "you are now Asimov-ready" moment.
04
Hand-edited CLAUDE.md is risky to touch
A command that rewrites a developer's existing CLAUDE.md can clobber hand-written context. Asimov context needs a home it can regenerate without owning the whole file.
Audience. A developer adopting asimov-plugin in a product repo for the first time (or refreshing an existing setup), who wants the repo wired for the L3 commands and subagents in one run — plus the Asimov repo itself, which dogfoods the command.

R14
The command derives the repo name from its input ($ARGUMENTS in Claude Code; the text after the invocation in Codex) when non-empty, otherwise from the git remote origin URL, otherwise from the working-directory folder name.
R15
The command presents a single consolidated write plan listing every target (each convention README, index.html, _chrome.css — plus, in Claude Code, asimov.md and the CLAUDE.md edit; in Codex, the AGENTS.md region and each .codex/agents/ shell) with its action drawn from one canonical set — NEW · OVERWRITE · APPEND · MERGE · SKIP · ASK — and waits for explicit confirmation before writing anything.

R18
When the repo ships 3+ sibling docs of one category (per the §6.4 detection rule), the command MAY add an entity gallery to the index, one tile per sibling linking to that sibling's doc.
R19

R20
When the repo has an orientation source — the README.md intro, else a charter/overview doc under documentation/, else the D100 Purpose section — the command MAY add 2–3 short overview paragraphs to the index between hero and catalogue, naming the source used in the write plan and report; with no source it emits none.
R21
Codex skill only. The skill renders asimov-md-template.md (the same substitutions as asimov.md, leading comment stripped) directly into a managed region of AGENTS.md at the repo root, between <!-- asimov:start --> and <!-- asimov:end --> markers — creating the file with only the region when absent, appending the region at the end when the file exists without markers. The region is rendered from the template, never copied from an asimov.md.
R22
Codex skill only. On re-run against an AGENTS.md with exactly one intact marker pair, the skill replaces only the text between the markers; every line outside the markers is left unchanged.
R23
Codex skill only. When the AGENTS.md markers are broken or duplicated (a start without an end, an end without a start, more than one pair), the skill writes nothing to that file, labels the target ASK, and asks the developer to repair or delete the region by hand.
R24
Codex skill only. The skill copies each agents/*.toml shell in the plugin byte for byte into the product repo's .codex/agents/ — NEW when absent, OVERWRITE when present — using a file copy, never a read-and-rewrite; when the plugin's agents/ holds no .toml, the target is skipped and the plan says so.
NF1
The command is read-only on every file in the repo except its declared write targets; it never calls Write on a source doc, and its only edits to an existing file are the managed region of an existing convention README, the additive CLAUDE.md import line (Claude Code command only), and the AGENTS.md managed region plus the Asimov-owned .codex/agents/*.toml copies (Codex skill only). The Claude Code command writes neither AGENTS.md nor .codex/agents/; the Codex skill writes neither asimov.md nor the CLAUDE.md import.
NF2
Claude Code command only. The CLAUDE.md edit is idempotent: re-running the command when the @asimov.md import is already present adds nothing and reports SKIP.
NF3
The generated index.html is pure static HTML + CSS — no JavaScript, no client-side behaviour — and links to _chrome.css rather than inlining it.
NF4
All templates are re-read at the start of every invocation; the file in the plugin is the run-time source of truth.
NF5
The command's first output is a one-sentence narration of what it will do, emitted before any tool call.
NF6
The Claude Code command runs on claude-opus-5-5, matching its row in model-choice.md §1. The Codex skill names no model — its frontmatter carries no model key.
NF7
The Asimov-managed region in an existing convention README is delimited by explicit <!-- asimov:start -->/<!-- asimov:end --> markers so a re-run refreshes exactly that region; the same markers delimit the AGENTS.md region the Codex skill writes (R21). The CLAUDE.md import needs no markers — it is a single bare @asimov.md line, located on re-run by reference.
NF8
The Codex skill is kept out of Claude Code: its frontmatter carries disable-model-invocation: true and user-invocable: false, so Claude Code neither lists nor triggers it; /asimov-init is the Claude Code entry point. Its agents/openai.yaml sets allow_implicit_invocation: false, Codex's own switch, so Codex runs it only on explicit invocation.
OOS1
Authoring the full repo CLAUDE.md / analysing the codebase to describe the product. Why: that is Claude's own /init; /asimov-init only adds the Asimov layer via @asimov.md and points the developer at /init for the rest.
OOS2
Authoring the convention content (the actual coding rules). Why: the command scaffolds the read-list skeleton; the team fills in the rules. Guessing rules would bake wrong conventions into the subagents' overlay.
OOS3
Authoring doc bodies (D100/D101 content). Why: that is the job of asimov-design and siblings; /asimov-init only indexes and scaffolds.
OOS4
A config mechanism for the documentation/ path taxonomy. Why: the layout is intentionally a code fork point shared across the D101 commands, not a one-toggle config (D100 hard rule 9).
OOS5
Installing or verifying the plugin itself. Why: marketplace install is a developer step done before the command runs; the command assumes the plugin is present.
OOS6
Writing L3 process-rule docs or configuring PR / Copilot settings. Why: process enforcement lives in product-repo settings, not in the toolkit (D100 §3); deferred out of this command's scope.
4
Business design
The principles the command holds to, its vocabulary, the targets it writes — two shared by both tools, two written by the Claude Code command only, two by the Codex skill only — the conditional generation rules with counter-examples, and the decisions taken with their rejected alternatives.

§4.1Principles

1
One run to Asimov-ready. A single guided command takes a fresh repo from plugin-installed to fully wired — context, conventions, and docs site — instead of three manual steps.
2
Own what you write, touch nothing else. In Claude Code the Asimov context lives in asimov.md, which the command owns and regenerates freely, and CLAUDE.md only gains a one-line @-import. In Codex, which expands no imports, the skill owns a marked region in AGENTS.md and touches nothing outside the markers.
3
Scaffold structure, never invent content. The command creates the convention read-list skeleton and the import wiring; it never guesses coding rules or product context.
4
Detect, don't assume. Stacks are discovered from real repo markers; an undetected stack yields no folder and an explicit report line, not a guessed default.
5
Read-only on everything else; confirm before writing. The command shows one consolidated write plan and waits; outside its declared targets it never mutates a file.
6
Plugin templates are the run-time source of truth. Every template is re-read each invocation so the wiring and visual language can't drift.

§4.2Vocabulary

The domain terms the command and this design share. Green = an artefact the command produces; amber = a derived value; cyan = an input structure or mechanism it relies on.

asimov.md

The Asimov-owned context file the Claude Code command writes at the repo root. Holds the L3 taxonomy, doc locations, convention-overlay pointers, and the command/subagent inventory. Regenerated wholesale on every run.

@-import

A @path line in CLAUDE.md that Claude Code expands into context at session start. @asimov.md is how the Asimov layer reaches Claude without living inside CLAUDE.md. Codex does not expand @ lines, which is why its context arrives inline instead (see Managed region).

Convention read-list

A documentation/conventions/<stack>/README.md that @-references every convention file in its stack. The build subagents read it to load the local overlay (D100 §7.2.1).

Stack detection

Inferring which stacks a repo uses from marker files (*.csproj → dotnet, angular.json → angular). Drives which convention read-lists are scaffolded.

Managed region

A marker-delimited block (<!-- asimov:start --> … <!-- asimov:end -->) the command refreshes inside a file it doesn't own, so a re-run updates exactly that block (NF7): an existing convention README (both tools) and AGENTS.md, where the Codex skill carries the Asimov context rendered from the same template as asimov.md, because Codex reads AGENTS.md, not CLAUDE.md (R21). The CLAUDE.md import needs none — it is a single bare line, detected by reference.

Codex subagent shells

The plugin's agents/*.toml files — one per Asimov subagent. The Codex skill copies them byte for byte into the product repo's .codex/agents/; they are Asimov-owned there and overwritten on every run (R24).

Write plan

The single consolidated list of every target and its action (NEW · OVERWRITE · APPEND · MERGE · SKIP · ASK) shown for confirmation before any write (R15).

§4.3.1CONV
Convention read-lists
"What do the build subagents load as their local overlay?"
For each detected stack, scaffold conventions/<stack>/README.md from the template when absent; offer a managed-region merge when present (R6–R9).
  • Skeleton only — a read-list with placeholders, not real rules (OOS2)
  • No stack detected → no folder, explicit report line (R9)
§4.3.2SITE
Documentation site
"Where do the repo's docs live as a browsable landing page?"
Write documentation/index.html (six-bucket taxonomy) and _chrome.css — the catalogue behaviour inherited verbatim from /docs-init (R10–R12).
  • One card per unique doc; empty buckets dropped; sources never edited
  • Optionally fronted by an intro zone — overview prose / flow band / entity gallery — when the repo supports it (R17–R20, §6.4)
  • _chrome.css identical to template → left untouched
Claude Code-only targets — written by the /asimov-init command, never by the Codex skill
§4.3.3asimov.md
asimov.md (repo root)
"What standing context does Claude need about this repo's L3 setup?"
Asimov-owned. Written from the plugin template, filled with repo name and detected stacks. Regenerated wholesale on re-run (R1, R2).
  • Holds taxonomy, doc locations, convention pointers, command/subagent inventory
  • Not for developer edits — they belong in CLAUDE.md, which survives re-runs
§4.3.4CLAUDE
CLAUDE.md import
"How does asimov.md actually reach Claude?"
Ensure a single @asimov.md line exists. Append it if missing; create a minimal CLAUDE.md if none exists; never touch other content (R3–R5).
  • Idempotent: re-run with the import present adds nothing (NF2)
  • Does not author the rest of CLAUDE.md — that's Claude's /init (OOS1)
Codex-only targets — written by the codex-asimov-init skill, never by the Claude Code command
§4.3.5AGENTS
AGENTS.md managed region
"How does the same context reach Codex, which reads AGENTS.md and expands no @-imports?"
Carry the Asimov context, rendered straight from asimov-md-template.md, inline between <!-- asimov:start --> and <!-- asimov:end -->. Absent file → create it with only the region. Present without markers → append the region at the end. Present with one intact pair → replace only the text between the markers (R21–R22).
  • Codex's counterpart of asimov.md + the import — the skill writes neither of those (NF1)
  • Everything outside the markers is the developer's and is never touched
  • Markers broken or duplicated → nothing written to the file; the plan shows ASK and the developer repairs it by hand (R23)
§4.3.6.codex
Codex subagent shells
"How do the plugin's Codex shells get into the product repo?"
Copy each agents/*.toml in the plugin byte for byte into .codex/agents/ — NEW when absent, OVERWRITE when present. Asimov-owned, regenerated wholesale like asimov.md (R24).
  • A file copy, never a read-and-rewrite — encoding and line endings stay as shipped
  • Hand edits to a copied shell are lost on the next run; no .toml in the plugin → target skipped and said so in the plan

§4.4Generation rules

The conditional rules that govern what the command writes. Each carries a positive example and a counter-example — the adjacent case where the rule does not fire.

asimov.md regeneration (Claude Code only)
Overwrite
As an Asimov-owned file, asimov.md is regenerated wholesale every run — there is no merge step to preserve.
  • Existing asimov.md → replaced with the freshly rendered version
  • Developer notes placed in asimov.md are lost — they belong in CLAUDE.md
CLAUDE.md import (Claude Code only)
Append-once
Add the @asimov.md line only when absent; otherwise leave the file exactly as-is.
  • CLAUDE.md without the import → import appended, rest untouched
  • Import already present → nothing written, action reported as SKIP (NF2)
Stack detection
Marker-driven
Scaffold a convention read-list only for stacks whose marker files are found in the repo.
  • A *.csproj present → conventions/dotnet/README.md scaffolded
  • No angular.json anywhere → no conventions/angular/ folder created (R9)
Existing convention README
Merge / Ask
When a stack README already exists, offer to refresh only the Asimov-managed region; never overwrite the whole file silently.
  • Existing README with a managed region → region refreshed, hand-written rules kept
  • Existing README without a managed region → command asks before inserting one
_chrome.css special-case
Skip / Ask
Write when absent; leave untouched when byte-identical to the template; prompt overwrite/keep/diff when it differs.
  • Existing file identical to template → not rewritten, mtime preserved
  • Existing file differs → command asks first, never overwrites silently
Index de-duplication
1 card
A doc is identified by base name; if both formats exist, emit one card with the HTML badge only (inherited from /docs-init).
  • D101-foo.md + D101-foo.html → one card, HTML badge
  • Only D101-foo.md exists → one card, MD badge (no collapse of a lone file)
Index intro-zone showcase
Opt-in
Between hero and catalogue, optionally emit overview prose, a typed flow band (each node typed by a repo-defined kind, with a legend) and/or an entity gallery — derived only from a real source, never invented (R17–R20; detection rule in §6.4).
  • README intro / overview doc / D100 Purpose present → 2–3 overview paragraphs; architecture doc describes a named pipeline → flow band; 3+ sibling docs of one category → entity gallery linking each
  • No documented pipeline / no sibling cast → block omitted (flow band noted as a suggested manual enhancement) — a wrong diagram is worse than none
AGENTS.md region (Codex only)
Region-refresh
Write or refresh only the marker-delimited region; the rest of the file is the developer's (R21–R23).
  • Existing AGENTS.md with one intact marker pair → text between the markers replaced, every other line kept
  • Markers broken or duplicated → nothing written to the file; the plan shows ASK and asks for a hand repair
.codex/agents/ shells (Codex only)
Overwrite
Asimov-owned copies of the plugin's agents/*.toml, regenerated wholesale every run like asimov.md (R24).
  • Existing .codex/agents/baley-the-code-reviewer.toml → replaced with the plugin's current file, byte for byte
  • Plugin agents/ holds no .toml → no copy made and nothing deleted; the target is skipped and the plan says so

§4.5Decisions

A decision recorded without its rejected alternative is one that gets re-litigated.

Alternative considered
Why rejected
Asimov context in a standalone asimov.md, wired via @asimov.md import
A marker-delimited Asimov block written inside CLAUDE.md
A standalone file is Asimov-owned and regenerated wholesale with no marker parsing and zero risk to the developer's own CLAUDE.md content. It also mirrors the convention-overlay's own @-reference mechanism (D100 §7.2.1), so the repo uses one consistent wiring pattern.
asimov.md at the repo root, next to CLAUDE.md
.claude/asimov.md (tucked under the Claude config folder)
Root keeps the file discoverable beside the CLAUDE.md that imports it and makes the @asimov.md path trivial. The tidier .claude/ location is the open alternative tracked in Q1 — easy to switch since only the template path and the import line change.
Only wire the Asimov layer into CLAUDE.md; defer full repo context to Claude's /init
/asimov-init authors the entire CLAUDE.md by analysing the codebase
Repo-context authoring is exactly what Claude's built-in /init already does well; duplicating it would risk clobbering hand-written context and put two tools in charge of one file. Asimov owns only its layer.
Detect stacks from marker files; scaffold only what's found
Always scaffold a fixed set (dotnet + angular + test) regardless of repo
Empty folders for stacks a repo doesn't use are noise that reads as "forgot to fill in". Detection keeps the scaffold honest and the report meaningful.

A pure skip leaves a repo that pre-dates the read-list convention permanently un-upgraded. A managed region lets the command add or refresh the Asimov read-list scaffolding while preserving the team's hand-written rules.
Rename and absorb /docs-init into /asimov-init
Keep /docs-init as a separate command that /asimov-init calls
One entry point is the whole point — "make this repo Asimov-ready". The docs-site step is one of four; a separate command splits the mental model and doubles maintenance for no real standalone use case.
Run the Claude Code command on claude-opus-5-5; the Codex skill names no model
Keep /docs-init's Sonnet (then claude-sonnet-4-6)
Authoring repo-orienting asimov.md prose, judging stack detection from ambiguous markers, and safely merging into existing files demand more judgment than mechanical docs-indexing. The run is infrequent (once per repo) so cost is secondary. A Codex skill declares no model, so the choice applies to the Claude Code command only.
For Codex, render the context template straight into an AGENTS.md managed region; the skill writes neither asimov.md nor CLAUDE.md
Write asimov.md and the CLAUDE.md import in Codex too and copy the asimov.md body into AGENTS.md; or a single @asimov.md line in AGENTS.md, mirroring the CLAUDE.md wiring
Codex reads AGENTS.md, not CLAUDE.md, and does not expand @ imports — the line would be dead text, and an asimov.md nothing in Codex reads would be a dead file. The managed region gives Codex the same context Claude Code gets through the import, and the markers keep the refresh bounded to the part Asimov owns.

Technical design
Where each tool's entry point lives and how it finds the plugin, the run flow, the files it reads and writes, the detection lookup and content outlines, configuration, failure handling, and the gotchas an implementer should expect.

§6.1Platform

The setup entry point ships once per tool, both inside asimov-plugin. Both read the same seven plugin files — four templates and three definitions under artifacts/root/asimov-md/ and artifacts/documentation/{conventions,site}/ (the per-artifact folders that replaced the retired templates/ folder on 2026-09-10) — and write into the active product repo's working tree. Both are granted Read, Write, Glob, Grep, Bash. No services, schema, or infrastructure are involved. The two differ in where they live, how they are invoked, how they find the plugin, and the context carrier each writes — asimov.md + the CLAUDE.md import in Claude Code (§4.3.3–§4.3.4), the AGENTS.md region + the .codex/agents/ shells in Codex (§4.3.5–§4.3.6).

Ten stages from invocation to report — stage 2b (the maturity notice) was added 2026-09-15 without renumbering the rest. Green = entry / gating, cyan = read, amber = transform / compute, coral = the single write step. Confirmation (stage 7) gates every write.

§6.8Known constraints & gotchas

01
asimov.md is not for hand edits
Because it is regenerated wholesale (R2), anything a developer types into asimov.md is lost on the next run. Repo-specific context belongs in CLAUDE.md, which the command only appends to.
02
@-imports load at session start, not via Read
CLAUDE.md @-imports are expanded by Claude Code's context loader; the Read tool does not auto-expand them. The same caveat the subagents face with convention READMEs (D100 §7.2.1) applies — a freshly written asimov.md reaches Claude on the next session, not retroactively this one.
03
Taxonomy is a multi-command fork point
The documentation/ layout is shared with the D101 commands. Changing it here without the others breaks lockstep (D100 hard rule 9).
04
Convention READMEs are skeletons, not rules
A scaffolded read-list references convention files that may not exist yet. Until the team fills it in, the subagents' overlay is structurally present but empty — that's by design (OOS2), not a bug.
05
Codex: where you are is not where the plugin is
The working directory is the product repo; the skill and its templates sit in Codex's plugin cache under the home directory. A relative plugin path resolves from the working directory and misses, so every plugin path is built absolute from the derived <plugin-root> (§6.1).
06
Codex: the region and the shells update on re-run, not on plugin update
The AGENTS.md region and the .codex/agents/ copies are snapshots taken when the skill runs. A newer plugin changes nothing in the repo until the skill runs again; like asimov.md, both reach their tool on the next session.
