Scope: How the Asimov toolkit is authored, generated and published so that Claude Code and Codex users get the same commands, subagents, personas and quality bars. §2–§5 are the business agreement; §6 carries the technical design and §7 the build recipe.

§2One toolkit, two tools

Context& is moving toward Microsoft Foundry for model hosting — including OpenAI's GPT models, where Codex is the natural tool — while Asimov today only exists inside Claude Code, so the method would not follow the move.

  • Distribution is Claude-only. The marketplace install and update path is the single way in, with no second route and no degraded mode.
  • Every shipped component carries Claude-specific binding. Command metadata, model names, plugin-root paths, skill locations and the context wiring are all written in one tool's vocabulary.
  • The method itself is already tool-neutral but unreachable. The definitions, templates and persona method need nothing Claude-specific, yet a colleague can only get at them through Claude Code.
  • A second tool would today mean a second hand-maintained copy. Two copies of the same method drift apart, and the drift is invisible until two colleagues get contradictory answers.
Audience. The colleagues on Context& projects, who must be free to pick Claude Code or Codex without losing any capability — and, secondarily, the toolkit maintainers, who get one source to maintain and two targets to publish.

4
Business design
The principles that make parity the contract, the shared vocabulary, what the neutral source covers, the named rules, and the decisions taken with their rejected alternatives.

§4.1Principles

1
Identical capability is the contract; the machine room may vary. Same commands, skills, outputs and quality bars in both tools — how each tool gets there is Asimov's problem, never the user's.
2
Tool independence is the default, not the exception. The neutral source is the product and each tool is a target, so no tool is privileged and a future one is another target rather than a rewrite.
3
The method lives in exactly one place. Definitions, bars, templates and the persona method exist once in the source, and everything generated is derived and never hand-edited.
4
The source carries intent, the generator carries precision. The source states a model tier and effort; one mapping table per tool resolves it to a concrete model, so a model upgrade is a deliberate decision with a single point of change.
5
The pipeline is the producer. People commit source only; CI generates, versions and publishes — and output that has not changed publishes nothing.
6
Ride the open standards where they exist. Where the ecosystem already shares a format, the toolkit adopts it directly instead of inventing a competing one.

§4.3What the neutral source covers

Five component families plus distribution — each stated as what it must deliver in both tools, with the file formats and paths left to §6.

Commands

"What happens when a colleague invokes an Asimov command?" — one source per command, invoked by name in either tool, running the same phases and writing the same output.

  • The interview runs in the main session; the pinned work that follows is handled by the tool's own delegation mechanism.
  • The six commands built today are covered; a command added later is authored once and reaches both tools.
Subagents

"Who does the code work?" — one source per role, carrying the same responsibilities, competence and boundaries in both tools.

  • Each role declares its own tier and effort, so the builder, tester and reviewer roles keep their intended weight.
Personas

"Who reads the document?" — the standard readers and any product-specific reader must be invokable in both tools.

  • Persona skills follow the shared ecosystem standard, so they pass through to both targets close to unchanged.
  • A custom reader authored in a product repo is subject to the same parity requirement as a shipped one.
Artifact definitions and templates

"Where does the method live?" — one folder per artifact (source/artifacts/<landing-place>/<artifact-slug>/, definition + template side by side) plus the shared source/resources/; already tool-neutral, shipped as they are, and read at run-time by the commands in both tools.

  • The existing discipline of reading the definition at run-time rather than inlining it survives the port unchanged.
  • Each definition opens with the artifact's maturity level (D101-artifact-maturity.html); the producing command reads it from the installed plugin in either tool, so the notice needs no per-tool mechanism. Amended 2026-09-21 (v1.2).
Context wiring

"How does a tool know about Asimov inside a product repo?" — the bootstrap command establishes the standing context each tool's own way, with the same content behind it.

  • Both tools are wired at bootstrap, so a colleague joining later inherits a repo that already speaks their tool.
Distribution

"How does a colleague install and update?" — each tool has its own marketplace mechanism, and both are fed from this repo and the same release.

  • Not every component family can travel by the same route in both tools; where a route is missing, the bootstrap command carries the payload instead.

§4.4Rules

Five rules govern how the source, the generated components and the models relate. Each carries the adjacent case where it does not apply.

Rule 1 — generated files are never hand-edited

A change to a generated component is made in the neutral source and regenerated, never typed into the generated file.

  • A wording fix in a command's prompt is made in the source, and the pipeline rolls it out to both tools.
  • Artifact definitions, templates and resources are not generated — they are source themselves (source/artifacts/, source/resources/, copied verbatim into both plugins), so editing them directly is correct practice, not a breach of this rule.
Rule 2 — unchanged output publishes nothing

When regeneration produces byte-identical output, there is no commit and no release.

  • A documentation-only change leaves the generated trees identical, so no new version appears.
  • A single changed word in a command source does produce a difference, and that difference is published as a new version.
Rule 3 — the parity gate

A capability ships only when it works in both tools; an asymmetry is allowed solely where the tool offers no mechanism at all, and then only as a documented known limitation.

  • The model-mismatch alert ships in both tools even though it will rarely fire in one of them, because the structure must be the same.
  • Pinning the interview model in Codex is not a parity breach to fix but a known limitation, because the vendor has declined to provide the mechanism.
Rule 4 — model names live only in the mapping table

Concrete model names appear in one place; everything else speaks tier and effort.

  • A model upgrade is one row in the table plus a regeneration, rather than a hunt through every command.
  • A tier and effort written in a command source is not a model name and is exactly the intended source vocabulary; a concrete name in that same place would be the breach.
Rule 5 — a model mismatch is reported, never enforced

When a step is about to run on a model below its designated tier, the command says so and leaves the choice with the user.

  • Starting the design interview on an under-powered session model produces an alert before the interview begins.
  • A session running a better model than designated passes silently — the alert only ever fires downward.
  • The alert never swaps the model itself and never blocks the run — a colleague who deliberately continues is allowed to.

§6.1Platform

Everything lives in this repo: a hand-edited neutral-source tree, a Node.js/TypeScript generator, two generated plugin trees (one per tool), and the two GitHub Actions workflows that gate and publish. Product repos are touched only by the bootstrap command's outputs. Codex-to-Foundry wiring is each developer's machine configuration (~/.codex/config.toml) and stays outside the toolkit, per OOS2.

⚠ Escalation gate. The restructure moves the hand-edited tree and rewrites both workflows — land it together with the D100 rewrite (§10, hard rule 6), or the marketplace serves from a tree the pipeline no longer maintains.

§6.2Data flow — source to publish

Who owns each step from a source edit to both tools serving the new version — the hand-offs between the developer, the pipeline and the marketplaces are the point.

Source entry / gate Generation Version & publish Dashed — served by the tools
  1. 1
    The developer commits neutral source only and opens a PR — generated trees are never in the change (R7, rule 1).
  2. 2
    The PR gate generates twice and byte-compares the two runs — a difference between them is a determinism defect and blocks the merge (NF1, AC6).
  3. 3
    A gate failure is fixed in the source or the generator, never by editing generated files — nothing has been published yet.
  4. 4
    On merge, the release workflow regenerates and compares against the previous release (the latest tag) — main never carries generated trees, so the pipeline cannot retrigger itself, and the path filter documents what a release is made of.
  5. 5
    Byte-identical output stops the run: no commit, no version, no release (rule 2, AC7).
  6. 6
    Changed output is stamped, committed off-main and published in one run — sequential version tag (N.0.0) plus the rolling latest pointer; the release commit lands only on the tags, never on the protected main (Q1; §6.1 decisions).
  7. 7
    Both marketplaces serve installs from the latest release tag — Claude Code with its existing flow (R2), Codex via its plugin marketplace (R1).

§6.4.5The model-mismatch alert
  • Each generated command opens by comparing the running model — which the model reads from its own session context, in both tools — against its designated tier via the mapping table's rank column.
  • Running below the designated tier produces the alert, phrased against the tier, before the work starts; the run is never blocked (rule 5).
  • Running at or above the tier passes silently.
  • A model the table cannot rank produces a neutral note naming the designated tier — never an alert, never silence.

§6.8Known constraints & gotchas

⚠ Codex path resolution is a convention, not a substitution. Claude Code replaces ${CLAUDE_PLUGIN_ROOT} mechanically before the model reads anything; in Codex the skill-relative path works because the tool hands each skill its own absolute directory in context and the model combines the two (probe-verified 2026-09-03). It held cleanly under test, but it is the weaker guarantee of the two.
⚠ Codex silently ignores model fields in SKILL.md frontmatter. A nonexistent model declared there loads without a warning (probe-verified) — a model designation only takes effect at subagent delegation via the agent TOML. Never "fix" a Codex skill by adding a model field.
⚠ Agent TOMLs update on bootstrap, not on plugin update. A toolkit release updates plugins immediately, but a product repo's .codex/agents/ files only change the next time someone runs /asimov-init there — a drift vector between the two tools until then.
⚠ Codex has no file tools; on Windows its shell defaults to ANSI. The command prompts say "use the Read tool", which exists only in Claude Code. Codex reads and writes through PowerShell, and Get-Content / Set-Content without -Encoding utf8 turned every em-dash in asimov.md, AGENTS.md and the site into â€” (observed 2026-09-22, first live /asimov-init in Codex on Windows). Mitigation: every command carries the shared {{file-io}} rule as its first hard rule — UTF-8 on both ends, byte copies for files that must stay identical, a mojibake spot-check before reporting done. A prompt rule is the only lever a skill has here; it is not a mechanism.
Codex does not expand @-references in AGENTS.md (probe-verified) — the managed region is the only carrier that reaches the model at session start.
Claude Code's availableModels allowlist fails silently. A skill's model override outside the organisation's allowlist is ignored and the session keeps its current model — that silence is the case R10's downward alert exists to catch.
The effort vocabularies are close but not equal. Claude Code runs low–max; Codex on the Context& Foundry provider reports none, minimal, low, medium, high, xhigh, max (verified 2026-09-21 — the v1.0 seed's ultra was rejected, and minimal conflicts with Codex's web_search tool). The mapping table translates explicitly, never passes through.
Main never carries the generated trees. Installs serve from the latest release tag; a local-clone install requires a generator run first (cd generator && npm install && npm run generate) because the trees are gitignored on main.

§7.1What is genuinely new to build

Everything not listed here is reuse; this is the whole of the new work.

§7.5Cross-cutting — shared by every unit

  • Determinism is built once. Sorted directory walks, LF line endings, no timestamps or run-dependent values in output — the generator's core owns it, both emitters inherit it (NF1).
  • One token-substitution implementation. Both emitters call the same substitution, so a token can never behave differently per target by accident.
  • One mapping-table parser. The generator and the mismatch-preamble injection read ranks through the same code — one truth about model ordering.
  • Hand-edits to generated trees are self-defeating. The next regeneration erases them and the PR gate surfaces them as unexplained diffs — rule 1 is enforced by the pipeline, not by discipline alone.

§9Open questions

No question is left open — all four were settled during authoring, the last of them the release trigger.

Resolved during authoring
Q1Resolved 2026-09-02
Should the existing release workflow move from manual triggering to running automatically on every merge to the main branch, and who owns that change?
Decision: it moves to automatic on every merge to the main branch, owned and decided by cka; it would reopen if the pipeline ever published somewhere the team does not control.
Q2Resolved 2026-09-02
Which language and runtime is the generator written in, given the repo has a pipeline but no build environment?
Decision: Node.js/TypeScript, because the team is mixed Windows and Mac; it would reopen if the team became single-platform, and the parsing and test-coverage caveats are carried into §6.
Q3Resolved 2026-09-02
How are models designated across two tools whose model vocabularies differ?
Decision: tier and effort in the source with one mapping table per tool as the only home for concrete names; it would reopen if a tool introduced real version-locked tier aliases.
Q4Resolved 2026-09-02
Does the bootstrap command cover one chosen tool or all supported tools?
Decision: all supported tools, because bootstrap writes committed project files; it would reopen if two tools' wiring ever conflicted in one repo.
