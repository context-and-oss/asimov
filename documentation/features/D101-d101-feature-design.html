/d101-feature-design

Turns a thin feature brief — a paragraph in chat, a pasted Jira ticket, a meeting note — into a D101, in three phases with a stop in the middle: requirements, then business design, then technical design. The run ends when the business design is written to disk; the mechanism waits for a second invocation.

Scope: The Design stage of the L3 pipeline (D100 §3, stage 1). System-level architecture (marketplace, plugin shape, distribution, model declaration) lives in D100-Asimov-architecture.md; this D101 covers the /d101-feature-design command itself. §2Purpose & audience

/d101-feature-design turns a thin feature brief into a D101, in three phases against the two bars in d101-feature-design-definition.md §2 — business-complete first (a business reviewer can agree to what will be built and why, before any mechanism exists), gap-free second (an implementer who never saw the conversation can act on it). It interviews the developer for missing inputs and writes the D101 into the active repo's documentation/features/ folder, once per design phase. Together with /d101-review it covers the AI-assisted half of the Design stage: authoring, then self-check. The human reviewer (≠ author) gate on the specs PR (D100-Asimov-architecture.md §3) is unchanged — the command makes that gate cheaper to pass, not redundant.

01
A full design arrives too early
Without a stop, one run produced §2 through §6 in a single pass. The document was well-formed and the business shape had never been argued — the fastest way to a design nobody agrees with.
02
Mechanism anchors the business design
Settling §6 while §4 still moves quietly reshapes §4 toward whatever was convenient to build. Afterwards nothing in the document marks which way the influence ran.
03
Chat is not a document
A business design the developer has only seen as conversation is a business design they have not read. Judgement about §4 needs the rendered page, side by side, in one view.
04
One bar had no name for "not yet"
With gap-free as the only bar, a deliberately unfinished §6 looked identical to a failed one — so the pressure was to invent mechanism rather than declare it open.
Primary audience. Developers in any product repo authoring D101s during the Design phase. Secondary: reviewers of the resulting D101 — they read what the command produced, so they care that the structure is predictable.
Not for. The Spec / Code / Review+Test stages — those have their own commands and subagents. Not for purely descriptive documentation of code where no design decisions remain to surface; reverse-engineered features are in scope (see R10, AC8) when there is design intent worth capturing — the command stays interview-driven either way.

§4.1Design principles

1
The business shape is settled before the mechanism. Phase B ends with a file on disk and the run over. What the business agrees to is argued while changing the answer is still cheap, and §6 cannot quietly pull §4 toward whatever is convenient to build.
2
The stop is a file, not a question. Ending the run at a written document — rather than asking "happy with §4?" and continuing — is what makes the gate real. The developer judges the business design by reading the rendered page, which is the only form their reviewers will ever see it in.
3
Unsettled is a state, not a failure. §6 at phase B is declared open with a named list of what is outstanding (d101-feature-design-definition.md §4.6). Naming the gap costs one paragraph; hiding it behind invented mechanism costs a rewrite, and a reader cannot tell the two apart.
4
Interview, don't guess. When the brief doesn't say, the command asks. Invented values rot silently; explicit TBD — verify is loud and reviewable.
5
The template is the contract. The command structures every D101 the same way. Predictable structure is what makes reviews cheap.
6
Neither bar's verdict is the command's. It previews §8a or §8b and says which checks it believes are weak. Business-complete is the author's call, gap-free the human reviewer's — a command that graded its own output would collapse both gates.
7
Stop at the boundary. The command does Design only. Beyond what §6 invites and what §7 records as the build recipe (d101-feature-design-definition.md §4.8), it does not propose implementation paths, file structures, or code — those belong to the S101 stage.

§4.3Flow

Trigger. A developer in a product repo runs /d101-feature-design. The command is normally invoked with no argument — the natural CC pattern is "run command, AI guides from there". An optional argument is treated as the developer's opening reply, or as a path to a D101 to continue. Outcome of run 1: a business design on disk, §6 declared open, the run over. Outcome of run 2: the same file at Full design, ready for human review.

Steps (from the developer's perspective)
1
Developer runs /d101-feature-design in the product repo.
2
Command loads d101-feature-design-template.html and d101-feature-design-definition.md from the installed plugin — both bars, not one (R4). Then it resolves the definition's maturity block to at most one chat line — the step 1b notice — and says nothing more about maturity for the rest of the run (R29).
3
Open, then resolve the phase (R18). Command lists the existing D101s and asks: continuing one, or starting fresh? Fresh → phase A. Continuing → it reads the file and takes the phase from the .phase-chip, falling back to whether a #s6-open section is present, falling back to Full design for legacy documents. A Business design file gets one question: keep working on §2–§5, or move to §6 (R19)?
4
Restate and confirm. Command paraphrases the feature back. Developer corrects misreadings.
5
Framing questions. Command asks: which product / repo; the business approver who will sign off (a target, not a recorded approval); the named decider for open questions; any sibling D101 to cross-reference; and the working slug.
6
Show the path — both runs. Command states that this run ends at §5 with a file on disk, and that §6 comes from a second run.
7
Phase A — requirements (R14). §2 audience and purpose, §3 requirements. Command infers what it can, asks only about gaps, pushes back on compound requirements, non-goals without reasons, and purpose written at code altitude. Ends with a summary in chat and a confirmation. Nothing is written.
8
Phase B — business design. §4 with its subsections, then §5 UI design and its interactive mockups (which are business design, not mechanism), then §8 acceptance criteria, §9 open questions, and back to §1. Command pushes back on rules without counter-examples, anonymous TBDs, code-altitude narrative, and ACs that root back to nothing. A rule the developer deliberately declines is recorded as an accepted deviation, signed and dated (R30). Every parked mechanism goes on the outstanding list for §6.
9
Preview §8a (no verdict). Command summarises the business design and runs the business-complete checks — 1, 2, 3, 4, 5, 7, 8 if user-facing, and 9 — flagging which it believes are weak. Check 6 is not run: a document at this bar deliberately cannot be turned into an S101 yet. Developer confirms before drafting.
10
Write, then stop (R15, R16). Command writes documentation/features/D101-<feature-slug>.html with the phase chip on Business design, §6 rendered as the Still to write block and §7 as the pending stub (R27), reports the path, names the next steps — and ends the run. Asked to continue to §6 anyway, it declines and offers to keep working on §2–§5, or to record the mechanism as an open question (R17).
11
Developer reads the rendered page. Optionally runs /d101-review, which resolves the same phase and reports against §8a, or a persona review that reads §2/§4 as one of the document's intended readers (/persona-list shows who is available; /persona-new authors a product-specific reader). Iterating on §2–§5 means running this command again against the file — which is phase B once more, not phase C.
12
Phase C — technical design, second run. Command re-reads the file, works the outstanding list as its agenda, fills §6.1–§6.8, then §7.1–§7.5 as the build recipe (outside both bars — R28), then §10, previews §8b (now including check 6 and check 10; §7 is not part of it), and writes — phase chip to Full design, open block and pending stub gone. If closing an outstanding item turns out to change §4, it says so and stops: that is a return to phase B, not something to paper over in §6.
13
Developer takes the document and an estimate to the business approver named in §1, and opens the specs PR for human review (≠ author) per D100-Asimov-architecture.md §3. The status chip moves to Approved by their hand, never the command's (R21).

"the mechanism can't do what §4 promised"
Stops and says so rather than quietly reshaping §4 or narrowing it inside §6. Returning to phase B is the correct move — a business rule changed by mechanism is a business decision, and it is not the command's to make.
09⚠
Phase chip and body disagree
"Full design chip, §6 still open"
Trusts the body over the chip when resolving the phase (R18), says which signal it went with in one sentence, and corrects the chip on the next write.

§4.4Rules / constraints

The phase model introduces three conditional rules. Each is stated with the case where it fires and the adjacent case where it does not, per d101-feature-design-definition.md §6.3 — the counter-example is what stops the rule being read more broadly than it is.

BR1 — the phase gate
One design phase per run
Phase C is reachable only in an invocation that did not itself run phase B.
  • Fires when phase B has just written the file in this run and the developer asks for §6 — the command declines and the run ends (R16).
  • Stays quiet when the run began against a file already at Business design and the developer chose to move to §6. Phase C is then this run's only design phase, and it proceeds normally.
  • The rule is about phases per run, not writes per file. A file may be rewritten at phase B any number of times across runs.
BR2 — §6 is open, not absent
A named outstanding list
At the Business design phase, §6 renders as one Still to write block carrying a list of real unknowns.
  • Fires when the interview parked mechanism — the block states the document is not gap-free and lists each unknown by the consequence of not knowing it.
  • Stays quiet when a section genuinely does not apply to the feature: an N/A stub with a one-line reason is correct there, and the outstanding list is not the place for it. N/A gives a reason; open gives a list.
  • A bare TBD, or a restatement of the §6.1–§6.8 headings, satisfies neither shape and fails check 9.
BR3 — the command owns one axis
Phase yes, status never
The command sets the .phase-chip on every write and never touches the Draft → Approved transition.
  • Fires when a write completes: the phase chip is set to match what was just written, whether or not the developer mentioned it.
  • Stays quiet when the developer says the business has approved the design. The command may record who the approver is in §1, but the status chip stays Draft — the transition is theirs to make, outside the toolkit (OOS5).

§4.5Decisions and alternatives

A decision recorded without its rejected alternative is one that gets re-litigated.

Decided
Alternative considered
Why this won
Argument default: No argument required — opens with invitation, treats argument (if any) as opening reply
Required argument with argument-hint suggesting "paste Jira ticket"; no-argument with shorter greeting
Most natural CC flow is "run command, AI prompts." Requiring an inline brief creates blank-page friction (the most reported friction per additional-command-ideas.md filter discussion). Long multi-line input on the command line is also awkward UX.
Interactive vs autonomous drafting: Interactive (interview mode by default)
Autonomous draft from input, manual revise after
Gap-free bar is hard to meet from a thin input; interviewing surfaces gaps before drafting, avoiding throwaway drafts.
Opening shape: Invitation → restate → 5 framing questions → show-the-path
Skip framing, go straight to §-walk; or ask framing questions interleaved with §-walk
"Blank page" is the load-bearing friction. Framing (system, approver, decider, sibling, slug) + showing-the-path tells the developer where they are and what's coming, before the section-by-section labor.
Slug derivation: Interactive confirmation
Heuristic from feature name
Input is often ambiguous; weird slugs are hard to rename across D101-, image folders, and references.
Template + definition handling: Read at run-time (by reference)
Embed in prompt body at install time
Updates to template / definition apply immediately on the next invocation without reinstalling (D100 §7.4).
Existing-file handling: Diff + 3 options (overwrite / alternative path / cancel), never silent overwrite
Always update in place; or always create variant
Developers iterate; silent overwrite erodes trust, always-variant litters the features folder.
Output writes during interview: One write per design phase — none in phase A, one at the end of B, one at the end of C
A single write at the very end (the previous rule); or streaming draft sections as the conversation proceeds
Reverses the earlier "exactly once" rule. The objection to partial files — that they read as "done" to other tools — is answered by the phase chip and the open-§6 block, which mark the state in the document. Streaming is still rejected: a half-written §4 on disk carries no such marker.
Where the business/technical boundary is enforced: A hard stop that ends the run, requiring a second invocation
Ask "is §4 finished?" and continue in the same run on a yes
A conversational yes can be given without opening the file, which is the failure the gate exists to prevent — judgement about §4 needs the rendered page. Ending the run makes reading it the only way forward, at the cost of one extra command invocation.
Command shape: One command with three internal phases, routed by the target file's phase
Two commands — /d101-business-design and /d101-technical-design
The file is the state, so a single command can resolve where it is and route correctly; two commands would add a second row to model-choice.md, D100 §4.3 and this documentation set without making the gate any harder to cross. The developer's mental model stays "I am designing a feature".
Phase and approval as two axes: Separate chips — phase (author) and status (business approver)
One chip with a combined scale (Business design → Full design → Approved)
They move independently and by different hands. A combined scale would imply a Full design document is closer to approved than a Business design one, and would let the phase axis drag the approval axis along with it.
UI mockups belong to phase B
Generate them in phase C alongside the mechanism
A UI surface is what the business agrees to, not how it is built — it is exactly the part of the design a non-technical reviewer can correct. Deferring it to phase C would leave the business design without its most reviewable artifact.
Review notes are folded in as input, never transcribed (R25, d101-feature-design-definition.md §4.10)
Copy the notes file's findings verbatim into the D101 as a record of what was reviewed
A transcribed finding is a fact about a past review, not about the feature — it would sit in the document like an anonymous TBD nobody asked. Folding a finding in the way a chat comment would be treated keeps the D101 about the feature, not about its own review history.
Deletion is gated on consumption, not on offer (R26)
Delete the notes file as soon as it is found, whether or not the developer used it
Deleting on sight would destroy the developer's only cross-session copy of findings they haven't acted on yet — the file exists precisely so a "not now" doesn't cost anything. It is disposable only once its content has actually reached the document.

§6.3Outputs

Writes a styled, self-contained HTML file at <repo>/documentation/features/D101-<feature-slug>.html. Structure matches d101-feature-design-template.html. Two write points, to the same path — the second supersedes the first in place.

Write 1 — end of phase B
  • .phase-chip = Business design (no .full class); .status-chip = Draft v0.1, or the next minor version when rewriting
  • §1 Document information — owner, business approver, version, status, scope. The .doc-scope line ends by naming what is settled and what is not
  • §2 Purpose & audience
  • §3 Requirements (functional, non-functional, out of scope)
  • §4 Business design (principles, concepts, rules with counter-examples, decisions)
  • §5 UI design with its embedded mockups when user-facing
  • §6 — the #s6-open Still to write block: a .callout.warn plus the named outstanding list. No #c6 chapter band, no §6.1–§6.8, one flat side-nav entry
  • §7 — the #s7-pending stub: one .callout.warn, no list, no #c7 band, one flat side-nav entry (R27)
  • §8 Acceptance criteria; §9 Open questions; §10 References, as far as they exist
  • §11 Changes from source — omitted for greenfield, included for reverse-engineered
Write 2 — end of phase C
  • .phase-chip = Full design with the .full class; .status-chip version bumped, Draft unchanged
  • §6 replaced: the #s6-open block removed, the #c6 chapter band and §6.1–§6.8 emitted, side-nav §6 entry nested
  • §7 replaced: the #s7-pending stub removed, the #c7 band and §7.1–§7.5 emitted — or the §7 N/A stub for a pure-reuse build — side-nav §7 entry nested (R28)
  • §10 References completed
  • Everything else carried forward from write 1 unless the developer changed it
⚠ Only §6, §7 and §10 are expected to change between the two writes. A phase-C write that also rewrites §4 has either quietly reshaped the business design to fit the mechanism, or is closing a §4 gap that should have sent the document back to phase B (§4.3 error path 08).
Mockup files — written in phase B, outside the D101
  • Written alongside write 1, as separate self-contained documents under documentation/features/mockups/d101-<slug>/ — one per surface, or one per screen with its overlays.
  • Not part of the D101 file, and not rewritten in phase C unless the UI design itself changed.
  • Each carries its own inline CSS and JS, approximates the product UI rather than the D101's dark chrome, and is embedded via <iframe class="mockup-frame"> with a relative path.

§6.4Failure handling (command-specific)

System-wide failure modes (install, manifest, missing model) are in D100 §8.5. Command-specific:

01⚠
Template file unreadable
Command halts and reports the missing path before any interview begins.
02⚠
Developer abandons mid-phase
Nothing is written for the abandoned phase; CC's chat history retains the in-progress state. Abandoning phase C leaves the file at Business design, which is a valid state to be found in — the loss is one conversation, not the document.
03⚠
Document doesn't meet its bar despite the interview
§8a is caught by the author reading the written page, optionally via /d101-review; §8b is caught at human review on the specs PR. The command surfaces gaps before drafting; closing them is a developer + command joint responsibility.
04⚠
Existing D101 has unrelated content the command doesn't recognise
Treated as a structural mismatch; command shows the diff and presents the same three options as R8 (overwrite / alternative path / cancel).
05⚠
Phase unresolvable from the file
No chip, no open block, and §6 ambiguous — the command treats the document as Full design, says so in one sentence, and sets the chip on the next write. Legacy .md D101s land here by design (R18).
06⚠
Diagram templates missing or unreadable
No standard notation available. Severity low: the command draws a flowchart instead, reports that in chat, and carries on — the diagram templates are a best-effort input, not a hard stop like the visual template (R22).

§6.5Known constraints & gotchas

01
Slug derivation
Feature slugs come from interactive confirmation, not heuristic parsing — "Account Administration" should land as D101-account-administration.html, not D101-account-admin.html, and the developer confirms.
04
Phase C starts from the file, not the conversation
The two runs are usually separated by hours or days, so phase C has no memory of phase B — it re-reads the document. Anything agreed in the phase-B chat but never written down is gone. That is the intended pressure (it forces the document to carry the design), but it means a phase-B run that ends without a write loses real work.
05
Legacy D101s have no phase
Every D101 written before this change carries no phase chip and is treated as Full design — which is right for finished documents and wrong for any that were abandoned half-written. The chip is set on the next write; until then the fallback can flatter an unfinished document.
02
Template fork
The command reads the template as installed — if d101-feature-design-template.html lags behind the source template in any product repo, the command produces stale-structure D101s. See D100 §10 Q3.
03
No multi-feature drafting
One invocation produces one D101. Drafting two related features is two runs.
