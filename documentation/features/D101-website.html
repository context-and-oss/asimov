§2Why this exists

The site exists, but its design record is a stale markdown file, three General pages are stubs, and nothing on the site says that the plugin ships a delivery model and its first pm-* skill. The site is for a developer, lead or sponsor who has not installed Asimov; this document is for whoever edits site/.

§3Requirements

Functional — 8
R1
Every page can be read without access to the repository.
R2
The site restates no rule from a definition; it links to the definition, template and D101 on GitHub.
R3
Every artifact page shows the artifact's maturity level from its definition, or planned when no definition exists.
R4
Every page carries the same navigation: Home · Why · How it works · What's inside · Artifacts (Documentation, Project management, General) · AI transition · Get started.
R5
"What's inside" is an overview that describes each kind of thing in the plugin in one sentence, without counts, and links to one page per kind under the same sub-nav.
R6
Project management is told under "What's inside": the delivery model, the advisor that reads it, and that a pm-* family is planned. The area page under Artifacts stays planned, names no skill, and points to the story until the first artifact lands.
R7
The three stub pages (personas, conventions, asimov.md) carry content in the artifact-page shape (§4.3).
R8
Every internal link resolves to a file.
Non-functional — 4
NF1
No build step: plain HTML, one stylesheet, Netlify publishes site/ as it is.
NF2
Links are relative, so the site works from file:// and at any folder depth.
NF3
English; every h1 under eight words, every lede one sentence, bullets and one-liners over paragraphs.
NF4
No customer product names anywhere on the site.
Out of scope — 4
OOS1
A custom domain — Netlify's default URL until one is procured (Q1).
OOS2
A page per pm-* skill — one member, no settled shape; the family shares the project-management page (Q3).
OOS3
A100 and S100 in CLAUDE.md or D100 — the codes are added together when more artifacts land.
OOS4
A build step, templating or a JS nav include — a pasted nav is the price of no tooling.

Business design
Page shapes, rules, decisions.

§4.3Page shapes

Narrative page

One h1, one lede, one figure, short prose.

  • Home shows L2 to L3, the nine stages, and three worked examples of the tooling in use.
  • What's inside is an overview: one sentence and a link per kind. Each kind has its own narrative page under the same sub-nav: commands, personas, agents, project management.
  • Project management tells the delivery model (phases, approaches, disciplines, one figure), the advisor that reads it, and what will land under Artifacts.
Area page

What the area is, then a table of its artifacts: code · name · maturity · one line.

  • Documentation carries the document-model figure and the maturity legend.
  • Project management has no table yet: one lede with the planned chip, and a pointer to the story under What's inside.
Artifact page

h1 with code and name, lede with maturity chip, meta rows (produced by · lands in · read by), two to five points, links to definition, template and D101.

  • D101 is the worked example; every other artifact page copies its shape.
  • A planned artifact fills h1, chip and one paragraph, and has no links block.

§4.4Rules

Rule
Description
Explain, don't define
A page says what an artifact is and links to its definition for the rules. A plugin thing with no definition links to its file instead.
Chip mirrors definition
An artifact page's chip equals maturity in the definition it links to; no definition means planned. A skill or agent gets no chip.
Link only what exists
The links block lists the definition, template and D101 that exist. A planned artifact has no links block.
No counts
No page says how many commands, personas, agents or templates there are. A code such as D101 is a name, not a count.
Codes as drawn
Document codes appear as in the document-model drawing, S100 and S101 included. The Delivery Model's own codes are not shown until an Asimov artifact carries one.
Story and file, on purpose
What's inside tells the story; Artifacts describes the file. Personas: the readers who sign under What's inside, the skill file under General. Project management: the delivery model under What's inside, the artifact table under Artifacts. Each side links to the other.

Technical design
Where it lives, how a change gets live, what the check enforces.

§6.1Platform

Static files under site/, served by Netlify from a manual upload. No build, no server, no git connection. One script, documentation/website/check-site.mjs, enforces the §6.4 shapes before merge, locally and in the PR workflow. The manual deploy is temporary (Q6); until then live and main can differ, so whoever deploys opens the live URL.

§6.2Publishing flow

Entry / gating Check Write: merge, deploy Delegated to Netlify
1
Edit. Change a page; a new page gets the canonical nav block.
2
Check. node documentation/website/check-site.mjs exits 0 before the PR.
3
Gate. The PR workflow runs the same script; a failure blocks the merge.
4
Deploy. After the merge, upload site/ to Netlify and open the live URL.

§6.4Shapes

The nav block
Part
Contract
Canonical copy
The <nav class="nav"> element in site/index.html.
Per-page variation
Only two: the relative prefix on every href (../ per folder level) and which link carries class="on".
Check
Strip both variations; every page's nav must equal the canonical copy.
Sub-nav
An area's <nav class="subnav"> is repeated on every page of that area with the same two variations; the canonical copy is the area's index.html. Three areas today: inside/, artifacts/documentation/, artifacts/general/.
Chip ↔ definition

A chip is a span.chip with one level class. An area table's chip is a copy, checked against the same definition.

§7Implementation

Checked against site/, check-links.mjs and Asimov-PR.yml on 2026-09-24. Everything not listed exists today.

  • check-site.mjs replaces check-links.mjs: the same link walk plus the §6.4 checks (nav, sub-nav, chips, figures, no /-prefixed paths, no GitHub URL outside the §6.6 base). node:fs and node:path only; one line per failure, exit 1.
  • PR workflow: actions/setup-node@v4 with Node 22, then the script, as a step after the maturity check in the ci job.
  • personas, conventions, asimov.md: the d101.html skeleton, filled from each artifact's definition and D101. Links, nothing restated.
  • Figures: the two svg.scene blocks in index.html get files under site/figures/; same aria-label on file and inline copy. delivery-model.svg already has its file.
  • Deploy: drag site/ onto Netlify, or npx netlify-cli deploy --prod --dir site; open the live URL.
