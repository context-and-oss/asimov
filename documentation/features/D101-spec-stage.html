Spec stage

One approved D101 becomes one implementation plan (S101) and one task spec per task (S102), written by a command with a built-in validation loop, so a reviewer who is not the author can approve a plan that fresh builders can build from without asking.

Scope: the Spec workflow: /s101-implementation-plan, /s101-review, four artifact skills and the S101/S102 templates. The Build workflow (dispatch, ledger, verification, Baley against the spec) is out. §2–§5 are the business agreement; §6 is open — see §6.

§2Why the Spec stage

A D101 at Full design reaches a builder through chat today: the task cut, the order and the interfaces are decided invisibly, per run.

  • The graph lives in chat. Order and parallelism are re-decided every run.
  • One long task. The builder gets the whole feature: L2 with a file attached.
  • Names by guess. Two builders invent two names for the same thing.
  • §7 as a stopgap. Build notes live in the D101, where they do not belong.
  • Nothing to review between design and code. The reviewer sees the diff, never what the agent was told.
Audience. The developer planning a feature, the reviewer who is not the author, the person directing a run, and the build subagents that read an S102 as their brief. In one line: the command asks at most five questions, decides the rest, writes the plan and stops once; §3 is the contract behind that line.

§3Requirements

Functional — 23
R1
From one D101 at Full design, the command writes one S101 and its S102s to documentation/specs/<slug>/.
R2
A D101 not at Full design is refused, with the reason stated.
R3
Tasks are cut as vertical slices, one per D101 acceptance criterion; each slice is one phase in the S101.
R4
A slice that crosses stacks becomes one S102 per stack in the same phase.
R5
Every S101 opens with a Foundation phase: one skeleton S102 per stack.
R6
The skeleton is cut per slice: no two slice tasks that may run in parallel modify the same skeleton file.
R7
Every slice phase carries a Calvin S102 that writes the slice's acceptance test; that test is the phase's checkpoint.
R8
Every S102 is written for exactly one builder role.
R9
Every S102 is validated blind right after it is written.
R10
An S102 that fails validation is rewritten and validated again until it clears the buildable blind bar.
R11
An S102 that fails validation three times, or whose finding names a gap in the D101 rather than in the S102, stops the run; the command reports instead of rewriting.
R12
Once every S102 exists, the plan is validated as a whole against the dispatch-ready bar.
R13
A plan-level finding sends the affected S102s back into their own loop.
R14
/s101-review runs both validations on an existing plan and reports without changing any file.
R15
No command records an approval or moves a status.
R16
Run against a D101 that already has an S101 and whose requirements and acceptance criteria are unchanged in content, the command updates the plan in place and leaves every S102 that already clears its bar untouched.
R17
Run against a D101 whose requirements or acceptance criteria have changed in content since the S101 was written, the command writes a new S101 and marks the old one superseded.
R18
The plan validation warns, never refuses, when an S102 exceeds the size thresholds; the thresholds live in the S101 definition.
R19
The command explores the D101 and the repo before it asks anything.
R20
The command asks at most 5 questions, one at a time, each with a recommended default.
R21
Questions are asked only about the task cut, the phase boundaries and open D101 items that change the breakdown.
R22
Everything else the command decides itself and records as an assumption in the S101.
R23
The command stops once, when the S101 and every S102 are written and validated, with a findings list in chat.
Non-functional — 4
NF1
No product entity in templates, skills or commands (hard rule 7).
NF2
Specs are Markdown with YAML frontmatter; the task graph is machine-readable in the S101 frontmatter.
NF3
Commands read the definitions and templates by path at run-time (hard rule 3).
NF4
The Spec workflow writes only under documentation/specs/<slug>/.
Out of scope — 6
OOS1
Dispatch and the ledger — the Build workflow; designed once a real S101 has been run.
OOS2
The verification agent (code against S102 acceptance criteria) — the Test stage, Build workflow.
OOS3

4
Business design
Principles, concepts, the Spec workflow and its authoring loop, the architecture (commands, skills, artifacts), the rules, the plan lifecycle, and the decisions.

§4.1Principles

1
The spec is the product. What gets reviewed is the S101 and the S102s; code is the output.
2
Plan ≠ ledger. Run state never lives in a spec.
3
Cut vertically. One slice per acceptance criterion; the checkpoint is the criterion met.
4
Skeleton before bodies. Phase 0 turns the interfaces into code before anyone builds against them.
5
Validate blind. Whoever wrote the S102 does not test it.
6
Shape by script, content by model. Mechanical checks give the same answer every run.
7
Ask only what cannot be discovered. The D101 and the repo answer first.
8
Method in skills, conversation in commands. The same method serves every harness.

§4.2Concepts

The vocabulary the rest of this document and both spec definitions use.

Concept
What it means
S101
The implementation plan for one D101: task graph, phases, interfaces, constraints, escalation.
S102
One task for one builder: the whole brief a fresh agent receives.
Slice
The work that makes one D101 acceptance criterion pass, end to end.
Phase
A slice as a unit of the plan: its S102s plus a checkpoint.
Checkpoint
A state a reviewer can verify without reading code; for a slice, its acceptance test green, written at API level against the skeleton's public methods, end-to-end only where the repo's conventions name a runner.
Foundation phase
Phase 0: the skeleton, one S102 per stack, compiling with no bodies.
Skeleton
Classes, interfaces and public methods with summaries, cut per slice; the S101 interfaces as code, and in Angular with minimal templates so a build proves it.
Owned set
The files an S102 creates, modifies and tests; nothing else is touched.
Validation
The spec check before code: does the plan clear its bars and agree with itself.
Verification
The code check after build: run an S102's acceptance criteria against what was built (Build workflow).
Dispatch-ready
The S101 bar: every task can be handed to a fresh builder in graph order without asking the author.
Buildable blind
The S102 bar: a builder with no conversation history builds it and knows when it is done.
Spec workflow
D101 → S101 + S102s → validation → reviewer approval; this document.
Build workflow
Ready S101 → phase by phase → builders → verification → review → checkpoint; out of scope.

§4.3The Spec workflow

One D101 goes in on the left; one S101 and N S102s come out on the right. Commands carry the conversation, skills carry the method, and the same skills serve both commands.

Yours: the repository Asimov writes Asimov reads, then validates Fresh subagent, no conversation history
  • In: one D101 at Full design. Anything else is refused (R2).
  • The plan command reads the D101 and the repo, asks at most 5 questions with defaults, then uses the authoring skills to write and the validation skills to check, task by task and then the whole (R19–R23).
  • Out: one S101 and N S102s in documentation/specs/<slug>/: phase 0 skeleton per stack, then per slice one builder task per stack and one Calvin acceptance-test task (R1, R3–R7).
  • The review command runs the same validation skills on an existing plan and writes nothing (R14). The author self-previews; the reviewer ≠ author approves; the author sets ready (R15).
The authoring loop

Each S102 is validated blind as it is written; the plan is validated once every task exists. A finding at either level sends the affected task back; a third failure, or a finding that points at the D101, stops the run.

Start / decision Writing or validating Delegated to a fresh subagent Stop
  1. 01
    Write one S102 for one builder role from the S101 graph (R8).
  2. 02
    A fresh read-only subagent validates it against the S102 checks, seeing only the S102, the S101, the D101 and the repo (R9). Fails → rewrite → 02 again (R10); a third failure, or a finding that names a D101 gap, stops the run with a report (R11).
  3. 03
    With every task written, validate the plan against the S101 checks: coverage both ways, interface closure, disjoint parallel sets, no cycle, no contradicted constraint, size warnings (R12, R18). A finding sends the affected tasks back to 01 (R13).

§4.4Architecture

Two definitions, two templates, four skills, two commands, one blind subagent and one folder. One D101 in; one S101 and N S102s out. The definitions set the bars, the templates the shape, the skills the method, the commands the conversation.

Human · the one accented message is the blind call Command and skills Fresh subagent, no conversation history The specs folder
  • /s101-review is the same picture without the author's questions and without the writes: both validation skills run, the report is printed, the folder is untouched (R14).
  • A lone S102 from the board calls artifact-s102-authoring and the blind validator directly; there is no S101 to decompose.

§4.5Rules

Each rule with the case where it fires and the adjacent case where it does not.

Rule
Fires
Does not fire
Only Full design is planned
A D101 at Full design → an S101.
A D101 at Business design → refused, no file written.
Slice = phase
AC3, single-stack → phase 3 with one builder S102 and one Calvin S102.
A shared type two slices need is not a slice; it goes to Foundation.
Parallel = disjoint
Two slices with no common file may run together.
A common file is a dependency; the plan says which task owns it, and two slices needing the same skeleton file get the skeleton cut so each owns its own, decided at planning time.
The loop exits
A third failed validation, or a finding that names a D101 gap → the run stops and reports.
A second failure on an S102 defect → rewrite and validate again.
Size warns
Four owned non-test files → a warning; the plan is still written.
A cycle in the graph → rejected; that is shape, not size.
Ask only about the cut
Two criteria could be one slice or two → ask.
Which model tier → decide, record as an assumption.
Update or supersede
Requirements and criteria unchanged in content → update in place, and an S102 that already clears is left untouched.
A criterion changed in content → new S101, old one superseded; a version bump with a wording fix is not a change.
Validate blind
An S102 is validated by a fresh subagent with only the S102, S101, D101 and repo.
The plan validation runs inline; it is mechanical and cross-file, not a blind property.

§4.6Plan lifecycle

One status axis on the S101. The Spec workflow moves it as far as ready; the Build workflow moves the rest.

Start state In progress Terminal
  • The command writes and re-writes draft, and writes the successor when the D101's criteria changed (R16, R17).
  • The author sets ready after the reviewer's approval; no command does (R15).
  • The Build workflow moves ready → in progress → done; out of scope here.

§4.7Decisions

A decision recorded without its rejected alternative is one that gets re-litigated.

Decided
Alternative considered
Why rejected
One command with the loop built in
One command per task
The graph has to be seen whole; per-task commands re-derive it.
Blind validation by a fresh subagent
Inline, by the writing model
The author fills the gaps from memory; buildable blind is a fresh-context property.
Skeleton as phase 0
Inside each S102, or written during planning
Inside each task the names are agreed only on paper; during planning the Spec stage would write code.
Builder tests inline, Calvin per slice
Builder only, or Calvin only
L3 has no human Test bar: tests are agent-written and the acceptance test must be reviewable before code exists.
Shape by script
Everything by the model
A model is soft even when told to be hard; the L3 bar is "schema-validated".
At most 5 front-loaded questions
Step-by-step interview, or no questions
The D101 did the intent work; a per-step interview repeats Kiro's heavy mode, and no questions guesses the cut.
Stop once, at the end
A gate per artifact
Two stops for the same reviewer on the same plan.
Soft size warnings
A hard size gate
Evidence is strong on direction and weak on the number, and the number moves every few months.
Update in place; supersede on changed intent
Always a full replacement
Review findings are the same work refined; a replacement discards the reviewer's reading.
Acceptance tests at API level against the skeleton
End-to-end per slice
A bodiless skeleton cannot run an app; end-to-end only where the repo's conventions name a runner.
The loop exits after three failures or a D101 gap
Loop until it clears
An unclear D101 is not fixed by rewriting the S102; the third attempt is the signal.
Validation ≠ verification
One word for both
Two checks, two moments, two inputs; one word made the design talk past itself.

§6Still to write

⚠ This document is not gap-free. §2–§5 settle what the Spec workflow produces, who owns each step and the rules it follows. No S101 can be written from it until the items below exist.
  • How the blind subagent is dispatched and what it is given, so a "pass" means the same in Claude Code and in a harness without subagents.
  • What the shape script checks and how it reports, so two runs on the same plan agree.
  • How the S101 frontmatter encodes the graph, so a validator reads dependencies, phases and owned files without reading the body.
  • How the command detects a requirement or criterion changed in content across D101 versions (stable ids, a stored fingerprint), so a re-run never silently overwrites a plan the reviewer approved.
  • How an S102 that already clears is recognised on a re-run (a fingerprint per task), so a resumed run rewrites only what changed.
  • Which runtime the shape script assumes in a product repo, so two repos get the same shape report.
  • How the command keeps its own context small across twenty or more validation rounds, so a twelve-task plan still stops once.
  • Where a run's findings and assumptions land, so the reviewer sees what the command decided alone.
  • How the method splits between the authoring and validation skills, so a hand-edited S102 can be validated without the command.
  • What the command does when its five questions are spent and a decision remains.

Q5Resolved 2026-09-29
Who writes the tests of an S102?
Decision: the builder writes unit tests inline; Calvin writes the slice's acceptance test as its own S102, which is the phase checkpoint (§4.7). Reopens if a slice's acceptance test cannot be written before its code.
Q6Resolved 2026-09-29
Where does the code skeleton belong?
Decision: phase 0 Foundation, one S102 per stack (§4.7). Reopens if the skeleton tasks turn out to need judgement rather than transcription.
Q7Resolved 2026-09-29
Interview the developer, or plan from the D101?
Decision: plan from the D101 and the repo, ask at most 5 front-loaded questions with defaults, stop once (§4.7). Reopens if runs regularly exhaust the five.
