D101 · Feature design · Asimov plugin

Build stage

One run of asimov-build builds a ready plan: each task goes to its Asimov agent with its task spec, Baley and a fresh verifier check the result, the ledger records it, and the person says go after every phase. What was approved at the cut is what gets built.

Scope: the Build workflow from a ready S101 to a branch ready for a PR: asimov-build, the ledger, verification, Baley against the task spec. §2–§5 are the business agreement, §6 the technical design; §7 is N/A.

§2Why

The Spec stage now delivers a ready plan, and nothing builds it.

  • Hand-fed. Every task spec is pasted to an agent by hand, in an order the person keeps in their head.
  • Unrecorded. What was built, what the tests said and what a review found live in a chat that is gone tomorrow.
  • Unchecked. The builder reports on its own work; nobody runs the done-when the spec promised.
Audience. The developer who directs a run; the PR reviewer who reads the ledger; the colleague who resumes a run someone else started.

§3Requirements

Functional — 11
R1
asimov-build builds only an S101 at ready whose approval holds.
R2
Each task goes to the Asimov agent its role names, fresh, with the task spec as its only brief, in both harnesses.
R3
Tasks run in graph order; tasks with no open after and disjoint files run at the same time.
R4
Once a phase is built, Baley reviews its diff against its task specs and the plan's review focus.
R5
Then a fresh verifier runs every task's done-when and the checkpoint; never the builder.
R6
A task whose review or done-when fails is rebuilt with the findings, at most twice; then the run stops.
R7
After each phase the checkpoint is shown and the run waits for a go; the go commits the phase as one commit, nothing is committed before.
R8
Run state lives in the ledger; the run never writes an S101 or S102, except the S101 status ready → in progress → done.
R9
A run resumes from the ledger without repeating a done task, also for another person.
R10
Every stop and every ruling is in the ledger; the person rules on all of them. A stop in one task lets running tasks finish, then ends the run.
R11
The run ends with a branch ready for a PR and opens none.
Non-functional — 2
NF1
One chat line per agent call; findings in words; the reports go to the ledger.
NF2
The model per task follows the tier (model-choice.md §1.1) in Claude Code; Codex runs the session's model.
Out of scope — 4
OOS1
Opening the PR — Approve is the human gate outside the toolkit.
OOS2
Rulings by an orchestrator below the person — the person rules on everything in the first version.
OOS3
Agent teams — the graph gives the parallelism; a fresh agent per task is enough.
OOS4
Writing status back to Jira — observe first.

§4.1The run

Who does what: tasks are built in batches, the phase is verified and reviewed once, the person says go.

Entry / gate Agent work Ledger / commit Run ends
Box
What happens
pick ready tasks
Every task whose after are done and whose files touch no running task's; they build together (R3).
build from S102
The agent the role names, fresh, with the task spec and nothing else; the model by tier (R2, NF2).
write ledger
The task's state, the attempt and the agent (R8).

Tasks left: pick again. All built: the phase goes to Baley.

Baley reads the phase's diff against its task specs; then Powell runs every task's done-when and the checkpoint (R4, R5).
passed?
All pass: the person reads the checkpoint. A failed task is ready again with its findings, twice at most; the third ends the run (R6).
go
The person says go; a stop here leaves the phase in the working tree (R7).
commit
One commit: the phase's files and the ledger. Then the next phase, or done and a branch ready for a PR (R7, R11).
stop · you rule
The run ends; the reason and the choices are in the chat and the ledger (R10).

§4.2Vocabulary

Term
What it means
run
One invocation of asimov-build on one plan, from its first ready task to a stop, a go that ends a phase, or done.
phase
A node of the plan's tree: its tasks, its checkpoint, one commit.
attempt
One build of one task by one fresh agent; the second and third carry the previous findings.
checkpoint
The phase's check from the plan, run once its tasks are done; met or not.
go
The person's word after a met checkpoint; the only thing that commits.
stop
The run ending before a go, with the reason and the choices in the chat and the ledger.
ruling
What the person chose at a stop: resume with a note, discard the phase, or stop.
ledger
documentation/specs/<slug>/S101-<slug>.ledger.md: per task its state, attempts, agent and reports; per phase its checkpoint, go and commit; every ruling. Committed with each phase.
plan status
The S101's own axis, ready → in progress → done: the one line the run writes into a spec.

§4.4Business rules

#
Rule
BR1
A task starts when every task it comes after is done. A task whose predecessor stopped waits for the ruling; it is never skipped.
BR2
Tasks run together only when their files are disjoint. Two tasks that both touch the solution file run one after the other, even with no after between them.
BR3
A task that fails the phase's review or verification is rebuilt with its findings, twice at most. A finding that names a design gap stops the run at once; it is fixed in the Spec stage, not by a retry.
BR4
A commit happens at a go and never before. A stop in the middle of a phase leaves the half-built phase in the working tree; the ruling is resume, discard the phase, or stop.

§5UI Design

The feature's only surface is the chat of one run, styled after the Spec-stage transcript mockup: one column, monospace, one line per agent call, a gate after every phase.

The run as a transcript
  • Full run. The plan named with its approval, then per phase: one line per build, one review and one verify, the checkpoint, the gate; a go prints the commit (R7, NF1).
  • Stopped by a task. The third failure ends the run with the findings in the ledger and three choices: resume with a note, discard the phase, stop (R6, R10).
  • Resumed. The ledger says where the last run ended; done tasks are listed, not rebuilt (R9).
  • Refused. A draft plan, or an approval that no longer matches: one line and nothing written (R1).

Technical design
The pieces, one phase as messages, the files, the ledger and the prompts, the reports, the settings, the failures, the gotchas.

§6.1Platform

asimov-build is an asimov-skill: one SKILL.md for Claude Code and Codex plus agents/openai.yaml, run in the product repo on the branch that is checked out. It spawns the plugin's agents through the harness, one fresh agent per call, in the L3 order Code → Review vs. spec → Test vs. spec, and keeps the method in three skills: the ledger's, a vs. spec target in Baley's, and Powell's.

⚠ Escalation gate. Commits only at a go, never on the default branch, never a push, never a PR.

§6.2One phase, as messages

Who talks to whom, in order, for one phase. Every agent is fresh; only asimov-build keeps the conversation.

The person Agents
Message
Carries
/asimov-build slug
The S101 path is derived; the run refuses a plan not ready, a broken approval, a dirty tree or the default branch, and resumes from the ledger when one exists.
S102 path · model
The builder's prompt: build this one task spec, read the S101 contracts and constraints, change by hand only the owned files and regenerate (never open) what the task spec's owns.regenerates lists, stop as the S102 definition §5 says. Claude Code: the Agent tool with the shell's name and the tier's model. Codex: the copied agents, mechanism per Q2.
summary · flags
The builder's own summary, as its role skill defines; a flag is a stop (R10).
ledger: built
State, attempt and agent written before the next task starts, so a dead run resumes here.
owned files · S102 paths · review focus
Baley's prompt: the diff of the phase's owned files, reviewed on its two axes plus a third, against the spec; the phase's regenerated files (lock files, generated clients) are listed apart and checked only for being what the hand edits imply.
S102 paths · checkpoint
Powell's prompt: run every done-when as written and the checkpoint; change nothing; report per task with the command and its last line. The working tree is hashed before and after.
checkpoint · one line each
The chat: one line per build, one per review, one per verify, the checkpoint, then the gate (NF1). The raw reports go to the ledger.
go
Commit of the owned files, the files the phase regenerated and the ledger; status in progress on the first go, done after the last phase.

§6.4Shapes

The ledger · documentation/specs/<slug>/S101-<slug>.ledger.md
Field
Notes
frontmatter
ledger: S101 · slug · s101 path · fingerprint of the approval it was started from · started by and date.
phases[]
One per phase of the plan: id · status (pending · building · built · passed · committed · discarded) · commit hash · go by and date.
tasks[]
Under its phase: id · status as §4.3 · attempts · agent · model.
body
One ## per phase; under it ### T00n · attempt k with the builder's summary and flags, ### review with Baley's report, ### verify with Powell's, ### ruling with the person's choice, note and date.
rules
Frontmatter is machine state, the body is the record; both are appended, never rewritten. A resume trusts the frontmatter and reads the body only to show the person where it stopped.
The chat line

§6.8Known constraints & gotchas

Powell's read-only is prompt discipline plus a hash. Its tools include a shell, because done-whens are commands; the ban on writing is in its skill, and the tree hash before and after is what makes a breach a finding rather than a trust.
Codex runs one model. The tier is advisory there; the ledger still records the model used.
Paths. ${CLAUDE_PLUGIN_ROOT} in Claude Code; the derived plugin root of D101-codex-support.html §6.2 in Codex, passed to every agent prompt.
