D101 · Feature design · asimov-plugin

Codex support

One plugin folder that Claude Code and Codex both install. Each tool reads its own manifest, both load the plugin's skills, and the setup has one entry point per tool: the /asimov-init command in Claude Code and the codex-asimov-init skill in Codex, which works out where the plugin is by itself.

Scope: installing the Asimov plugin in Codex beside Claude Code from one plugin folder — the Codex marketplace listing and plugin manifest, the Codex setup entry point and how it finds the plugin's files, the convention that keeps a Codex-only skill out of Claude Code, and what stays Claude Code only. What the setup writes into a repository, target by target, is designed in D101-asimov-init.html and not repeated here.

§2Why

A team on Codex could not install Asimov: the repository listed the plugin for Claude Code alone.

  • Claude Code only. The plugin had a manifest for Claude Code and none for Codex, so a Codex user had nothing to add or install.
  • Setup out of reach. The setup command sits in commands/, a folder Codex does not load, so a Codex user could not make a repository Asimov-ready.
  • Context one tool never sees. asimov.md reaches Claude Code through an import in CLAUDE.md; Codex reads AGENTS.md and expands no imports.
  • Plugin files out of reach from a skill. The skills name the plugin's files through a variable only Claude Code fills in, so a skill running in Codex cannot find its templates.
Audience. Asimov maintainers, and developers in product repositories who work in Claude Code, in Codex, or in both.

Business design
Principles, vocabulary, what a developer sees in each tool, the rules, the decisions.

§4.1Principles

1
One folder, one manifest per tool. Each tool reads its own small manifest and ignores the other's.
2
Skills are the shared layer. Both tools load the plugin's skills; commands and agent shells are per tool.
3
One setup entry point per tool. Claude Code keeps its command; Codex gets a skill of its own, marked so that Claude Code ignores it.
4
A skill that runs in Codex finds the plugin itself. It derives the plugin folder from its own location and checks it, because Codex fills in no plugin-root variable.
5
Claude Code keeps working. Nothing a Claude Code user sees changes.

§4.4Rules

What holds whichever tool is in use.

Rule 1 — Each tool reads only its own manifest

The plugin folder carries one manifest per tool, and the repository one marketplace listing per tool; a tool ignores the other's.

  • Codex reads the Codex listing and the Codex manifest; Claude Code reads its own two and sees nothing new.
  • Counter-example: the skills/ folder is read by both tools; it is not per tool.
Rule 2 — A Codex-only skill is marked, not hidden

A skill meant for Codex alone stays in the shared skills/ folder and carries the two frontmatter switches (disable-model-invocation, user-invocable) that make Claude Code ignore it.

  • codex-asimov-init carries both switches, so Claude Code neither lists it, runs it when typed, nor lets the model start it.
  • Counter-example: the role skills carry neither switch and load in both tools.
Rule 3 — Only the developer starts the Codex setup

The Codex setup skill runs when the developer invokes it; Codex never starts it on its own.

  • A developer types $asimov-plugin:codex-asimov-init, and the run opens with one sentence on what it will do, then a write plan.
  • Counter-example: asked to "set up the repo", Codex does not start the skill; it names the invocation for the developer to type.
Rule 4 — A skill in Codex finds the plugin itself

A skill that reads plugin files in Codex derives the plugin root from its own file path and verifies it by reading a known file before it uses it.

  • The setup skill takes its own path, cuts it two levels above the skill folder, reads the first template there, and only then loads the rest.
  • Counter-example: the three skills that still name plugin files through the Claude Code variable do not find them in Codex (Q2).
  • Counter-example: the skill never passes a .. path; Codex resolves one from the working directory, not the skill folder.

Technical design
Where each tool reads, how the Codex setup finds the plugin, the files and their shapes, failure handling, the constraints that stay.

§6.1Platform

The plugin folder plugins/asimov-plugin/ holds a manifest per tool: .claude-plugin/plugin.json for Claude Code and .codex-plugin/plugin.json for Codex. The repository root holds a marketplace listing per tool: .claude-plugin/marketplace.json and .agents/plugins/marketplace.json, both named asimov-marketplace and both pointing at the same folder. Claude Code loads commands/, agents/*.md and skills/. Codex loads skills/ and caches the installed plugin under ~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/. The Claude Code setup is the command commands/asimov-init.md; the Codex setup is the skill skills/codex-asimov-init/.

§6.2How the Codex setup finds the plugin

Step 1 of the skill, before any template is loaded: derive the root, verify it by one read, search the cache if the read fails, stop if nothing matches.

Start and the two decisions Deriving the root Reads: the template, the cache Terminators The rest of the run, designed in D101-asimov-init
1
Derive root. Take the skill's file path from Codex's skill list and cut it before skills/codex-asimov-init; every plugin path is built from the result, absolute.
2
Read file 1. Read artifacts/root/asimov-md/asimov-md-template.md under that root; a successful read verifies it.
3
Search cache. If the read fails, Glob <home>/.codex/plugins/cache/**/artifacts/root/asimov-md/asimov-md-template.md; several matches — take the longest shared prefix with the skill path; none — stop, report the derived path and the search, write nothing.
4
Load templates. Read the four templates and three definitions and list agents/*.toml; from here the run follows D101-asimov-init.html.

§6.8Known constraints & gotchas

Plugin-root variable in skills. artifact-d101-authoring, artifact-d101-gap-review and pm-advisor address their files through ${CLAUDE_PLUGIN_ROOT}. Claude Code substitutes it in skill, command and agent content (plugins reference); Codex leaves it literal (codex#19582) and sets PLUGIN_ROOT/PLUGIN_DATA, with CLAUDE_PLUGIN_* aliases, only as environment variables for hook commands (build plugins). In Codex these three skills cannot find their files (Q2).
Why the root is derived, verified and searched. Codex resolves a relative path in a plugin file from the working directory (codex#22842), shows the model each skill's file path (build skills), and caches plugins at ~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/, older versions included (build plugins).
Commands are Claude Code only. Codex loads a plugin's skills/ folder (build plugins), not commands/; the five slash commands run in Claude Code alone (Q1).
Marking a Codex-only skill. disable-model-invocation and user-invocable: false are Claude Code's switches, and skillOverrides does not apply to plugin skills (skills); allow_implicit_invocation: false is Codex's, and $-invocation still works (build skills).
Manifest location. The Codex documentation names a root plugin.json as the portable manifest and keeps .codex-plugin/plugin.json as a compatibility fallback (build plugins); the plugin uses the fallback location today.

§7.5Cross-cutting

  • Drift sweep. When a file in §6.3 moves, grep the repository for codex-asimov-init, .codex-plugin and .agents/plugins and fix what remains. The derived-root step of §6.2 also lives in the five Spec-stage skills (asimov-spec and the four artifact-s10x-* skills, since 2026-10-02); a change to the method changes all six.
  • Versions move together. When a release bumps the plugin version, both manifests take the new number (Q3).
  • Nothing is verified in Codex. No run of the skill or install in Codex has been recorded; the acceptance criteria in §8 are what such a run would check.
