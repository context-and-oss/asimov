D101 · Feature design · asimov-plugin

Codex support

One plugin that Claude Code and Codex both install straight from the repository, with no generator and no build step. The method stays in skills, each subagent gets a thin shell per tool, a model is named only in a Claude Code agent shell, and the setup entry point is one skill both tools run.

Owner
Christian Kaysen
Business approver
Allan Borup
Tools
Claude Code · Codex
Plugin version
0.1.0 → 0.2.0
Last updated
2026-09-30
Build step
None
Scope: installing the Asimov plugin in Codex beside Claude Code from one plugin folder: the tool manifests, the agent shells, where a model may be named, the setup entry point as a skill both tools run, and the repository guidance that describes them.

§2Why

Teams on Codex cannot use Asimov today, and the parts already prepared for Codex have nothing that installs them.

  • Claude Code only. The plugin carries a manifest for Claude Code alone, so a Codex user has nothing to install.
  • Shells without a home. A Codex shell exists for every subagent, marked as a prototype, and no install path reaches it.
  • Two places to keep in step. Every model name is written in the component and again in a separate index, which a check compares by hand-written rule.
  • Setup out of reach. The setup command lives where only Claude Code looks, so a Codex user cannot make a repository Asimov-ready.
  • Context one tool never sees. asimov.md reaches Claude Code through an import in CLAUDE.md; Codex reads neither, so a Codex session starts without the Asimov context.
Audience. Asimov maintainers, and developers in product repositories who work in Claude Code, in Codex, or in both.

4
Business design
Principles, vocabulary, what a developer sees in each tool, the rules, the decisions.

§4.1Principles

1
One folder, one manifest per tool. Each tool reads its own small manifest and ignores the other's.
2
The method lives once. Skills hold every procedure; a shell only says who the subagent is and which skill it follows.
3
A model belongs to an agent shell. The shared layer names no model, so it reads the same in both tools.
4
One file per entry point. An entry point that must run in both tools is a skill, the one format both tools load from a plugin.
5
Claude Code keeps working. A Claude Code user notices nothing but the model a command runs on.

§4.4Rules

What holds whichever tool is in use.

Rule 1 — A model is named only in a Claude Code agent shell

Every other file the plugin ships runs on the model of the session that uses it.

  • The .NET builder's Claude Code shell names Sonnet 4.6, and the builder runs on it.
  • Counter-example: the feature-design command, pinned to a larger model until now, names none and runs on the session's model.
  • Counter-example: the .NET builder's Codex shell names none and runs on the session's model.
Rule 2 — A shell holds identity, never method

A shell names the subagent, describes when to use it, sets its permissions and points at its role skill.

  • The reviewer's shells say who Baley is, that it is read-only, and which skill to follow.
  • Counter-example: the steps of a review — resolve the diff, walk it, grade findings — are in the role skill, not repeated in either shell.
Rule 3 — The reviewer is read-only in both tools

Each tool is told, in its own terms, that the reviewer may read but not write.

  • Asked to fix what it found, the reviewer reports the finding and changes nothing, in Claude Code and in Codex.
  • Counter-example: the builders and the tester keep write access in both tools.
Rule 4 — Both tools see one version

The two tool manifests carry the same version, and it moves on every plugin release.

  • This change moves both manifests from 0.1.0 to 0.2.0 together.
  • Counter-example: the marketplace listings carry no version of their own.
Rule 5 — The setup entry point is a skill only the developer starts

The developer invokes it in either tool; neither tool's model may start it on its own.

  • A developer types /asimov-init in Claude Code or $asimov-plugin:asimov-init in Codex, and the run opens with the write plan.
  • Counter-example: asked to "set up the repo", the model does not start it; it names the command for the developer to type.
Rule 6 — The context lands where each tool reads

The same rendered text goes to the place each tool loads at session start: the @asimov.md import in CLAUDE.md for Claude Code, a managed region in AGENTS.md for Codex.

  • After a run, a Codex session knows the Asimov commands and subagents without anyone pasting asimov.md.
  • Counter-example: text outside the markers in AGENTS.md is the team's and is never touched; broken markers stop the write to that file.
Rule 7 — The setup entry point delivers the Codex shells

The plugin's agents/*.toml are copied byte for byte into the repository's .codex/agents/, the only place Codex loads custom agents from; they are Asimov-owned and regenerated on every run.

  • After a run in a trusted repository, a Codex session can spawn giskard-the-dotnet-developer by name, and the shell it runs is identical to the plugin's.
  • Counter-example: a run that cannot obtain Codex's approval for the .codex/ write reports the shells as skipped and names the two ways to finish; it never writes them another way.

Technical design
Where each tool reads, how an install runs, the files and their shapes, failure handling and the constraints that stay.

§6.1Platform

The plugin folder plugins/asimov-plugin/ holds a manifest per tool: .claude-plugin/plugin.json for Claude Code and .codex-plugin/plugin.json for Codex. The repository root holds a marketplace listing per tool: .claude-plugin/marketplace.json and .agents/plugins/marketplace.json, both pointing at the same folder. Claude Code loads commands/, agents/*.md and skills/. Codex loads skills/. The setup entry point is a skill (skills/asimov-init/), so both tools load it. Codex loads custom agents only from ~/.codex/agents/ or a trusted repository's .codex/agents/; the setup skill copies the plugin's agents/*.toml there. Each tool ignores the other's manifest and files.

⚠ Required check turns red. The pull-request check on main requires a model: in every command and a row in documentation/model-choice.md; both are removed, so the check fails until the workflow is changed after this round (Q3).

§6.2An install

The developer adds the same repository in either tool; each tool follows its own manifests and loads its own part of the folder.

§6.8Known constraints & gotchas

Plugin-root variable in skills. artifact-d101-authoring, artifact-d101-gap-review and pm-advisor address their files through ${CLAUDE_PLUGIN_ROOT}, which Claude Code substitutes and Codex does not; left as is in this round, recorded by the test. The setup skill uses relative paths instead (§6.4).
Where Codex looks for agents. Codex's documented agent locations are the user's ~/.codex/agents/ and a trusted repository's .codex/agents/, not a plugin folder; the setup skill copies the shells there (R15).
No preload in Codex. A Codex shell has no field that loads a skill; loading the role skill first rests on the instruction in developer_instructions.
Commands run on the session's model. Removing the pins moves /d101-feature-design, /asimov-init and /persona-new off Opus and the others off Sonnet, onto whatever the session runs.
