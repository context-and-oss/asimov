D101 · Feature design · asimov-plugin

Codex support

Asimov's method is tool-independent, but the plugin runs only in Claude Code, so a team member on Codex cannot use it. This design adds Codex as a second tool with the smallest change that works: one plugin folder both tools install, the method held once in skills, a thin agent shell per tool, and no model named anywhere.

§2Why this exists

Asimov's method is tool-independent, but the plugin is Claude Code-only, so a team member on Codex cannot use it at all.

  • The design flow stops at the tool boundary. A Codex user can read a D101 but cannot author or review one against the bar.
  • No subagents in Codex. Giskard, Daneel, Calvin and Baley, and the delegation flow in the Asimov context, exist only for Claude Code.
  • Nothing in the plugin can be picked up as it stands. It pins Claude model names and Claude-only file paths.
  • The first attempt was too heavy. A generator and a tool-neutral source tree were judged more than the project wants to maintain; the change must be the minimal one.
Audience. Toolkit maintainers, who build it; developers on either tool, who install and use it; team leads, who need to know what parity between the two tools means.

4
Business design
The principles, the vocabulary, what a developer sees in each tool, the rules that keep the two tools in step, and the decisions with the alternatives they ruled out.

§4.1Principles

1
One toolkit, two tools. A developer picks the tool; the team shares one method. A capability counts as shipped only when it works in both (NF4).
2
Minimal change. What exists for Claude Code stays as it is; Codex is added beside it, never by rebuilding. No build step, no generated tree.
3
The method lives once, in skills. A tool gets only the thin adapter it needs — a manifest, an agent shell — and the adapter carries no method text.
4
Follow established practice. Do what the multi-tool add-ons already do (Superpowers: one plugin folder, an explicit manifest per tool); never build on one tool tolerating another tool's files.
5
The toolkit names no model. Agents and skills run on the model the session runs on; a model choice is the user's or the session's, never the plugin's.
6
User decisions stay user decisions. Setting up a repo for Asimov is never the model's call, in either tool.
7
Nothing after install or update is assumed. What a user must do — install, trust, re-run, restart — is written where they look, in the README, for each tool.

§4.3What a developer sees, tool by tool

Every point where a developer touches Asimov, with the one rule that governs it and what it looks like in each tool.

Installing

"How do I get Asimov into my tool?" — one repository, each tool's own marketplace command.

  • Claude Code: /plugin marketplace add context-and-oss/asimov, then /plugin install asimov-plugin.
  • Codex: codex plugin marketplace add context-and-oss/asimov, then codex plugin add asimov-plugin@asimov-marketplace.
  • Both: start a new session afterwards.
  • The plugin is not available in Codex's IDE extension (OOS4).
Invoking an entry point

"How do I run a command?" — same name in both tools, invoked the way the tool invokes skills.

  • Claude Code: /d101-review path/to/D101.html (bare name, or /asimov-plugin:d101-review).
  • Codex: $asimov-plugin:d101-review followed by the path in the same prompt, or the /skills picker.
  • A skill that needs a target takes it from the prompt and asks when none is given.
User-only entry points

"Can the model set up my repo on its own?" — no: asimov-init is never the model's choice.

  • Claude Code: absent from what the model can call; /asimov-init still works for the user.
  • Codex: absent from the model's skill list; the explicit $asimov-plugin:asimov-init still works.
Delegating to a subagent

"How does Giskard get my task?" — the orchestrator delegates by name, following the delegation flow in the Asimov context; the agent runs on the session's model.

  • Claude Code: the four agents come with the plugin; nothing to set up beyond /asimov-init.
  • Codex: the four agents appear after /asimov-init has delivered them and the developer has marked the repo trusted; they load at the start of a session, so delivery is followed by a new session.
  • Same method in both: the agent opens its role skill and follows it.
Personas

"Who can read my design?" — the three standard readers ship with the plugin in both tools; a custom reader written with /persona-new appears in both tools of the same repo.

  • Standard: persona-poseidon, persona-athena, persona-hermes, invoked like any skill.
  • Custom: one skill, written to both tools' skills folders in the product repo.
Setting up a repo

"What does init do for the tool I am not using?" — /asimov-init, run from either tool, wires both.

  • Writes the Asimov context for Claude Code and for Codex, scaffolds the convention read-lists and the documentation site, and delivers the Codex shells.
  • Its report lists what was written and, for Codex, that the repo must be trusted and a new session started.
  • Run in Codex, the write into .codex/agents/ asks for the developer's approval — Codex's sandbox protects that folder. Approve it, or run asimov-init once from Claude Code.
After a plugin update

"I updated the plugin — what now?" — each tool's own refresh, then a new session; /asimov-init again only if the agent shells changed (R11).

  • Claude Code: /plugin marketplace update asimov-marketplace, then /reload-plugins or a new session.
  • Codex: codex plugin marketplace upgrade asimov-marketplace, then a new session.

§4.4Rules

Eight rules keep the two tools in step; each carries the case where it fires and the adjacent case where it does not.

Parity rule

A capability ships only when it works in both tools.

  • Fires: a new persona skill is added to the plugin → it is checked in Codex too before it is merged.
  • Does not fire: the Codex IDE extension cannot load plugins at all → recorded as a known limitation, not a blocker.
User-only rule

An entry point that is a user's decision is closed to the model in both tools.

  • Fires: asimov-init writes into the repo on the user's behalf → the model can never start it.
  • Does not fire: d101-review → the model may run it when the user asks for a review in plain words; the user just as often types it.
Role-skill rule

A role skill is run only by its agent shell; the orchestrator delegates to the agent and never runs the role skill itself. Entry-point skills are the user's to invoke in the session.

  • Fires: a .cs task arrives in the session → delegated to Giskard, not answered by opening role-dotnet-builder.
  • Does not fire: the user runs /asimov-init → an entry-point skill, invoked in the session as intended.
  • Neither tool can enforce this technically — role skills must stay visible so the shells can reach them — so the rule lives in the Asimov context, next to the delegation flow.
Thin-shell rule

An agent shell carries name, description and the pointer to its role skill — never method text.

  • Fires: a wording fix to how Giskard cites conventions → changed in the role skill only; both shells stay untouched.
  • Does not fire: the description sentence that tells the orchestrator when to pick Giskard → it lives in the shell, because it is routing, not method.
No-model rule

Nothing in the plugin names a model; agents and skills run on the session's model.

  • Fires: an agent shell would pin a model → removed; the shell inherits.
  • Does not fire: a developer starts their session on a smaller model → their choice, and the agents follow it.
Two-file skill rule

Every skill is a minimal SKILL.md that points at method.md.

  • Fires: artifact-d101-authoring at 13.7 kB → the method moves to method.md, the entry shrinks to frontmatter plus the pointer.
  • Does not fire: persona-hermes at 3 kB → still split; the shape is the same for every skill, size or not.
Source-and-mirror rule

Every file that exists once per tool has one source; the other copy is a mirror.

  • Fires: a custom persona is edited in .claude/skills/ → /persona-new re-run (or the later update flow) refreshes .agents/skills/.
  • Does not fire: someone edits the .agents/skills/ copy directly → that is drift, not a new source; the Claude copy wins on the next sync.
Version rule

The plugin's version changes in the same change that alters anything under the plugin folder.

  • Fires: a role skill's method.md is corrected → version bumps, so both tools offer the update.
  • Does not fire: a D101 under documentation/ is edited → nothing in the plugin moved; no bump.

Technical design
Where the plugin lives, how a task flows from a developer to an agent in either tool, the file map, the shapes of every per-tool file, the external contracts relied on, the settings, the failures and the gotchas.

§6.1Platform

One folder, plugins/asimov-plugin, committed on main, is the whole installable. Claude Code reads its .claude-plugin/plugin.json, skills/, agents/*.md; Codex reads its .codex-plugin/plugin.json and skills/ and ignores the rest. Each tool finds the folder through its own marketplace manifest at the repo root — .claude-plugin/marketplace.json and .agents/plugins/marketplace.json — both pointing at the same path. No build step: what is in the repository is what installs, cached per version by each tool. The method lives in skills/<name>/method.md; every other per-tool file is a pointer to it. Codex cannot carry agents in a plugin, so the Codex shells (agents/*.toml) travel to a product repo's .codex/agents/ with /asimov-init, and Codex loads them there only when the developer has marked the repo trusted.

⚠ Escalation gate. Anything that would need a file transformed per tool — a generated manifest, a converted shell, a substituted path — is out; the design holds only while every file in the folder is read as-is by the tool it is for. If a tool changes so that stops being true, that is a new D101, not a build step slipped in.

§6.2Data flow

One delegated task, from the developer's prompt to the agent's report. The two tools differ only in how the agent's shell gets its method — the alt fragment — everything before and after is the same exchange.

Entry Processing Repo files
  1. The developer states the task in the prompt; the model's session is the orchestrator.
  2. The orchestrator reads the Asimov context — asimov.md through the CLAUDE.md import in Claude Code, the AGENTS.md managed region in Codex — and follows its delegation flow; in Codex that text is also what authorises spawning at all.
  3. It delegates by name: Claude Code's agent tool with the plugin agent; Codex's spawn_agent with agent_type set to the shell's name. No model is passed; the agent inherits the session's.
  4. The shell gets its method: Claude Code preloads the role skill's SKILL.md (the skills: field); in Codex the shell's instructions invoke $asimov-plugin:<role-skill>. Either way the entry says "read method.md", and the agent does.
  5. The agent reads the repo's convention read-list and files, writes code or tests (Baley writes nothing), and reports with citations and flags.
  6. The orchestrator continues the delegation flow (test-impact check, the opt-in questions) and answers the developer.

§6.5Contracts relied on

No API of Asimov's own. The design rests on five external contracts, each documented by its owner and verified live on 2026-09-29 (research note): Claude Code's plugin, skill and subagent formats (disable-model-invocation, skills: preload, "Base directory for this skill"); Codex's plugin and marketplace manifests (compatibility path for Claude manifests noted, not used); Codex skills ($plugin:skill, the skill path in the listing, policy.allow_implicit_invocation, the 8 kB entry cap for portable-format plugins); Codex custom agents (TOML in ~/.codex/agents/ or a trusted repo's .codex/agents/, agent_type spawn, inheritance when model is absent); and the shared SKILL.md convention both tools read.

§6.8Known constraints & gotchas

User-only blocks preload. Claude Code's disable-model-invocation: true also stops a subagent from preloading that skill, and Codex's allow_implicit_invocation: false hides it from sub-agents. Only entry points a user runs may carry the flag; role skills never.
Codex protects .codex/ inside the repo. Its workspace-write sandbox refuses a write into .codex/agents/ until the developer approves it, so delivering the shells from Codex is an approved write, never a silent one; Claude Code writes the same files without asking.
Codex reads project agents only in a trusted repo, and only at session start. Delivery by /asimov-init is followed by a new session; an untrusted repo shows no agents at all.
Codex skills take no arguments. Whatever follows $asimov-plugin:<skill> in the prompt is the input; the entry-point methods read their target from the prompt and ask when none is given.
Codex namespaces plugin skills. The model and the user see asimov-plugin:d101-review; the bare name is Claude Code's convenience.
The 8 kB cap is real but conditional. Codex truncates a SKILL.md at 8,000 bytes only for skills of plugins in its portable Agent-Plugins manifest format (a root plugin.json with $schema); a legacy .codex-plugin manifest — ours, and Superpowers' in OpenAI's own catalogue, whose skills run to 15 kB — injects the full file. The two-file shape is kept for uniformity and to be safe if the manifest format moves; files a skill reads with tools are never truncated.
Codex migrates commands/ at install, dropping anything over 4 kB silently. Removing commands/ is what makes the six entry points reach Codex whole.
Version is the update signal in both tools. Claude Code: "push new commits without changing it, users don't receive them"; Codex caches per version. A local-clone marketplace in Claude Code reads in place and needs no bump — the development path.
Development installs. Claude Code: claude --plugin-dir plugins/asimov-plugin loads the folder for one session and overrides an installed plugin of the same name. Codex: add the clone as a local marketplace (codex plugin marketplace add <clone>); remove and add the plugin again after editing.
Codex plugins are not available in the IDE extension; the CLI and the desktop app load them.

§7.5Cross-cutting — shared by every unit

  • No model, effort or model_reasoning_effort anywhere in the plugin (no-model rule).
  • No ${CLAUDE_PLUGIN_ROOT} under skills/; every plugin reference is relative to the skill folder (R10).
  • Every writing skill carries the UTF-8 rule as its first hard rule (R9).
  • Every SKILL.md under 8 kB with the pointer body; every skill has method.md (NF3).
  • Both plugin manifests carry the same name, version and description; the version is bumped once for the whole change.
  • Commits stay logical: manifests · skills · shells · init and personas · docs and CI, so a reviewer can read each against its §6.4 shape.
