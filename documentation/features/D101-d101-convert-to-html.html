Feature
/d101-convert-to-html
Scope: Design stage of the L3 pipeline (D100 §3, stage 1) — migrating legacy markdown D101s to the HTML format.

The slash command the toolkit ships for converting a legacy markdown D101 into the styled HTML format next to the source. Sits in the Design stage alongside /d101-feature-design and /d101-review, but covers a different need: new D101s are authored directly as HTML by /d101-feature-design; this command exists for D101s written before the toolkit moved to HTML-first authoring, or imported as markdown from elsewhere.

System-level architecture (marketplace, plugin shape, distribution, model declaration mechanism) is in ../D100-Asimov-architecture.md; this doc covers /d101-convert-to-html itself. Once converted, the HTML is the source of record and the markdown source is retired.

§2Purpose & audience

Purpose. Give every Context& developer a single slash command that converts an existing markdown D101 into the toolkit's styled, self-contained HTML format next to the source. This is migration support: new D101s are authored directly as HTML by /d101-feature-design, so there is no markdown intermediate to convert. The command targets D101s written before the HTML-first switch, or markdown D101s imported from elsewhere.

The command is conversion-only and read-only on the markdown: it never edits the source markdown, never invents content, and reproduces the markdown's sections 1:1 in the HTML output.

Primary audience. Developers in any product repo who hold a legacy markdown D101 and want it in the current HTML format — for review, sign-off, or simply to bring it onto the documentation/ site.

Secondary audience. Business approvers and product reviewers who receive the converted HTML for sign-off — they don't run the command, but its output shapes how they engage with the design.

Not for. Authoring or editing a D101 — that happens via /d101-feature-design, which writes HTML directly. Auto-publishing to GitHub Pages or any external surface — the command writes one file locally; sharing is manual. Cross-D101 sites, multi-document navigation, or content management — conversion covers one D101 to one HTML, nothing more.

R1
The command MUST be invokable as /d101-convert-to-html in any product repo where the Asimov Plugin is installed.
R2
The command MUST run on the model assigned to it in the (Design, /d101-convert-to-html) row of documentation/model-choice.md; its declared model and that row MUST stay in sync.
R3
The output HTML MUST be visually identical to plugins/asimov-plugin/artifacts/documentation/d101-feature-design/d101-feature-design-template.html — same chrome, layout, and component styling — treating that template as the runtime source of the visual contract rather than rendering the visual language from memory.
R4
The command MUST recognise the canonical D101 section structure (§1 Document information … §8 References, plus optional §9 Changes from source) from the source markdown's ## N. / ## N.M headings. It does NOT load a separate markdown structural-reference template — that template was retired when the toolkit moved to HTML-first authoring; the section list is well-known and described inline in the command body.
R5
The command MUST always list candidate documentation/features/D101-*.md files (the markdown sources available to convert) sorted by modification time, marking any that already have an .html, and wait for an explicit reply — whether or not an argument was supplied. A path argument only pre-selects: the command names it as the suggested target and still asks for confirmation. Without an argument it accepts a number, filename, or path in reply. It MUST NOT auto-select.
R6
The command MUST write its output to <source>.html next to the source markdown (e.g. documentation/features/D101-foo.md → documentation/features/D101-foo.html).
R7
The command MUST preserve markdown content 1:1 in the output: no editorializing, no reordering of sections, no summarizing, no invention. Every paragraph, list item, table cell, requirement, decision, AC, and question in the source MD MUST appear in the output HTML in the same order and wording.
R8
The command MUST map each markdown section to the HTML component the catalogue assigns to that section type (the catalogue at the top of d101-feature-design-template.html and the table in §4.2 are authoritative). A section whose type is not in the catalogue MUST render as plain prose and be reported (see §6.7) — the command MUST NOT invent a new component class for it.
R9
The command MUST use neutral bullets (→) for <ul class="bullets"> items by default, and ⚠ (<li class="warn">) only for items that are real foot-guns (items the source MD marks with ⚠, or items the source MD explicitly frames as a "watch out" / surprise outcome). The command MUST NOT emit ✓ or ✗ symbols in the output, even when the source MD uses them.
R10
The command MUST refuse to render if the source markdown cannot be read or the template HTML cannot be loaded — reporting the missing path and stopping without writing any file.
R11
When the target HTML file already exists, the command MUST show a one-screen diff summary against the planned output and present three options — overwrite (default), write to alternative path, or cancel. It MUST NOT overwrite without explicit confirmation.
R12
The command MUST NOT add interactive widgets (calculators, sliders, animations, fade-ins) to the output, and MUST emit no <script> at all — the template carries none, so the output is fully static. Rich HTML structure is in scope; interactive behaviour is not.
R13
The output HTML MUST be a single self-contained file: all CSS inline, no required external JavaScript, only Google Fonts as an external CDN dependency (with system-font fallback when offline).
R14
The output HTML MUST carry both top-bar chips per template ground rule 12 — a .status-chip from the source's §1 Status row plus version, and a .phase-chip.
R15
The .phase-chip value MUST be derived from the source markdown, not asked for: a populated technical-design section yields Full design; an absent, empty, or bare-TBD technical-design section yields Business design.
R16
When the derived phase is Business design, §6 MUST render as the #s6-open Still to write section instead of §6.1–§6.8, with the outstanding list built only from what the source markdown itself states is undecided.
R17
The command MUST NOT change a source's Draft status to Approved.
R18
When it renders a diagram, the command SHOULD load plugins/asimov-plugin/resources/diagrams/README.md and the notation template that routing table points to, and follow that template's notation, node budget and geometry. This input is best-effort, not a hard dependency like the visual template (R10): when the README or the routed template cannot be read, the command MUST draw a flowchart instead, MUST say so in chat, and MUST NOT stop the conversion.
R19
The output MUST always carry a top-level §5 UI Design section, listed in the side-nav. UI content the source carries (surfaces, screenshots, mockup references) renders as a .subhead per surface + <ul class="bullets">; a source with no UI content gets a .callout reading N/A — backend-only feature, no user-facing surface. The section MUST NOT be omitted — it would leave a §4 → §6 gap.
R20
The output MUST always carry a top-level §7 Implementation heading, listed in the side-nav, as a stub: an N/A — no implementation notes in source .callout when the derived phase is Full design, or the one-line #s7-pending stub when it is Business design. Legacy markdown has no implementation section; the command MUST NOT invent build notes. Acceptance, open questions, references and changes-from-source follow at §8–§11.
R21
Before its first tool call, the command MUST emit one sentence saying what it will do and where the output lands (e.g. "Converting a markdown D101 to HTML next to the source in documentation/features/. The markdown won't be modified.").
R22
The output's top-nav MUST be site-wide — brand and section links point at ../index.html and ../index.html#s1..#s6, never at per-page anchors. The per-page TOC lives in .side-nav, populated from the sections the output actually emits at their HTML output numbers (nested <ul> for §4.x and §6.x; a single flat §6 Still to write entry in a business-design output).
R23
The command MUST NOT synthesize UI mockups. It MAY embed an existing mockup file via <iframe class="mockup-frame"> only when the source markdown already references it; screenshots render as relative <img> tags.
NF1
Read-only on the markdown source. R7 is load-bearing — developers will iterate the MD and re-render multiple times; corruption of MD by a render step would break the trust contract with /d101-feature-design.
NF2
No drift from the template. R3 is load-bearing — the visual language is owned by the template file, not by the command body. New visual components are added to the template first; the command picks them up at the next invocation.
NF3
No product-specific assumptions in the command body. Per D100 §8.4, the command works in any repo that follows the documentation/features/ convention. Product entity names MUST NOT appear in the command prompt.
NF4
Idempotent. Running /d101-convert-to-html twice on an unchanged MD produces byte-identical HTML, modulo the choice of file written. This makes Git noise predictable for repos that commit rendered HTML.
OOS
Editing the markdown. Reason: separating render from authoring keeps the L3 pipeline coherent — /d101-feature-design owns authoring; /d101-review owns self-check; /d101-convert-to-html owns rendering. Mixing roles undermines the reviewer-not-author gate.
OOS
Auto-publishing to GitHub Pages, a wiki, or any external surface. Reason: GitHub-coupling is a fork point (D100 §8.4); product repos may want different publish destinations. The command writes one file locally; how it's shared is the developer's choice.
OOS
Multi-document sites or cross-D101 navigation. Reason: cross-document concerns (terminology drift, sibling-D101 references) belong to a future /trace command (research/additional-command-ideas.md §3.3). /d101-convert-to-html renders one D101 to one HTML.
OOS
Edit-back from HTML to MD. Reason: the conversion is one-way — the HTML becomes the record and the MD is retired; round-tripping invites silent divergence.
OOS
Translation / localization. Reason: the command renders source-language content as-is. Localization is a publishing concern, not a rendering concern.
OOS
Batch rendering of all D101s in a folder. Reason: defer to v2 if a real need surfaces. v1 is single-file to keep the contract small.
OOS
PR comments or inline annotations. Reason: same as /d101-review — GitHub-coupling is a fork point. The HTML is a standalone artifact.
4
Business design
Design principles, the artifact model and section→component mapping, the render flow, the bullet/chapter/meta-note rules, and the decisions with rejected alternatives.

§4.1Design principles

1
The legacy markdown is the input; the HTML is the migrated output. New D101s are authored directly as HTML by /d101-feature-design. This command operates only on legacy markdown D101s: it reads the markdown 1:1 and emits the HTML once. It never edits the markdown, and the migrated HTML — not the markdown — becomes the doc the team carries forward.
2
No invented content. Every word, every example, every number in the HTML traces to the source MD. The command does not paraphrase, summarize, or "improve" content — even when an LLM would naturally want to.
3
Visual structure speaks for itself. Section numbers go as small inline badges, not on their own line. Editorial titles ("What must be true" alongside "§3 Requirements") are dropped — the §-badge + topic name is enough. Chapter bands separate multi-subsection chapters (§4, §6) but singleton chapters get no extra framing.
4
Bullets are neutral by default. Use → arrows for ordinary items, ⚠ only for items the source MD marks as foot-guns or explicit "watch outs". Never ✓ / ✗ — they overstate contrast that often isn't there (a "rule applied" outcome and a "rule's null branch" outcome are both the rule working, not a positive/negative pair).
5
One-page, self-contained. The output is one HTML file with inline CSS, no required JS, no CDN beyond fonts. Offline-readable, email-attachable, no build step.

§4.2Model / concepts

The command operates on three artifact types.

Source markdown
input

A legacy markdown D101 living at documentation/features/D101-<slug>.md in the active product repo, following the canonical §1–§8 section structure (and optionally §9 for reverse-engineered features). Such files predate the HTML-first switch or were imported from elsewhere.

Visual template
runtime read

plugins/asimov-plugin/artifacts/documentation/d101-feature-design/d101-feature-design-template.html. A working HTML scaffold containing the full CSS, top-nav / hero / metadata-strip / footer shells, chapter-band markup, and one example of each component class. The command reads it at runtime to learn the visual vocabulary.

Output HTML
derived

<source>.html written next to the source markdown. Self-contained: CSS inline, no required JS, Google Fonts as the only external dependency.

The conversion is a section-to-component mapping: each markdown section type has a preferred HTML component class. The mapping is documented in two places — the catalogue at the top of d101-feature-design-template.html (the runtime source of truth) and the table below (the human-readable index).

Legacy MD numbers in, current HTML numbers out. Legacy markdown predates the current template, which promotes UI Design to a top-level §5 and shifts the technical design to §6, then adds a top-level §7 Implementation (acceptance §8, open questions §9, references §10, changes from source §11). The MD section column below keeps the source's legacy numbering; the converter emits each into the correspondingly-named HTML section at its current template number, and inserts the two sections legacy markdown never had — §5 UI Design (an N/A stub when the source has no user-facing surface, R19) and §7 Implementation (always a stub, R20) — so the output matches every other HTML D101. Section content order and wording are preserved — only the §-labels move. See d101-convert-to-html.md.

§4.3Flows

§4.3.1 Render a single D101

Trigger. Developer runs /d101-convert-to-html [optional path] in a product repo.

Steps.

1
Command loads ${CLAUDE_PLUGIN_ROOT}/artifacts/documentation/d101-feature-design/d101-feature-design-template.html. If it fails, stop with a missing-path error. (No separate markdown template is loaded — see R4.)
2
Resolve the target markdown path: always list documentation/features/D101-*.md (marking those that already have an .html); an explicit $ARGUMENTS becomes the suggested target. Wait for the developer's confirmation or pick in both cases (R5).
3
Read the source MD.
4
Determine output path: <source>.html. If the file exists, show a diff summary and present overwrite / write-elsewhere / cancel.
5
Walk the MD section by section. For each, identify the section type from the heading and map to the corresponding HTML component per §4.2.
6
Substitute content from the MD into the component templates; do not invent, summarize, or reorder.
7
Write the HTML file.
8
Report the path back, plus any non-mapped sections that fell back to plain prose.

Outcome. A self-contained HTML file exists at the target path; developer can open it in a browser or email it.

Error paths. Missing source MD: stop and report. Missing template: stop and report. Target HTML exists: show diff and wait for confirmation. Non-standard section in MD: render as plain prose and flag in the final summary.

§4.4Rules / constraints

Each rule carries a positive example and a counter-example — the case where the rule deliberately does not fire.

R-NEUT
Bullets are neutral
⚠ only for foot-guns.
  • Positive example. A source-MD bullet the author wrote as a foot-gun — e.g. ⚠ Moving the output HTML breaks its relative image links, or one the MD frames as a "watch out" — renders as <li class="warn"> with ⚠ styling; the neutral bullets in the same list keep →.
  • Counter-example. A rule whose two bullets describe valid branches of one behaviour — "section is in the catalogue → mapped to its component" and "section is absent from the catalogue → rendered as plain prose" — are both the rule working; both stay neutral <li> with →, with no ⚠ even though they contrast.
R-CHAP
Chapter bands
Only for multi-subsection chapters.
  • Positive example. Source MD §4 has subsections §4.1, §4.2, §4.3, §4.4, §4.5. The render emits a .chapter-band block with numeral 4 before the §4.1 section.
  • Counter-example. Source MD §3 has subsections §3.1, §3.2, §3.3 (functional / non-functional / OOS), but the render treats §3 as a single section with three flat .subhead groups (all visible, no tabs, no script) — no chapter band. The render also emits no chapter band for HTML §2, §5, the §7 stub, §8, §9, §10, which are singleton sections.
R-DROP
Drop meta-notes
Drop self-referential structural notes.
  • Positive example. Source MD §4 begins with an italicized "Structural note" explaining that §4.3 uses field-organised structure rather than the template's typical Flows format. The render drops this paragraph — the visual structure makes the choice self-evident.
  • Counter-example. Source MD §4.3 begins with a substantive intro paragraph that defines the concepts the subsections will refer to. The render keeps this paragraph as .section-desc because it's content, not structural commentary.

§4.5Decisions and alternatives

A decision recorded without its rejected alternative is one that gets re-litigated.

Decided
Alternatives considered
Why this won
Conversion mechanism — AI-driven via Claude Code slash command
Pandoc + post-process script; a Python/JS markdown-it converter with custom plugins
Pandoc emits flat semantic HTML; the rich component-class output (.subhead + bullet blocks, .data-table, .decisions matrix, severity chips, inline SVG flows) requires structural reasoning that a parser-only pipeline can't do. A custom converter would need maintenance equivalent to writing a new toolkit. AI-driven loses determinism but gains adaptability to non-standard MD sections.
Model — claude-sonnet-4-6 (default effort)
Opus 4.8 xhigh; Haiku 4.5
Conversion is a contractual transformation (MD section → component per documented mapping). Sonnet's reasoning is sufficient and matches the review-tier defaults (/d101-review, /s101-review). Opus is overkill for the bounded task. Haiku risks weak component choices for sections that don't map cleanly to the catalogue.
Template form — Working HTML scaffold with placeholder content + inline catalogue
Skeleton with {{section}} markers only; CSS-only "design system" doc
A working example shows the AI all components in context with their real markup, not as abstract rules — letting it match by example rather than parse instructions. Skeleton-only loses the demonstration of how components nest. CSS-only loses the structural patterns (chapter bands, nav, hero shell) that aren't class-level.
Source of record — the HTML, once converted; the markdown is retired
Keep the markdown canonical and re-render on every change; bi-directional sync
The toolkit authors D101s as HTML (/d101-feature-design writes it, /d101-review reads it), so a converted doc joins that flow only if the HTML is the record — the conversion runs once, then edits happen in the HTML. Keeping the MD canonical would leave two files to drift; bi-directional sync invites silent drift. The L3 pipeline commits to one canonical form (§4.1 principle 1).
Output destination — Next to the source MD (<source>.html)
Separate /rendered/ folder; gh-pages branch; .html in .gitignore by default
Co-location keeps source + render visible together for navigation and for Git review. A separate folder adds a path convention that products would have to learn. .gitignore policy is left to each product repo — the command doesn't enforce.
Bullet symbol policy — Neutral → + ⚠ only
✓ / ✗ pairs preserved from MD; ✓ / ✗ / ⚠ triad
Empirically observed in a source D101, ✗ was applied to "the rule's null branch" — both outcomes were the rule working. The symbol overstated contrast where none existed. Neutral bullets + sparingly-used ⚠ for real foot-guns surface attention where it belongs.

§6.1Platform / infrastructure

Lives in the Asimov Plugin, alongside /d101-feature-design and /d101-review. Specifically:

  • Command file: plugins/asimov-plugin/commands/d101-convert-to-html.md
  • HTML template (read at runtime): plugins/asimov-plugin/artifacts/documentation/d101-feature-design/d101-feature-design-template.html — the sole template the command loads; the markdown section structure is recognised inline (R4).

  • Writes to: <active-product-repo>/<source-md-dir>/<source-md-stem>.html

No new Azure resources, no new infrastructure, no new SDK dependencies. The command is a markdown file that Claude Code executes.

§6.8Known constraints & gotchas

01
Google Fonts dependency
The template imports Inter and JetBrains Mono from fonts.googleapis.com. Offline-only environments will fall back to system fonts; layout may shift slightly. No alternative is offered in v1 — bundling fonts inflates the HTML by ~100 KB per render and was judged not worth it for a derivative artifact.
02
Single-page output
Long D101s produce long HTML pages. There is no pagination and no collapsible sections; the only navigation aid is the .side-nav per-page TOC in the left sidebar (the top-nav is site-wide, R22). This is intentional — sign-off reviewers should see the whole document in one scroll.
03
Sonnet 4.6 may editorialize
Even with the explicit "no invented content" rule, the model occasionally rephrases content into "better" English. The command prompt names this risk and the rule explicitly; the gap-free verdict on a rendered D101 includes a 1:1 content check.
04
No image embedding
Images referenced in the source MD (e.g. documentation/features/images/<slug>/foo.png) are rendered as relative <img> tags — they work when the HTML is opened from the file system, may break when the HTML is moved or emailed. v1 does not copy images alongside the HTML. (See Q4.)

§8Open questions

Q1 Context& lead (@Aborup)
Should the command support a batch mode /d101-convert-to-html documentation/features/ to render every D101 in a folder, with a single summary report?
Resolution path: Defer to v2; revisit if multi-D101 rendering becomes a recurring need. v1 is single-file by design (§3.3).
Q2 Each product repo's maintainer
Should the output HTML be added to Git by default, or recommended for .gitignore as a derived artifact?
Decision: Resolved 2026-09-15 — commit it. The HTML is the source of record after conversion (§4.5), so there is nothing to ignore; the once-promised .gitignore suggestion in the final summary was never implemented and is dropped.
Q3 Context& lead
Should the template support custom-coloured chapter bands (e.g. per repo or per D101 scope), via a frontmatter knob on the MD or a per-repo template override?
Resolution path: Defer; current template uses a uniform cyan accent. Reconsider if a product team requests visual differentiation across product repos.
Q4 Context& lead
When a source MD references images at documentation/features/images/<slug>/, should the command copy them alongside the HTML, rewrite paths, or rely on relative paths to the original location?
Resolution path: Investigate during the first real-world use that involves images. v1 uses relative paths to the MD's location.
Q5 @Aborup + reviewer of this D101
Should /d101-convert-to-html register a forking pin alongside /d101-feature-design and /d101-review (D100 §8.4 — documentation/features/D101-*.md literal in lockstep)?
Decision: Resolved 2026-09-15 — yes. The command's Repo handling section pins the lockstep with d101-feature-design.md and d101-review.md, mirrored by CLAUDE.md hard rule 9.
Q6 @Aborup
Should /d101-convert-to-html flag the rendered HTML as stale when the source MD has been modified since the last render?
Resolution path: Defer; v1 always re-renders on demand. Staleness detection is a publishing concern; the developer who runs the command knows whether their MD has changed.
