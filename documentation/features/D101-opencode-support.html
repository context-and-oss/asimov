D101 · Feature design · Asimov distribution

OpenCode 2 support

Make Asimov's full workflow available to OpenCode 2 users, without requiring another coding tool or changing the artifacts and human gates their teams already use.

Scope: A third supported harness for setup, Design, Spec, Build, review, verification, personas, the Project frame and run logging; global installation is the default and repo initialization is explicit. §2–§5 describe the proposed business agreement; §6 is open — see §6.

§2Purpose & audience

Developers who choose OpenCode 2 should not have to switch coding tools to use Asimov's complete delivery workflow.

  • Access depends on the coding tool. Asimov currently documents installation for Claude Code and Codex, but offers no supported OpenCode setup.
  • Finding skills is not enough. A developer needs the workers, checks, recovery and human gates to finish a feature, not only design prompts.
  • Mixed-tool teams need one record. Designs, plans, task specifications and build records must retain the same meaning regardless of the coding tool used.
Audience. Primary readers are developers using OpenCode 2 and teams adopting Asimov; secondary readers are maintainers shipping and supporting all three harnesses.

R20

4
Business design
One workflow contract, two installation scopes, explicit setup and unchanged human ownership.

§4.1Principles

1
Full workflow at launch. A supported OpenCode user can finish the existing Design → Spec → Code → Review → Test sequence.
2
One Asimov. Tool choice changes how work is launched, not what the team's artifacts mean.
3
Install is not initialize. Making Asimov available never implies consent to rewrite a product repo.
4
The person remains the director. Checks provide evidence, while the existing approval, stop-ruling and commit decisions stay with their designated humans.

§4.2Concepts

Concept
What it means
Harness
The coding tool that hosts the conversation, runs tools and launches workers.
Installation scope
Global availability for one developer or availability restricted to one product repo.
Repo initialization
A separately requested, confirmed setup of Asimov context, conventions and documentation.
Entry point
The developer-invoked start of one stage or the Project frame.
Agent identity
A named worker whose role and boundaries are shared across harnesses.
Plan and task specifications
The approved work graph and individual briefs that establish what each worker may build.
Ledger
The durable record of attempts, findings, rulings and commits used to resume a build.
Run log
A disposable operational observation of a run, not its approval record or explanation of decisions.
Project frame
The engagement-level conversation around feature delivery, limited to capabilities already shipped.

§4.3User journeys

A — Make Asimov available

The developer installs Asimov before starting a product workflow.

  1. 1Follow the global installation instructions, or explicitly choose project-local installation.
  2. 2Confirm that the documented Asimov entry points are available in the intended scope.
  3. 3Leave all product artifacts unchanged until a writing workflow is requested.

If installation fails or the OpenCode version is unsupported, report that Asimov is not ready with the documented corrective action.

B — Initialize or refresh a repo

The developer invokes setup in the active product repo.

  1. 1Inspect existing instructions, detected stacks and documentation.
  2. 2Show each proposed target and whether it is new, managed, merged, skipped or needs a decision.
  3. 3Wait for confirmation before writing the agreed context, convention read-lists and site.
  4. 4Report completed writes, skipped conflicts and the next workflow the developer can start.

A declined plan writes nothing; conflicting ownership or damaged managed boundaries leave the affected target untouched and request a human decision.

C — Design and specify a feature

The developer names a feature, an existing design or another currently supported design input.

  1. 1Interview for the business design, write the D101 and stop so the developer can read it.
  2. 2On a later invocation, complete the technical design without recording business approval.
  3. 3Offer the phase-appropriate gap review and shipped or custom persona reads.
  4. 4Start Spec from an eligible design, show the proposed cut and wait for the person's plan approval.
  5. 5Produce and validate the task specifications, reaching ready only when the current Spec contract allows it.

Missing inputs or failed checks are surfaced through the existing stage's correction path, not converted into an approval or guessed past.

D — Build, recover and finish

The developer invokes Build on a ready plan in an eligible working tree.

Developer entry / gateWorker activityEnd of this phase's interaction

The diagram shows the successful phase hand-offs; retries and stops follow the numbered journey and existing Build contract below.

  1. 1Run the existing readiness and resume checks before dispatching any task.
  2. 2Send ready, disjoint-file tasks to Giskard, Daneel or Calvin according to their specified roles.
  3. 3Have Baley review the phase, then Powell verify its promised outcomes.
  4. 4Return failed work through the existing retry loop, recording findings in the ledger.
  5. 5Show the passed checkpoint and wait for go before committing the phase.
  6. 6Resume a later session from the ledger, or finish with the commit record and leave PR creation to the developer.

A third task failure, design gap, permission refusal or failed resume check stops the affected progression with evidence and the existing human recovery choices.

E — Use the frame, update or remove
  • The developer can invoke the Project frame or delivery-model advice independently of a feature build.
  • The developer follows the update procedure for the selected installation scope without granting permission to refresh product context.
  • The developer removes Asimov's OpenCode availability without deleting designs, specifications or committed ledgers.

An unavailable Project action is identified as not shipped rather than invented; update or removal conflicts leave unrelated configuration intact and require a human decision.

§4.4Rules & boundaries

BR1 — Global is the default, not the only scope

When no installation scope is chosen, the documented default is global; project-local installation requires an explicit choice.

  • Positive: a developer following the default guide gets availability across their repos.
  • Counter-example: selecting project-local leaves an unrelated repo without Asimov availability from that installation.
BR2 — Setup consent is separate

Only a confirmed initialization plan authorizes setup changes, and only within its proposed targets.

  • Positive: confirming a convention read-list update changes its managed content.
  • Counter-example: installing or updating Asimov does not regenerate that repo's instructions or documentation.
BR3 — Explicit entry points, reusable supporting skills

Stage and setup entry points require an explicit developer invocation; supporting role, artifact, persona and advisory skills retain their current task-driven use.

  • Positive: naming the Build entry point with a ready-plan slug starts its readiness checks.
  • Counter-example: asking a general coding question does not implicitly initialize the repo or start a build.
BR4 — Same gates, not automatic approval

Each stage follows its current approval policy, and a passing agent report does not substitute for a human decision.

  • Positive: a passed phase waits for the person's go before its commit.
  • Counter-example: a design-review report does not mark the D101 Approved, even when no gaps are reported.
BR5 — Worker boundaries survive portability

Builders change only their assigned files; reviewers and verifiers do not hand-edit product files.

  • Positive: Giskard implements a .NET task inside its owned-file scope.
  • Counter-example: Baley finding a defect reports it instead of repairing it, while permitted test/build commands may regenerate their declared outputs.
BR6 — Resume from evidence

A resumed run uses the ledger and current plan checks, not assumed worker memory from a previous session.

  • Positive: a new session retains committed phases and starts workers for the remaining work.
  • Counter-example: a changed approval fingerprint fails resume checks rather than inheriting the earlier go.
BR7 — Missing prerequisites are visible

If a step cannot obtain its required resource, worker or permission, it reports the blocker before proceeding with that step.

  • Positive: an unavailable builder prevents its task from starting and names how to enable it.
  • Counter-example: an optional log-write failure does not prevent a worker from completing its task.
BR8 — Existing ownership wins

Setup, update and removal preserve non-Asimov-owned content; uncertain ownership requires a human decision.

  • Positive: refreshing an intact Asimov-managed context region preserves the surrounding instructions.
  • Counter-example: a same-named user agent or broken managed-region marker is not silently overwritten.
BR9 — Logs observe, ledgers explain

The run log follows the existing privacy and non-blocking contract; decisions and recovery evidence remain in the ledger.

  • Positive: a worker-start observation records its identity without its full brief.
  • Counter-example: a logger error neither retries the builder nor records an approval, and raw diagnostic payloads remain opt-in.
BR10 — Removal is not artifact deletion

Removing the integration removes its availability, not authored product records.

  • Positive: a completed design and ledger remain readable after removal.
  • Counter-example: removing global availability does not erase another separately installed project-local integration.

§5UI Design

Use OpenCode's existing command discovery and conversation surface, illustrated below in a neutral terminal-style mockup rather than a new Asimov screen.

Command invocation, confirmation and recovery
  • Layout. Native command discovery feeds a conversation containing the target, concise progress, the checkpoint or write plan and the next required action.
  • Names. Expose /asimov-init, /asimov-design, /asimov-design-review, /asimov-spec, /asimov-build and /asimov-project.
  • Empty. An entry point without a target offers the existing eligible-target list or interview rather than guessing a feature.
  • Running. Show the target and one progress line per dispatched call, with reports retained in their current sidecar or ledger.
  • Awaiting consent. Setup waits at its write plan, Spec at its cut and Build at its phase checkpoint.
  • Error. A blocker names the affected step and recovery action; a counted task failure exposes the first finding and the remaining retry or stop route.
  • Populated. Successful output names the artifact or commit and the next stage, without recording a D101 approval.
  • Try it. Select setup and cancel its plan, select Build and choose go, or switch to the stopped scenario and choose resume or discard.
The mockup simulates conversation outcomes only: its scenario selector and response buttons are review aids, not proposed new OpenCode controls; it performs no installation, writes or commits.

§6Still to write

This document is not gap-free. The workflow scope and installation experience are defined, but the integration mechanism is not settled; no S102 can be written from this design until the following questions are resolved.
  • How one released distribution makes shared skills, commands, agents and all supporting artifacts available in both installation scopes without separating their versions.
  • How installed resource paths remain correct across package caches, local clones, nested working directories and paths containing spaces.
  • How OpenCode worker spawning and continuation preserve fresh first attempts, retry context, disjoint-file concurrency and cancellation without weakening the ledger's guarantees.
  • How Spec's writer and validation boundaries map to OpenCode's tools so that checks remain independent of the authoring context wherever the current contract requires it.
  • How setup owns and refreshes context and agent definitions without claiming existing user content or introducing duplicate mixed-harness instructions.
  • How permissions enforce reviewer and verifier boundaries while allowing the prescribed checks and explicitly confirmed writes or commits.
  • How stage and worker lifecycle observations map to OpenCode's actual events, including parent/child attribution, interrupted sessions and location changes, without inventing a session-end event.
  • How the model selection policy and missing-model recovery work for OpenCode providers, including the tier decision in Q3.
  • Which minimum OpenCode 2 version and prerequisites the installed-package tests will establish for Windows, Linux and macOS.
  • How updates and removal preserve unrelated configuration and authored records when global and project-local installations coexist.

Decider for these mechanism questions: Asimov maintainers, during the separate technical-design pass and before Spec begins.

§9Open questions

Q1Asimov maintainers
Who is the named business approver and who independently reviews the full design?
Resolution path: maintainers nominate the people before requesting approval; this draft records no approval.
Q2Asimov maintainers
What minimum OpenCode 2 version and host prerequisites constitute supported full-workflow operation?
Resolution path: establish the compatibility matrix from installed-package checks during technical design, before publishing installation guidance.
Q3Asimov maintainers
Should OpenCode inherit the session model by default, and how should optional task-tier mappings override it?
Resolution path: settle provider/model selection and missing-model behavior in technical design before defining configuration and dispatch contracts.
Q4Asimov maintainers
Which published package identity and release process provide a single compatible Asimov update?
Resolution path: verify package ownership and align release/version handling during technical design before the first OpenCode publication.
Resolved during authoring — 2026-10-28
Q5Feature requester
Is the first release full workflow or a setup-and-Design preview?
Decision: full workflow, including agents, retries, resume and logging; reducing it requires reopening scope.
Q6Feature requester
What installation experience should developers receive?
Decision: global by default, optional project-local installation and explicit repo initialization; automatic setup would reopen the consent agreement.
