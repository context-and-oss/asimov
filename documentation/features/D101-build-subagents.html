D101 · Feature design · asimov-plugin

Build subagents

The three Accelerate build-role subagents — two builders (.NET, Angular) and a tester — that carry a reusable core but load the active product repo's own conventions at run-time, and flag gaps or conflicts instead of guessing a default the team never approved. The shared subagent mechanism lives in D100 §7.2.1; this D101 covers what's specific to the three.

Model
Sonnet 4.6
Scope: asimov-plugin — the three build-role subagents (two builders + a tester) that load a product repo's per-stack conventions at run-time via a canonical entry README, and flag uncovered or conflicting cases rather than inventing a default. The reviewer (Baley) is a separate role with its own D101.

§2Why this exists

The toolkit covers the Design stage but ships no coding agents. A generic AI assistant doesn't know a given repo's patterns — its naming, its layer model, its test style — so its output has to be reconciled with the house conventions by hand, every time. A mature repo can carry dozens of convention files; re-explaining them in each prompt is its own tax.

01
Manual style fixes
Generic output ignores the repo's patterns — naming, project structure, test shape — so a reviewer hand-corrects it to match before it can merge.
02
Conventions re-explained
The repo's convention files get pasted or paraphrased into prompts again and again — context burned on every turn, and the paraphrase drifts from the source.
03
Silent wrong defaults
Where a convention is missing, or the task contradicts one, a generic agent quietly picks something — a default the team never reviewed and may not want.
Audience. Developers using asimov-plugin inside a product repo who want AI coding and test help that respects that repo's established conventions without re-stating them each time.

Functional 13
Non-functional 2
Out of scope 5
R1
The plugin ships three subagents: a .NET developer, an Angular developer, and a test author.
R2
Each subagent carries base info following a shared six-field skeleton — Role, Stack competence, Reads, Workflow, Boundaries, Output — independent of any product repo. The tester adds a seventh field, Target (R11), between Stack competence and Reads.
R3
At run-time, each subagent reads exactly one canonical per-stack entry file, addressed by exact path (not a bare folder reference).
R4
The entry-file mapping is: .NET → documentation/conventions/dotnet/README.md; Angular → documentation/conventions/angular/README.md; test → documentation/conventions/test/README.md.
R5
Each per-stack entry README @-references every convention file in its stack, giving the agent the complete read-list from one file; the agent then reads each referenced file (the @-list is not auto-expanded by the Read tool — see §6.8).
R6
When the conventions for a stack are absent or do not cover the task, the agent proceeds on base info and flags the uncovered area.
R7
When the task contradicts a convention, the agent flags the conflict rather than silently following either the task or the convention.
R8
For each non-trivial decision, the agent cites the convention file that backed it, so a reviewer can verify the choice against the source.
R9
The test author may flag production code as hard-to-test (a design smell) back to its author, in addition to the gap and conflict flags.
R10
The two builders share Workflow and Output verbatim. The tester extends both — Workflow with a resolve-the-target step and an author-with-restraint step, Output with a resolved-target line and a suite-size note — and is otherwise the same.
R11
The tester authors tests for production code touched by the current branch, not the whole repo: base from git remote show origin (fallback main, then master), changeset via git diff --merge-base <base>...HEAD --name-only. It does not extend into pre-existing untouched code. An explicit invoker target (file, class, symbol) or a named base overrides the default; the resolved target is narrated before conventions are read.
R12
When there is no diff (branch even with base, or base unresolvable) and no explicit invoker target, the tester says so and stops — nothing is authored.
R13
When pre-existing untouched code in or near the target has thin coverage, the tester surfaces a coverage flag naming the location; it does not expand scope to add those tests unprompted.
NF1
No product-specific identifiers appear in the agent prompts shipped by the plugin — stack names are generic, examples are illustrative (reusability, repo hard rule 7).
NF2
Each agent declares its model in YAML frontmatter (claude-sonnet-4-6) matching a row in documentation/model-choice.md, updated in the same commit (repo hard rule 2).
OOS1
Authoring the convention content itself — that is the product repo's job; the agents only consume it.
OOS2
The code-level "how" of generation (file signatures, libraries, data structures) — that is S101 territory.
OOS3
Agents calling one another / orchestration — deferred; cross-agent coordination is its own design and not needed for this version.
OOS4
Additional stack agents (e.g. Vue, Python) — no current plans; revisit if a new primary stack appears.
OOS5
Additional test types or stacks in documentation/conventions/test/ (integration, load, Angular specs) — no current plans; .NET unit tests only for now.
4
Business design
The principles behind a reusable core plus a repo-owned overlay, the vocabulary that names the pieces, the three agents themselves, the flag-don't-guess rules, and the decisions that shaped them.

§4.1Principles

1
Reusable core, local overlay. Base info is stack knowledge that travels with the plugin; the product repo owns the conventions that adapt the agent to its house style.
2
Flag, don't guess. Where a convention is missing or conflicts with the task, the agent surfaces it instead of inventing a default the team never approved.
3
Reference by path, never inline. The repo's convention files are the run-time source of truth; the agent reads them, it does not carry copies that drift (repo hard rule 3).
4
Shared mechanism, role per agent. All three read a per-stack entry README, apply it, and flag; only the role and stack knowledge differ between them — plus the tester's Target, which scopes what it works on (§4.3.3).

§4.2Concepts

Four terms the rest of the document leans on. The split between what ships with the plugin and what the repo owns is the load-bearing distinction.

Base info
ships in plugin

The repo-independent core of each agent, following a shared skeleton — Role, Stack competence, Reads, Workflow, Boundaries, Output. Travels with the plugin; the builders share Workflow and Output verbatim, the tester extends them and adds Target (§4.3).

Entry README
repo-owned

The single canonical file an agent reads — documentation/conventions/<stack>/README.md. Curated by the product repo; the one place that decides what the agent sees.

Convention file
repo-owned

An individual rule file (naming.md, service-pattern.md). The agent reaches it by reading every file the entry README @-references — the README lists them; the agent loads each.

Overlay & precedence
combination rule

How the two combine: conventions refine and constrain base info. On conflict the agent flags rather than silently choosing; on a gap it proceeds on base info and flags.

§4.3The three agents

Same mechanism, three personas — Giskard, Daneel, and Calvin. Each agent's base info follows a shared skeleton; the cards carry the per-agent fields.

Base-info skeleton. Every agent's base info carries the same six fields so the three stay consistent; the tester adds a seventh, Target (R11). Two are shared by the builders verbatim and stated once here: Workflow — read the entry README, apply conventions over base info, cite the source file, and flag any gap or conflict (§4.1, §4.4); Output — code or tests a reviewer accepts without style fixes, plus a short summary citing the conventions applied and listing any flags raised (§2, R8). The tester extends Workflow with a resolve-the-target step first and an author-with-restraint step, and Output with a resolved-target line (Authoring tests for: …) and a suite-size note (R10). The per-agent fields — Role, Stack competence, and Boundaries — are on the cards below; Reads is each card's entry path.
§4.3.1 Giskard
Giskard — the .NET developer
"How should this C#/.NET code be written in this repo?"
Role: writes and modifies production C#/.NET backend code. Reads documentation/conventions/dotnet/README.md and the files it @-references, then conforms to them.
  • Competence: idiomatic C#, async, dependency injection, common backend patterns — repo-independent
  • Boundary: backend only — tests are Calvin's, frontend is Daneel's (no auto hand-off, OOS3)
  • A repo's .NET set is usually the largest, so this agent typically loads the most convention context of the three
§4.3.2 Daneel
Daneel — the Angular developer
"How should this TypeScript/Angular code be written in this repo?"
Role: writes and modifies frontend TypeScript/Angular code. Reads documentation/conventions/angular/README.md and the files it @-references.
  • Competence: Angular, TypeScript, component/template and RxJS idioms — repo-independent
  • Boundary: frontend only — tests go to Calvin, backend to Giskard
  • Where a repo's Angular set is thin or in flux, this agent hits the gap rule (§4.4) often until the repo fills it in
§4.3.3 Calvin
Calvin — the test author
"How should tests be written in this repo?"
Role: authors tests for the production code touched by the current branch — a diff against base, not the whole repo — or for an explicit invoker target (R11). Reads documentation/conventions/test/README.md and the files it @-references.
  • Competence: unit-testing craft — arrange-act-assert, test naming, coverage thinking — repo-independent
  • Target: base via git remote show origin, changeset via git diff --merge-base; narrated before conventions are read. No diff and no explicit target → says so and stops (R12)
  • Boundary: writes tests, not production code; may flag production code as hard-to-test (R9) and untouched code with thin coverage (R13) back to its author — never expands scope on its own
  • Scope is .NET unit tests only for now — other test types/stacks are out of scope (OOS5)
Naming & Accelerate roles. Agents are named from Isaac Asimov's canon — fitting for a toolkit called Asimov — and each maps to an Accelerate multi-agent role (D100 §4.4). In this D101: Giskard (.NET) and Daneel (Angular) are builders; Calvin is the tester. The reviewer role — Baley, the detective who verifies — now ships in its own D101 (D101-baley-the-code-reviewer.html). Still reserved: Hari and Dornick for the planner/architect and spec-author roles, not yet built.

§4.4Rules

Three conditional rules govern what an agent does at the edges — the third is the tester's alone — plus the traceability expectation. Each conditional rule carries the case where it fires and the adjacent case where it does not.

Conflict rule
Flag
When the task contradicts a convention, the agent flags the conflict and stops for a decision — it does not silently follow either side.
  • Fires: the README says "no AutoMapper", the task asks for AutoMapper → the agent flags the conflict
  • Does not fire: the task says nothing about mapping → the agent just follows the README, no flag needed
Gap rule
Flag + proceed
When a convention for the area is missing or sparse, the agent delivers on base info and flags that no convention governed the choice.
  • Fires: angular/ only has naming.md, the task touches an uncovered area → the agent proceeds and flags the gap
  • Does not fire: dotnet/ fully covers the task → the agent applies the conventions, no gap flag
Coverage rule (tester)
Flag, stay in scope
When pre-existing untouched code in or near the target has thin coverage, the tester names the location as a flag and leaves it — the developer routes the follow-up (R13).
  • Fires: the branch adds one method to a class whose other methods have no tests → tests for the new method, a coverage flag for the rest
  • Does not fire: the invoker hands an explicit target ("cover OrderRepository") → the whole target is in scope, nothing to flag
Traceability
Cite source
Each non-trivial decision points back to the convention file that backed it, so a reviewer can verify it against the source (R8).
  • "private fields are camelCase per dotnet/service-pattern.md"
  • Pure base-info decisions (language syntax, framework idioms) need no citation

§4.5Decisions

A decision recorded without its rejected alternative is one that gets re-litigated.

Decided
Alternative considered
Why rejected
Agents read one canonical per-stack entry README by exact path; its @-references are the read-list the agent then loads file by file.
Point the agent at the conventions folder and let it glob for what to read.
Bare folder references are empirically unreliable — the agent has to guess what's relevant. A single curated entry file gives a predictable, reviewable read-list and one place for the repo to curate. (The @-list is read explicitly, not auto-expanded — see §6.8.)
Three stack-specific agents (.NET, Angular, test author).
One generic coding agent parametrised by stack.
Stack knowledge and conventions differ enough that a single prompt would be diluted; separate agents keep each role sharp and each convention set focused.
Conventions live in the product repo and are read at run-time.
Ship the conventions inside the plugin.
Conventions are repo-specific; baking them in breaks reusability (hard rule 7) and would force a plugin release for every repo's house style.
All three agents run on Sonnet 4.6.
Opus for code/test generation.
Code and test generation is contract-bounded work that runs often; Sonnet's reasoning suffices and throughput matters (model-choice.md §2).
Agents are named from Isaac Asimov's canon (Giskard, Daneel, Calvin; Baley since built as the reviewer; Hari / Dornick reserved for later roles).
Role-based names only (e.g. dotnet-developer), or persona-only (e.g. giskard).
The repo is named Asimov; canon personas give the toolkit identity and a coherent, extensible scheme. The agent name: and file combine persona + role (giskard-the-dotnet-developer), so the persona carries identity while the role keeps it discoverable for auto-delegation — both in one identifier, nothing lost.

6
Technical design
Where the agents live, how conventions get loaded and applied at run-time, the files that change, the fixed paths and model, how failures are handled, and the gotchas to watch.

§6.1Platform

The three agents are Claude Code subagents living in the agents/ directory in asimov-plugin. Each is a markdown file with YAML frontmatter declaring model: claude-sonnet-4-6. None declares tools:, so each inherits the full tool set — the tester relies on that for git via Bash (R11); contrast Baley, whose frontmatter lists tools: Read, Grep, Glob, Bash to enforce read-only. The conventions they read live in the consuming product repo under documentation/conventions/ — nothing about them ships in the plugin. No SQL, schema, or infrastructure change.

Model-choice sync. Each agent's model: frontmatter must be paired with a row in documentation/model-choice.md in the same commit (hard rule 2). The rows are added when the agent files are authored — not from this design doc — to avoid an index that names agents that don't exist yet.

§6.2Data flow

What happens from the moment an agent is invoked: it reads its stack's entry README, then reads each convention file the README @-references, and applies them alongside its base info — branching to a flag whenever it hits a gap or a conflict. The tester alone has a step before the README: it resolves its target (branch diff or explicit target) and stops if there is nothing to test.

§6.8Known constraints & gotchas

01
@-list is read, not auto-expanded
The Read tool does not transclude @-imports — that only fires in the CLAUDE.md memory chain, not for a file read on demand. So the entry README is a read-list the agent loads file by file (the Workflow's read step), not a self-expanding index. Keep each stack's list short enough that the agent reliably reads all of it.
02
README is load-bearing
A convention file that isn't @-referenced from its stack README is invisible to the agent (R5). Adding a convention file means also adding its reference, or the agent never sees it.
03
Sparse Angular conventions
The angular/ set is deliberately thin and in flux, so the Angular agent will hit the gap rule frequently until the repo fills it in. That is expected behaviour, not a defect.
