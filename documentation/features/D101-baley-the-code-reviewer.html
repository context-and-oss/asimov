D101 · Feature design · asimov-plugin

Review subagent

Baley — the Accelerate reviewer role: one read-only subagent that takes the diff of a branch against its base, loads the active product repo's own conventions for whatever stacks the diff touches, and reports findings on two axes — convention adherence and correctness & safety — without ever editing the code or declaring an approval verdict. The shared subagent mechanism lives in D100 §7.2.1; this D101 covers what's specific to the reviewer.

Scope: asimov-plugin — one code-reviewer subagent (Baley) at the Review stage that reviews a branch-vs-base diff against the product repo's run-time conventions plus base correctness/safety craft, and emits a structured, no-verdict finding report to chat.

§2Why this exists

The toolkit ships agents that author code (Giskard, Daneel) and tests (Calvin), and a command that reviews design docs (/d101-review) — but nothing reviews the code those agents produce. The L3 process rule "automated review runs before any human reviewer" currently leans on an external tool that cannot read the repo's convention files by path the way a toolkit agent can. The convention overlay is the authoritative bar, and the reviewer should read it the same way the authors do.

01
No conventions-aware first pass
The build subagents read the repo's conventions, but nothing checks the resulting code against those same conventions. The first reviewer who does is a human, opening the diff cold.
02
Style breaches reach the human
Convention deviations that a machine could catch survive to human review, so the reviewer spends attention hand-checking house style instead of substance.
03
No consistent correctness net
Bugs, broken edge cases, and obvious safety mistakes slip through without a repeatable first-pass review that runs the same way on every changeset.
Audience. Developers using asimov-plugin inside a product repo who want an automated first-pass code review that respects that repo's own conventions and surfaces correctness/safety issues before a human reviewer opens the diff.

4
Business design
The principles behind a read-only, no-verdict reviewer, the vocabulary it leans on, Baley's place among the existing agents, the flag-don't-assert rules, and the decisions that shaped them.

§4.1Principles

1
Review, don't fix. Baley surfaces evidence; the fix belongs to the build subagents (Giskard/Daneel/Calvin) and the approval belongs to the human. It is read-only by tool budget, not just by convention.
2
Conventions are the repo's, read at run-time. Baley reads the same per-stack overlay the build subagents read; it references convention files by path and never carries copies that drift (repo hard rule 3).
3
Two axes, kept apart. Convention adherence and correctness & safety are distinct lenses with distinct evidence — a cited convention file vs. a named failure class. The report keeps them in separate tables so the developer sees which is which.
4
No verdict — reviewer ≠ author. Baley never approves or blocks; the human reviewer holds the gate. This mirrors /d101-review's refusal to emit a verdict and the L3 rule that nobody approves their own work.

§4.2Concepts

Four terms the rest of the document leans on. The split between the two review axes, and the changeset as the unit of review, are the load-bearing distinctions.

Changeset
unit of review

What Baley reviews: the diff of the current branch against its base (base...HEAD), or an explicit set of paths the invoker names. Not the working tree, not the whole repo.

Convention overlay
repo-owned

The product repo's per-stack conventions Baley loads — documentation/conventions/<stack>/README.md and the files it @-references — the same overlay the build subagents read. Loaded only for stacks the changeset touches.

Axis
two lenses

The two lenses Baley applies: conventions (does it match the overlay — cites a file) and correctness & safety (is it a bug/risk — names a failure class). Each finding belongs to exactly one axis.

Finding
report unit

One observation: a file:line location, exactly one severity (Pass/Flag/Fail, §4.4), and one cited source — a convention file or a failure class. Findings never roll up into an overall score.

§4.3Baley, the reviewer

One persona, one role. Baley's base info follows the same skeleton as the build subagents — Role, Stack competence, Reads, Workflow, Boundaries, Output — with one extra field, Target, because a reviewer must first establish what changeset it is reviewing — plus two prompt sections of its own: the severity ladder (§4.4) and the hard rules (read-only, no verdict, no invented findings, cite the source, don't drift the bar, diff-only), each backed by an existing requirement (NF3/OOS1, R12, R2+R11, R9, R5, R2).

§4.3.1 Baley
Baley — the code reviewer
"Does this changeset match the repo's conventions, and is it correct and safe?"
Role: reads a branch-vs-base diff and reports findings on two axes. Read-only — it never edits the code and never approves it.
  • Competence: general review craft across C#/.NET, TypeScript/Angular, and unit tests — spotting bugs, edge-case gaps, races, leaks, injection/authz mistakes — repo-independent
  • Target: resolves the base branch (repo default, or invoker override), computes the diff with git, reviews only what it touches
  • Reads: the documentation/conventions/<stack>/README.md overlay for each stack the diff touches, plus every file it @-references
  • Boundary: reports, does not fix; does not review design docs or validate against a spec (no auto hand-off — OOS1, OOS2, OOS3)
  • A bug in code the diff does not touch is out of scope by design — Baley reviews the changeset, not the repo
Where Baley sits among the agents. In Accelerate terms the build subagents are builders and a tester: Giskard (.NET), Daneel (Angular), Calvin (tests) — see D101-build-subagents.html. Baley is the reviewer: it reviews their output for conventions and correctness. /d101-review reviews design docs, not code. The planned S102 validator (also a reviewer role) will check code against an implementation spec — a different bar from Baley's conventions-plus-correctness review (§8 Q1). The human reviewer approves; no agent does.
Naming. Agents are named from Isaac Asimov's canon. Baley — Elijah Baley, the detective who verifies — was reserved for the reviewer role in D101-build-subagents.html §4.3; this D101 ships it. The agent name: and file combine persona + role (baley-the-code-reviewer): the persona carries identity, the role keeps it discoverable for auto-delegation.

§4.4Rules

Two conditional rules govern what Baley does at the edges of its evidence, plus the severity ladder and the traceability expectation. Each conditional rule carries the case where it fires and the adjacent case where it does not.

Gap rule
Base-judgment
When no convention covers the area of a changed line, Baley judges on base craft and marks the finding as base-judgment — it does not dress a personal preference up as a convention breach.
  • Fires: the diff changes an area dotnet/ says nothing about → finding is marked base-judgment, no convention cited
  • Does not fire: dotnet/service-pattern.md covers the area → the finding cites that file as a convention breach
Uncertainty rule
Mark uncertain
When a suspected defect depends on code outside the changeset, Baley marks the finding uncertain in the reason rather than asserting a breach it cannot see in full.
  • Fires: the diff calls a method it doesn't change that might return null → flagged as uncertain, pending the unchanged code
  • Does not fire: the bug is fully visible within the changed hunk → asserted as a Fail
Traceability
Cite source
Every finding names its backing evidence (R9): a convention finding names the convention file; a correctness finding names the failure class.
  • "private fields are _camelCase per dotnet/service-pattern.md" (convention)
  • "unawaited Task — fire-and-forget" (failure class)
Severity ladder. Every finding gets exactly one severity. Pass — used at the axis level: an axis surfaced nothing for the changeset (never omit the axis silently). Flag — a real issue a reviewer should weigh but that does not, on its own, block: a minor convention deviation, a readability concern, or an uncertain finding. Fail — a clear defect to address before human review: a correctness bug, a safety mistake, or a load-bearing convention breach. The ladder mirrors /d101-review; findings are never aggregated into a score.

§4.5Decisions

A decision recorded without its rejected alternative is one that gets re-litigated.

Decided
Alternative considered
Why rejected
One unified reviewer across .NET, Angular, and test; it loads only the overlays the diff touches.
One reviewer per stack, mirroring the three build subagents.
A real changeset usually spans stacks (a feature touches backend + frontend + tests). Three reviewers would fragment one diff into three passes and three reports, and the correctness craft is largely stack-independent. One agent reads one changeset and produces one report.
Review the diff against the base branch (base...HEAD).
Review the uncommitted working tree, or review the whole repo.
The unit of review in L3 is the changeset a human will approve (the PR); base...HEAD matches that. Working-tree-only misses committed work; whole-repo is unbounded and re-flags untouched code that was never under review.
Two axes — conventions plus correctness & safety.
Conventions-only (sharper, more predictable output).
A code review that ignores bugs and safety isn't a code review. The convention overlay anchors the style axis; base craft carries the correctness axis. Keeping them in separate tables preserves the predictability a conventions-only pass would give.
Read-only and no verdict; findings only.
Let Baley emit an approve/block gate verdict.
Reviewer ≠ author and the human holds the approve gate (L3 core rules). An agent verdict would collapse that gate — exactly why /d101-review refuses one. Read-only is enforced by the tool budget (NF3), not left to prompt discipline.
Runs on Sonnet 4.6.
Opus for review.
Review is contract-bounded work — check a changeset against an overlay and against base craft — that runs on every PR; Sonnet's reasoning suffices and throughput matters (model-choice.md §2).
Named Baley (Asimov canon — the detective who verifies).
Role-only name (e.g. code-reviewer).
The repo is named Asimov and Baley was already reserved for the reviewer role (D101-build-subagents §4.3). Persona + role in one identifier (baley-the-code-reviewer) keeps identity and auto-delegation discoverability in one string.

6
Technical design
Where the agent lives, how it resolves a changeset and applies conventions at run-time, the files that change, the fixed values, how failures are handled, and the gotchas to watch.

§6.1Platform

Baley is a Claude Code subagent living in the agents/ directory in asimov-plugin — a markdown file with YAML frontmatter declaring model: claude-sonnet-4-6 and tools: Read, Grep, Glob, Bash. Bash is present only to run git (resolve the base, compute the diff); the absence of Edit/Write is what makes the agent read-only. The conventions it reads live in the consuming product repo under documentation/conventions/ — nothing about them ships in the plugin. No SQL, schema, or infrastructure change.

Read-only is structural. Read-only is not a prompt promise — it is the tool budget (NF3). If a future change needs Baley to edit, that is a different agent; do not add a mutating tool to this one without revisiting the reviewer ≠ author principle (§4.1).
Model-choice sync. The agent's model: frontmatter is paired with a row in documentation/model-choice.md in the same commit (hard rule 2).

§6.2Data flow

What happens from the moment Baley is invoked: it resolves the base and computes the diff, loads the convention overlays for the stacks the diff touches, walks the diff on both axes, and emits the report — marking a finding base-judgment or uncertain whenever its evidence runs out rather than asserting a breach.

Entry / resolve changeset Repo conventions (read) Judge / mark
1
Baley is invoked to review a branch in a product repo.
2
It resolves the changeset: the base branch (repo default or invoker override), then the base...HEAD diff and its file roster (R2, R3, R4).
3
It reads the convention overlay for each stack the diff touches — the entry README and every @-referenced file (R5, R6).
4
It walks the diff on both axes — conventions (cite the file) and correctness & safety (name the class) — assigning one severity per finding (R7, R8, R9).
5
Where evidence runs out it marks base-judgment (no covering convention, R10) or uncertain (defect depends on unchanged code, R11) instead of asserting. Then it emits the no-verdict report (R12).

§6.8Known constraints & gotchas

01
@-list is read, not auto-expanded
The Read tool does not transclude @-imports — that only fires in the CLAUDE.md memory chain. So an entry README is a read-list Baley loads file by file (Workflow), not a self-expanding index. Same constraint the build subagents carry.
02
Reviews only the diff
A bug in code the changeset doesn't touch is out of scope by design (R2). Baley is a changeset reviewer, not a whole-repo auditor; don't expect it to surface pre-existing issues in untouched files.
03
Base resolution depends on git
Shallow clones, a detached HEAD, or a missing remote can break merge-base. Baley falls back to main then master and states which base it used, so the reviewer can spot a wrong base.

§8Open questions

Q1 Allan Borup
Once the Spec stage lands, does the planned S102 validator subsume Baley, or do they coexist — Baley reviewing the changeset for conventions + correctness, the validator checking code against the S102's acceptance criteria? Resolution path: decide while spec'ing the validator subagent.
Q2 Allan Borup
Should Baley's report be posted onto the PR by an external poster, or stay in chat? Default for now is chat only (OOS4). Resolution path: tied to D100 §10 Q5; decide when the first PR-integration need appears.
Q3 Allan Borup
Does the single unified reviewer stay readable on large multi-stack diffs, or does report noise eventually justify splitting per stack (the alternative rejected in §4.5)? Resolution path: revisit if noise shows up in real use; decide after the first stretch of real reviews.
