# D100 — Asimov Architecture

Architecture of the `asimov` repo — the tool-agnostic toolkit that ships the L3 workflow's AI-assisted stages to **Claude Code and Codex**. One tool-neutral source tree is generated by CI into a plugin per tool, published through each tool's own marketplace mechanism, with identical capability on both sides. Design: [`features/D101-agnostic-toolkit-codex-support.html`](features/D101-agnostic-toolkit-codex-support.html).

## 2. Purpose & audience

**Purpose.** Describe the toolkit as a system: which components exist, how they're packaged, how they reach developers, and the architectural patterns they share. A developer (human or AI) reading this doc should be able to orient before touching any specific command, subagent, definition, or template.

**Primary audience.** Context& developers maintaining the toolkit, and developers using it in product repos.

**Secondary audience.** Architects deciding how the toolkit evolves; AI Transition reviewers tracking toolkit readiness.

## 3. System context

The toolkit sits inside the L3 workflow defined in the *AI Transition — Levels & Zones* framework (the part Asimov uses is summarised in [`ai-transition-levels-and-zones.md`](ai-transition-levels-and-zones.md)) — specifically, teams making the workflow change to **L3 on Zone 2**. The L3 pipeline has nine stages — *Intent → Design → Spec → Code → Review → Test → Approve → Deploy → Observe*.

The toolkit covers the **AI-assisted** portion of the pipeline — Design, Spec, Code, Review, and Test. Each stage maps to a tool: **Design** → the `/d101-*` commands; **Spec** → the planned `/s101-*` commands; **Code** → the build subagents (Giskard and Daneel write production code, Calvin authors the tests); **Review** → the reviewer subagent (Baley, conventions + correctness on the diff); **Test** → the planned validator subagent, which validates the built code against the spec (*"Agent vs Spec"*). See §4.4. Intent is captured upstream (e.g. Jira). Approve is the human gate. Deploy and Observe live in existing CI/CD and monitoring.

At L3 the unit of work shifts from a line (L2) to a whole spec, and the human role from **maker** to **director and reviewer**.

The toolkit does **not** enforce the L3 process — that lives in product repos. It gives the developer the right command at each AI-assisted stage; the surrounding process rests on four rules, enforced in product repos via PR settings and Copilot instructions, not by the toolkit:

- **Reviewer ≠ author** — nobody approves their own design, spec, or code.
- **No phase starts until the previous one is approved** — above all, coding does not start until the spec is approved (the spec-before-code gate).
- **Copilot reviews before any human reviewer** — automated review runs first; its findings are in front of the human when they open the artifact.
- **A gap found in a later phase is a bug in an earlier one** — fix the earlier artifact and re-run the phase; don't paper over it.

## 4. Components

The toolkit is authored once, in a **tool-neutral source tree** (`source/`), and generated by CI into a plugin per supported tool. Six kinds of **component** live in the source; the generated trees are derived output, committed by CI onto release tags and never hand-edited.

> **Terminology.** A *component* is a part of the toolkit itself — a marketplace manifest, a plugin, a slash command, a subagent, a skill, a definition or template, the generator — whether in its neutral source form or in a generated tree. An *artifact* is something the toolkit writes into a product repo — a D101, a persona review skill, the `asimov.md` context file — and is what the `source/artifacts/` folder (§4.5) is organised around. The two words are not interchanged in this document.

**The source → publish flow** (the full contract is the D101's §6): a developer commits neutral source only and opens a PR; the PR gate generates twice and byte-compares the runs (determinism) and refuses generated files in the tracked diff; on merge, the release workflow regenerates, compares against the previous release (the `latest` tag), and — only when the generated trees actually changed — stamps the next sequential version, commits the generated trees **off-main** (main is protected; the generated trees are gitignored there), tags `N.0.0`, moves the rolling `latest` pointer both marketplaces track, and publishes a release. Byte-identical output publishes nothing, and nothing is ever pushed to main — the pipeline cannot retrigger itself.

### 4.1 Marketplaces

Two marketplace manifests, one per tool, both declaring the single plugin for their tool:

| Tool | Manifest | Plugin entry |
|---|---|---|
| Claude Code | `.claude-plugin/marketplace.json` (hand-maintained) | `asimov-plugin` |
| Codex | `.agents/plugins/marketplace.json` (generated) | `asimov-plugin-codex` |

Marketplace name in both: `asimov-marketplace`.

Alternatives considered (the single-plugin shape, unchanged by the two-tool restructure):

| Option | Rejected because |
|---|---|
| Multiple plugins, one per pipeline stage (`asimov-design`, `asimov-spec`, …) | Fragments the unit-of-update; developers would install 4–5 separate plugins and update each. The L3 workflow is a single contract — splitting it across plugins breaks that. |
| Per-feature plugins (one plugin per slash command) | Overkill for the handful of components the toolkit ships. Adds manifest overhead with no separation benefit. |
| Multiple marketplaces (per team or per pipeline stage) | Same fragmentation cost as multiple plugins, plus extra install steps. |
| One tool's format as the source, translated to the other | Privileges one tool and lets its idioms seep into the source; the neutral source keeps every tool a target (D101 §4.5). |

### 4.2 The plugins

One **generated** plugin per tool, each exposing every command, subagent and skill the toolkit publishes:

- `plugins/asimov-plugin/` — the Claude Code plugin (`.claude-plugin/plugin.json`). Kept at its historical path so existing installs survive the restructure.
- `plugins/asimov-plugin-codex/` — the Codex plugin (`.codex-plugin/plugin.json`).

Developers install once in their own tool; commands, subagents and the shipped skills (§4.5, §4.6) become available across all product repos. Both trees are generated output, **gitignored on main and committed only onto release tags** by the release workflow: a change is made in `source/` and regenerated, never typed into a plugin file (D101 §4.4 rule 1 — the PR gate enforces it). Locally they exist after a generator run.

### 4.3 Slash commands

Developer-driven entrypoints. Each is authored as one markdown file under `source/commands/` with neutral frontmatter declaring a **tier** (small | medium | large) and an **effort** — never a concrete model name (§7.3). The generator emits each command as a skill (`skills/<name>/SKILL.md`) in **both** plugin trees — both vendors converged on the SKILL.md standard — so the invocation name is the same in either tool. Per-command design lives in `features/D101-<feature>.html`.

| Command | Stage | Tier / effort | D101 |
|---|---|---|---|
| `/d101-feature-design` | Design | large / xhigh | [`D101-d101-feature-design.html`](features/D101-d101-feature-design.html) |
| `/d101-review` | Design | medium / medium | [`D101-d101-review.html`](features/D101-d101-review.html) |
| `/d101-convert-to-html` | Design | medium / medium | [`D101-d101-convert-to-html.html`](features/D101-d101-convert-to-html.html) |
| `/asimov-init` | Setup (ad-hoc) | large / high | [`D101-asimov-init.html`](features/D101-asimov-init.html) |
| `/persona-new` | Design | large / high | [`D101-personas.html`](features/D101-personas.html) |
| `/persona-list` | Design | small / medium | [`D101-personas.html`](features/D101-personas.html) |
| `/s101-implementation-spec` *(planned)* | Spec | large / xhigh | — |
| `/s101-review` *(planned)* | Spec | medium / medium | — |
| `/conventions-check` *(planned)* | Review + Test | medium or small | — |

Command source paths follow the pattern `source/commands/<command-name>.md`. Every command body opens with a generated **model-check preamble**: it compares the running model against the command's designated tier via the mapping table's ranks and alerts — downward only, never blocking — when the session runs below designation (D101 §6.4.5).

**`/d101-feature-design` runs in three phases with a stop in the middle.** Phase A settles requirements (§2, §3) and writes nothing. Phase B settles the business design (§4, §5 UI Design, §8, §9), writes the file with the document phase marked `Business design`, §6 *declared open* and §7 Implementation *pending*, and **stops the run**. Phase C — the technical design plus the build recipe (§6, §7 Implementation, §10) — is reachable only in a *later* invocation against a file already at `Business design`, and flips it to `Full design`. §7 Implementation is the code-grounded recipe realising the §6 contracts; it sits **outside the two bars** (`d101-feature-design-definition.md` §4.8) and is the interim home for build-readiness notes until the Spec stage (S101) exists (§9).

The stop is deliberate and is the command's main design decision. Settling the mechanism before the business shape holds anchors the design to whatever was convenient to build, and a business design the developer has only seen as chat is a business design they have not read. Both axes are visible in the rendered document: **phase** (`Business design` → `Full design`, the author's call) and **status** (`Draft` → `Approved`, the business approver's). See `d101-feature-design-definition.md` §2.

**`/d101-review` is the review hub, not only the gap check.** It resolves the phase from the file, then offers the reviews that phase calls for and runs the ones the developer picks: the **gap review** against the matching bar (§8a or §8b, so a deliberately open §6 reads as *open*, not a failure — the command runs this itself); the **business-persona review** of §2/§4; and the **technical-persona review** of §4 (and §6 once written). The two persona reviews are **delegated to the persona skills** (§7.2 / `D101-personas.html`), which the command discovers and sorts into a business or a technical bucket by whether each reader declares it knows the mechanism (`persona-review-definition.md` §7). The hub reads the status axis for context but moves neither axis. See `D101-d101-review.html`.

**Review findings survive the session that produced them.** `/d101-review` writes a sibling `D101-<slug>.review.md` — every finding it just emitted to chat, plus a fingerprint of the D101 (its meta-strip date, phase and status) at review time. A later `/d101-feature-design` run reads it, offers it as input if the fingerprint still matches (naming the discrepancy if it doesn't), folds each finding in the way a chat comment would be, and deletes the file once that same run writes the D101. The file is a disposable cache, never a record: it carries no state a re-run of the stateless gap review couldn't reproduce, and it is gitignored at the standard `documentation/features/` location — never committed, never a review log. This is the one place `/d101-review` writes anything; `Write` was added to its tool grant for exactly this path, a scope enforced by prompt discipline (Claude Code's tool grant is not path-scoped) rather than a sandbox, stated as such in its hard rules. Design: `features/D101-review-handoff.html`.

`/conventions-check` is **ad-hoc** — invokable at any point in a session, not strictly tied to its Review + Test placement. Listed under Review + Test as its primary integration point, but developers can run it during Code or even Design phases when they want a convention check.

### 4.4 Subagents

Long-running, autonomous workers. Each is authored as one markdown file under `source/agents/`. The generator emits them per tool: for **Claude Code**, `agents/<name>.md` inside the plugin (as always); for **Codex**, one TOML per role (`name`, `description`, `developer_instructions`, `model`, `model_reasoning_effort`) — Codex plugins cannot carry agents, so the TOMLs ride in both plugin trees under `codex/agents/` and `/asimov-init` delivers them into a product repo's `.codex/agents/` (they update on bootstrap, not on plugin update — a known drift vector, D101 §6.8). The three build subagents and the reviewer exist; the S101 validator is planned but not built yet.

Subagent *kinds* follow the **Accelerate multi-agent roles** — *planner / builder / tester / reviewer* (the L3 multi-agent vocabulary; see [`ai-transition-levels-and-zones.md`](ai-transition-levels-and-zones.md)). Two roles ship today: **build subagents** (builders + tester — they produce code and tests) and the **reviewer** (it checks the changeset). *Planner* is reserved (architect/spec roles, not built).

| Subagent | Accelerate role | Stage | Tier / effort | D101 |
|---|---|---|---|---|
| `giskard-the-dotnet-developer` (.NET developer) | Builder | Code | medium / medium | [`D101-build-subagents.html`](features/D101-build-subagents.html) |
| `giskard-the-dotnet-developer-small` (.NET developer, small twin — pilot) | Builder | Code | small / medium | [`D101-build-subagents.html`](features/D101-build-subagents.html) §4.4 |
| `daneel-the-angular-developer` (Angular developer) | Builder | Code | medium / medium | [`D101-build-subagents.html`](features/D101-build-subagents.html) |
| `calvin-the-test-author` (test author) | Tester | Code | medium / medium | [`D101-build-subagents.html`](features/D101-build-subagents.html) |
| `baley-the-code-reviewer` (code reviewer) | Reviewer | Review | medium / medium | [`D101-baley-the-code-reviewer.html`](features/D101-baley-the-code-reviewer.html) |
| S101 validator *(planned)* | Tester | Test | medium / medium | — |

The three build subagents share one D101 because they are near-identical by design (the builders share Workflow + Output verbatim; the tester extends both with a branch-diff-scoped **Target**; otherwise only Role, Stack competence, and Boundaries differ); the reviewer is a distinct role (read-only, verdict-free, two-axis) and gets its own. The shared mechanism behind all of them lives in §7.2.1.

**Role vs. stage — note the split.** The *tester* role spans two pipeline stages: Calvin **authors** tests during **Code** (build time — writing a test is a build activity), while the planned validator **runs** that validation at the **Test** stage (the built code checked against the spec — *"Agent vs Spec"*). **Review** — conventions and correctness on the diff — is Baley's, and is distinct from the spec-validation at Test. So *who builds the tests* (Calvin, Code) is not *who validates* (the validator, Test).

Subagent source paths follow the pattern `source/agents/<subagent-name>.md`.

**A role may ship a small twin.** An agent source declaring `twin: small` is emitted twice — the default at its tier and `<name>-small` at the small tier — from the one prompt, differing only by a generator-injected scope guard (`source/agents/_scope-guard.md`) and description suffix. The orchestrator picks the twin only for a change that meets the written scope criteria (one production file, fully specified, no new abstraction, conventions cover it, one stack) and never overrides a model at delegation time; the twin hands back anything larger. Pilot: the .NET builder; Daneel and Calvin follow on evidence. Every Asimov agent that changes files signs its report with an `Asimov-Built-By: <agent> (<tool>, <model>, effort <effort>)` trailer, and the `asimov.md` delegation flow carries one line per party that changed files into the commit — Asimov agents, any ad-hoc agent the orchestrator spawned (`ad-hoc/<purpose>`, a recorded bypass), and the orchestrator's own inline edits — the evidence the pilot is judged on (D101-build-subagents v0.2 §4.4, §6.4, Q2).

### 4.5 Definitions and templates

Documents humans read; also read by slash commands and subagents at runtime. They are the cross-cutting **contracts** the rest of the toolkit aligns to — not features. Treated like a product repo's `documentation/conventions/` directory rather than like features. They are authored in `source/` and **copied verbatim into both plugin trees** by the generator — already tool-neutral, so they pass through unchanged; the commands read them from the installed plugin at run-time.

They are laid out **per artifact, not per file kind**: an *artifact* is something the toolkit writes into a product repo, and its folder `source/artifacts/<landing-place>/<artifact-slug>/` holds the definition and the template side by side, grouped by where the artifact lands (a D101 lands in the product repo's `documentation/`, so its folder is `source/artifacts/documentation/d101-feature-design/`). Building blocks that several artifacts draw on but that are not artifacts themselves — the diagram notations — live in `source/resources/`. A persona review skill lands in the product repo's skills folder, so its pair sits in `source/artifacts/skills/persona-review/`; the `/asimov-init` outputs sit under `source/artifacts/documentation/site/`, `source/artifacts/documentation/conventions/` and `source/artifacts/root/asimov-md/` by the same rule. The generator copies both trees verbatim into each plugin under the same relative paths (`artifacts/`, `resources/`), which is where the commands read them at run-time through `{{plugin-root}}`. The mapping tables (§7.3) are the one contract that is *not* an artifact: no command reads them at run-time — the generator does — so they live in `source/mappings/`, outside the artifact tree.

**A rule can be declined on the record.** `d101-feature-design-definition.md` §4.9 defines an **accepted deviation**: a decision that one named rule of the definition is deliberately not met at one named place in a D101, written *into that D101* next to the element it excuses and carrying the rule, a one-sentence reason, the accepter's name and the date. It exists because a review that re-reports a settled finding spends the author's decision on every run, and the signal decays. Three limits keep it from becoming a waiver system: it covers one rule *instance* and never a §8 check, it never stops the finding being reported (`/d101-review` prints it as the severity **Accepted**, which never resolves to Pass), and it lapses when the text it annotates is rewritten. Deliberately **not** a side file — a waiver keyed to a requirement number rots when numbering moves, and it hides the deviation from the human reviewer who owns the gap-free verdict. The mechanism spans `d101-feature-design-definition.md` §4.9/§7/§8, the D101 template, and both D101 commands; its design is `features/D101-accepted-deviations.html`.

**Every artifact carries a maturity level.** The *Maturity* column mirrors the YAML block (`artifact`, `maturity`, `since`) at the top of each artifact's definition. Levels are the Technology Radar rings — `assess` → `trial` → `adopt`, plus `hold` — and move on evidence of use by someone other than the author, never on time. The producing command reads the block from the installed plugin — in either tool — and prints the level as one chat line before its first question; it never changes it. Rows marked — are not artifacts (the mapping tables, the shipped persona skills, a resource). Design: `documentation/features/D101-artifact-maturity.html`.

**Personas are a fourth reviewer, in two kinds.** `/d101-review` judges a D101 against its bar; Baley judges a code diff against conventions and correctness; a **persona review** judges a design document against *a reader* — a named audience — and reports where the document forfeits its own review (the reader skims and rubber-stamps). It is the concrete form of `/d101-review` check 7 — and `/d101-review` can run it: the hub offers the persona reviews alongside the gap check and delegates them to the persona skills (§4.3). Personas come in two kinds, both delivered as skills named `persona-<slug>`: **standard** — generic archetypes authored in `source/personas/` and emitted into both plugin trees, available on install; and **custom** — product-specific readers authored by `/persona-new` into the product repo's own skills folder, invokable in both tools. Generic archetypes carry no product entity, so they may travel with the toolkit; a concrete reader is a product entity (§8.4, hard rule 8), so it stays local. `/persona-list` lists both. The `persona-` prefix is the namespace (skill discovery is flat — a folder can't group them). See `persona-review-definition.md` and the design `features/D101-personas.html`.

### 4.6 Skills

Model-invoked capabilities: a `skills/<name>/SKILL.md` in each plugin tree, discovered automatically on install and activated by the model when a task matches the skill's `description`. Two kinds ship. The **standard persona review skills** are authored in `source/personas/` (§4.5). **Advisory skills** answer questions from a body of reference material shipped in the plugin, rather than performing an action; they are authored in `source/skills/<name>.md` — the same neutral shape as a command (`name`, `description`, `tier` + `effort`; `{{plugin-root}}` in the body) minus `argument-hint` and the model-check preamble, since nobody types them — and emitted into both plugin trees like every other component (Claude Code's frontmatter carries the mapped model, Codex's carries none).

| Skill | Kind | Source | Purpose |
|---|---|---|---|
| `persona-poseidon`, `persona-athena`, `persona-hermes` | Persona review | `source/personas/` | Read a design document as one of its intended readers; the concrete form of `/d101-review` check 7. Their definition + template pair lives in `source/artifacts/skills/persona-review/` (§4.5). |
| `pm-advisor` | Advisory | `source/skills/pm-advisor.md` (medium / medium) | Advises on the delivery model held in `source/processes/`, shipped as `processes/` in both plugin trees. Carries an intent → file routing table, reads the relevant page at run time, and advises from it. Read-only: it never writes, and never edits `processes/` (a generated export). First member of a planned `pm-*` family; the family's shared D101 is not yet written. |

The `processes/` corpus `pm-advisor` reads is exported from the Learn/Engineer/Deliver vault, not maintained here: `processes/README.md` is its meta-entry and carries the draft-status caveat; `processes/delivery-model-framework.md` is its map. The export lands in `source/processes/`, and the generator ships it verbatim into both plugin trees so the skill resolves it under `{{plugin-root}}/processes/` — `${CLAUDE_PLUGIN_ROOT}/processes/` in Claude Code, a skill-relative path in Codex.

## 6. Distribution & install

| Aspect | How it works |
|---|---|
| Repo | Public GitHub repo `asimov` under the `context-and-oss` org, MIT-licensed, owned by Context&. |
| Install (Claude Code) | `/plugin marketplace add context-and-oss/asimov` once per developer; Claude Code reads `.claude-plugin/marketplace.json` from the default branch, whose plugin entry points at the `latest` tag; then `/plugin install asimov-plugin`. |
| Install (Codex) | Codex's plugin marketplace mechanism against the same repo; it reads `.agents/plugins/marketplace.json` and installs `asimov-plugin-codex`. |
| Update | Each tool's own marketplace-update command refreshes the local cache to the newest release. No auto-update — releases are announced on the GitHub releases page. |
| Auth | None for the public repo — the tools' existing GitHub access suffices; no tokens or secrets. Local development installs from a clone (`/plugin marketplace add <path-to-clone>`) after the generator has produced the plugin trees. |
| Versioning | Sequential semver-major tags (`1.0.0`, `2.0.0`, …; the tag equals the plugin version), created **automatically by the release workflow on every merge to main that changes the generated output** — unchanged output publishes nothing. The rolling `latest` tag is what both marketplaces track; main carries source only. Any release may change a bar or a template, so read the release notes before updating a repo with designs in flight. |
| Codex subagents | Not marketplace-served: `/asimov-init` copies the agent TOMLs from the installed plugin into the product repo's `.codex/agents/` (§4.4). |

There is no production deployment to provision — the toolkit is a developer tool consumed by Claude Code and Codex, not a runtime service. Model hosting (e.g. Codex against Microsoft Foundry) is each developer's machine configuration, outside the toolkit's scope.

## 7. Architectural patterns

### 7.1 Slash command shape

A command is one neutral markdown file (`source/commands/<name>.md`) with YAML frontmatter + prompt body:

- **Frontmatter** declares `name`, `description`, `argument-hint`, **`tier` + `effort`** (both required — a missing designation fails generation), and any tool hints (`allowed-tools`) that pass through where a target supports them.
- **Body** is the prompt, with tool-specific references written as tokens (`{{plugin-root}}`, `{{model-check}}`) the generator substitutes per target, and shared prose pulled in as **fragments** (`source/commands/_<name>.md` → `{{<name>}}`, identical in both targets — e.g. `{{file-io}}`, the UTF-8 rule every command carries as its first hard rule).

The generator emits the command as `skills/<name>/SKILL.md` in both plugin trees: the Claude Code emission carries the resolved `model` (+ `effort` where mapped); the Codex emission carries **no** model fields, because Codex silently ignores them in skill frontmatter — there the designation reaches the reader only through the generated model-check preamble. The exact prompt text and interview heuristics are implementation detail; they live in the source file itself and are designed against the relevant `features/D101-<feature>.html`.

### 7.2 Subagent shape

A subagent is a markdown file under `agents/` with frontmatter that declares model and, where the role needs it narrowed, a tool budget (today only the reviewer does; the builders and the tester inherit the full set). Subagents differ from slash commands in two ways:
- **No human in the loop during execution.** A slash command interviews; a subagent runs to completion and returns a report.
- **Output contract is explicit.** Subagents emit either code/tests (build subagents) or a structured finding report (the reviewer, and the planned validator).

#### 7.2.1 The convention-overlay mechanism (shared)

All the shipped subagents share one mechanism; this subsection is its canonical description, referenced by the per-feature D101s instead of being re-derived in each (hard rule 3).

- **Reusable core, local overlay.** Each subagent carries repo-independent *base info* following a shared six-field skeleton — **Role, Stack competence, Reads, Workflow, Boundaries, Output** — that travels with the plugin. The active product repo's conventions are a local overlay loaded at run-time, applied on top of the base.
- **One canonical entry file per stack, by exact path.** A subagent reads `documentation/conventions/<stack>/README.md` (e.g. `dotnet/`, `angular/`, `test/`). That README `@`-references every convention file in its stack; the subagent reads each referenced file itself — the Read tool does **not** auto-expand `@`-imports, so the README is a load-bearing read-list, not a transclusion. A convention file the README doesn't reference is invisible.
- **Flag, don't guess.** Where a convention is missing (**gap**), the subagent proceeds on base competence and flags the uncovered choice. Where the task contradicts a convention (**conflict**), it stops and flags rather than silently picking a side. Each non-trivial decision **cites** the convention file that backed it.
- **Asimov-canon personas mapped to Accelerate roles.** Subagent *kinds* follow the Accelerate multi-agent roles — *planner / builder / tester / reviewer* (see §4.4). The persona names are Isaac Asimov canon; the file name combines persona + role (`giskard-the-dotnet-developer`) so identity and auto-delegation discoverability live in one identifier.

Two subagents add a **Target** field on top of this base — the changeset they work on, a branch-vs-base diff: the **tester** (Calvin) authors tests only for what the diff touched, and the **reviewer** (Baley) reviews only what it touched. The reviewer further differs in a way no build subagent does: it is **read-only and verdict-free** (it reports findings; it never edits code or approves it — reviewer ≠ author, §3). The shared overlay-reading and flag-don't-guess behaviour is otherwise identical.

### 7.3 Tier-declared models, resolved by the mapping tables

Every command and subagent declares an abstract **tier** (small | medium | large) and an **effort** in its source frontmatter — never a concrete model name. One mapping table per tool (`source/mappings/claude-code.md`, `source/mappings/codex.md`) resolves tier → model, translates the effort vocabulary explicitly (Claude Code runs low–max, Codex low–ultra), and carries the **rank** rows the downward-only mismatch alert reads. Four consequences:

- **Concrete model names live in exactly one place per tool.** A model upgrade is one row changed, a regeneration, and a test of the affected commands in both tools — the upgrade ritual in each table's header.
- **The generated component is the runtime source of truth**, and it cannot drift from the table, because the generator writes it from the table on every run — the sync discipline the old `model-choice.md` needed is now structural.
- **Developers pick the right command for the work; the designation picks the model.** Where a tool cannot honour it (Codex skill frontmatter), the model-check preamble still tells the developer what the designation is.
- **Two designations per role come by twin, never by override.** Where a smaller model should take the simple cases, the role ships a generated small twin with its own fixed designation and a scope rule, and the orchestrator chooses the *agent* by written criteria (§4.4). Overriding a model at delegation time is forbidden in `asimov.md`: it bypasses the mapping table in Claude Code and, in Codex, is possible only by leaving the TOML's model unset — which would silently fall back to the parent's model.

### 7.4 Definitions and templates as contract

The definitions and templates under `source/artifacts/` — shipped verbatim into both plugin trees as `artifacts/` — are read both by humans and by commands. Commands embed the relevant document by reference at run-time, not as a frozen copy in the prompt — so updating `d101-feature-design-definition.md` or `s101-implementation-spec-definition.md` immediately changes the bar every command applies. Same for the D101/S101 templates.

This is the analogue of a product repo's `conventions/` — the standard everything in the codebase aligns to. The pattern: one canonical doc, many consumers, change in one place.

### 7.5 Repo-scoped output

Commands write into the **active product repo's working tree**, not into the toolkit repo. `/d101-feature-design` produces `documentation/features/D101-<slug>.html` in whichever product repo the developer is currently working in — once at the end of its business-design phase, again at the end of its technical-design phase (§4.3). The toolkit itself is read-only from a runtime perspective.

## 8. Cross-cutting mechanisms

### 8.1 Model selection

Per §7.3. The toolkit declares tier + effort; the mapping tables resolve them; each tool dispatches its own resolved model (Claude Code from skill/agent frontmatter, Codex from the agent TOMLs).

### 8.2 Configuration & secrets

None per developer. No API keys, no environment variables, no per-repo wiring. The marketplace install is the only configuration touchpoint, and it uses the tool's existing GitHub credentials. The CI pipeline runs on the repository's own `GITHUB_TOKEN` — no extra secrets there either. A developer pointing Codex at Microsoft Foundry configures that in their own `~/.codex/config.toml`; that is machine configuration, not toolkit configuration.

### 8.3 Lifecycle independence

Toolkit updates flow via each tool's marketplace-update command, not by merging into product repos — the load-bearing reason the toolkit is a **separate repo**. Templates, slash commands, and subagent prompts move on their own cadence; bundling them into a product repo would drag every product release through every tooling iteration.

Releases are produced by the pipeline, not by hand: every merge to main that changes the generated output is automatically stamped, committed off-main onto a sequential tag (`N.0.0` + the rolling `latest`) and published; unchanged output publishes nothing, and main itself only ever carries source. One asymmetry to know: the Codex agent TOMLs in a product repo's `.codex/agents/` update only when `/asimov-init` is re-run there, not on plugin update (§4.4).

Alternatives considered: (a) co-locate the toolkit in a product repo's plugin folder — rejected because the toolkit serves multiple systems and tooling updates shouldn't churn any single product's release pipeline; (b) one toolkit repo per system — rejected because the L3 workflow is one contract across systems; per-system forks would diverge.

### 8.4 Reusability

Slash commands, subagents, definitions, and templates avoid baking in product-specific names beyond what is load-bearing — reusability across products and organisations is a goal, not a hope (§8.3). Path conventions (e.g. `documentation/features/`) are acceptable shared conventions; product entity names are not.

### 8.5 Failure modes (system-wide)

Failure modes specific to a single command or subagent live in that feature's D101. System-wide:

| Failure | Surface | Recovery |
|---|---|---|
| Marketplace add fails — no GitHub access | The tool reports the network or auth error | Developer checks that the tool can reach GitHub; the repo itself is public |
| Manifest typo (`marketplace.json` / `plugin.json`) breaks install | Install fails silently or with a generic schema error | The PR gate parses the hand-maintained Claude marketplace manifest and checks its plugin entry agrees with the generated plugin manifest (Q2); the Codex pair is generated from `toolkit.json`, so a defect there is a generator bug fixed in one place |
| PR gate's two generator runs differ | Merge blocked — the determinism defect is visible before anything publishes | Fix the generator's nondeterminism; the gate is the detection (D101 §6.7) |
| Generation fails on main | No commit, no release; the last published version keeps serving | Fix and re-run the workflow; nothing partial was published |
| A mapped model is retired or absent from the provider | The tool errors at invocation / delegation | One row in the affected mapping table + regeneration (the upgrade ritual, §7.3) |
| Hand-edit typed into a generated tree | On main nothing is tracked there, and the PR gate refuses generated files in a diff; a local edit is erased by the next regeneration | Make the change in `source/` instead (rule 1) |
| Template or definition file missing | Command fails partway, reports missing path | Update the command's reference path; the next merge publishes the fix |
| Stale install — change committed, developer hasn't updated | Old command behaviour | The tool's marketplace-update command; no auto-update by design |
| The tool itself unavailable | All commands fail | Developers fall back to writing D101/S101 by hand against the templates. No degraded mode in the plugins. |
