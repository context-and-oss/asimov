# Codex support without a generator — fase 0 probes

**Date:** 2026-09-29 · **Author:** cka (probes run by Claude Code on cka's machine; documentation read the same day) · **Status:** research input for the Codex-support D101 v2, which supersedes `D101-agnostic-toolkit-codex-support.html` v1.2 (a generator design the project decided not to adopt).

**Question this note answers:** what do Claude Code and Codex guarantee, today, for the shape "one plugin folder, methods in skills, thin agent shells per tool, no model names, no build step"? Every fact is marked **LIVE** (observed on this machine), **DOCS** (quoted from the official documentation or the open-source Codex code the same day) or **OPEN** (neither; needs a live test in the interactive tool).

Versions: Claude Code 2.1.281 · Codex CLI 0.155.1 (latest release that day: 0.158.0; features on this install: `plugins`, `hooks`, `multi_agent` stable-on; `multi_agent_v2` off; `plugin_hooks` listed as removed — plugin hooks are now part of `hooks`, see §3).

## 1. Verdict per design question

Custom prompts are deprecated. | DOCS (CC) · LIVE (Codex migration) |
| 4 | Can a skill be user-only (never the model's decision), as `/asimov-init` must be? | **Yes, in both.** Claude Code `disable-model-invocation: true` (still `/name`; the description leaves the model's context; **cannot be preloaded into a subagent**). | 6 | How do we "@" data into Codex? | **We don't; Codex does not expand `@`.** Claude Code gets `@asimov.md` from `CLAUDE.md`; Codex gets the same text inline in an `AGENTS.md` managed region (already designed in `/asimov-init`). Plugin-internal data goes by skill-relative path (row 5). Codex's `spawn_agent` policy also says spawning is allowed only when "the user or applicable AGENTS.md/skill instructions explicitly ask" — the delegation flow in `AGENTS.md` is what authorises it. | DOCS · LIVE (tool text) |
| 7 | How does a thin agent shell get its method in each tool? | **Claude Code:** `skills:` preload on the agent — a plugin agent preloads a plugin skill by its bare name, and the skill arrives with its base-directory note. **Codex:** a custom-agent TOML (`~/.codex/agents/` or a trusted repo's `.codex/agents/`) is spawned by the parent with `agent_type = "<name>"`; its `developer_instructions` tell it to invoke `$asimov-plugin:<role-skill>`, and it can (the role skill must be model-visible). The parent may also hand the skill over at spawn (`items: [{type: "skill", path: <SKILL.md>}]`). The TOML has no preload field. | LIVE (both) · DOCS |
| 8 | Can we guide the user through an update? | **Yes, from one plugin hook in both tools.** `hooks/hooks.json` is the documented plugin-hook file in *both* tools — Codex's hooks feature uses the same file shape, event names and JSON contract as Claude Code by OpenAI's design, so this is not Codex reading a Claude file but the one format both specify. The script must not lean on tool-specific environment variables (`CLAUDE_PLUGIN_ROOT` is set by Codex only "for compatibility"; `CLAUDE_PROJECT_DIR` is absent there): it locates the plugin root from its own file path and takes the working directory from the `cwd` field of the event both tools pass on stdin. Codex runs plugin hooks only after the user trusts them once in `/hooks`. | 9 | Does the plugin version matter without a release workflow? | **Yes.** Claude Code detects updates by the manifest `version` first: "If you set `"version": "1.0.0"` and push new commits without changing it, users don't receive them." Codex caches per version (`cache/<marketplace>/<plugin>/<version>/`, `local` for local sources). **Every merge that changes `plugins/asimov-plugin/**` must bump `version`** — a CI check, not a generator. | DOCS (CC) · LIVE (Codex cache) |

## 2. Claude Code — facts

Docs read 2026-09-29 under `https://code.claude.com/docs/en/`: `skills`, `sub-agents`, `plugins/*`, `hooks`, `hooks-guide`, `cli-reference`, `env-vars`.

**Skills.** All frontmatter optional; unknown fields ignored silently. `disable-model-invocation: true` = user-only (`/name` still works; "Also prevents the skill from being preloaded into subagents"). `user-invocable: false` = model-only. `argument-hint`, `$ARGUMENTS`/`$N`/named `arguments` work. `context: fork` + `agent` runs the body in a subagent (docs list built-ins and `.claude/agents/`; plugin agents OPEN). `model`/`effort` are per-turn overrides. `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}` are substituted in the body and in `allowed-tools`; none is in the Bash tool's environment. Plugin skill name: `/plugin:skill`, bare `/skill` unless taken. LIVE: `Base directory for this skill: …` is injected on load (docs do not promise it; `${CLAUDE_SKILL_DIR}` is the documented form).

**Commands.** "Custom commands have been merged into skills… Prefer a skill for new work." `commands/` still loads with the same frontmatter minus `name`/`paths`. Dropping `commands/` loses nothing.

**Subagents.** Fields: `name`, `description`, `tools`, `disallowedTools`, `model`, `maxTurns`, `skills`, `memory`, `background`, `omitClaudeMd`, `effort`, `isolation`, `color`, `experimental.cacheTtl`; plugin agents ignore `permissionMode`, `hooks`, `mcpServers`, `initialPrompt`. `model` omitted → per-invocation param → `CLAUDE_CODE_SUBAGENT_MODEL` → the main conversation's model. `skills:` preloads full content; a missing or user-only skill is skipped with a debug warning (LIVE: `Warning: Skill 'x' specified in frontmatter was not found`). LIVE: a plugin agent preloads a plugin skill by bare name (`Preloaded skill 'probe-skill'`). Non-`.md` files in `agents/` are ignored without a warning (LIVE: `Loaded 1 agents` with a `.toml` beside the `.md`; `claude plugin validate` passes).

**Hooks.** `hooks/hooks.json`; SessionStart stdout becomes model context; JSON `systemMessage` is shown to the user; `hookSpecificOutput.additionalContext`, `reloadSkills`; env `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA`, `CLAUDE_PROJECT_DIR`, `CLAUDE_ENV_FILE`. Hooks also run inside subagents, but a subagent does not see the parent's SessionStart context (LIVE). LIVE: a Node hook read `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` and the model quoted `ASIMOV-PROBE: plugin version 7.0.0, plugin root …, project …, event SessionStart`.

**Updating.** `claude plugin update <plugin>@<marketplace>`, `claude plugin marketplace update [name]`; in-session `/plugin marketplace update <name>`, `/reload-plugins` ("Apply pending plugin changes to the running session without restarting it"). Auto-update: "off for every other marketplace" than Anthropic's; the user can turn it on per marketplace in `/plugin`. Cache `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`; a local-directory marketplace is read in place (development path, no version bump needed). `--plugin-dir <path>` loads a plugin for one session and silently overrides an installed plugin of the same name (used for these probes).

**Non-interactive writes into `.claude/` (verification run).** `claude -p` with `--permission-mode acceptEdits` refused every write into `.claude/skills/` (a protected folder), while `.agents/skills/` was written; an interactive session prompts instead. A harness limit for automated tests, not a plugin defect.

**Tolerance.** Docs name no rule for unknown folders; only a root `CLAUDE.md` (warned) and `bin/` (special) are called out. LIVE: `.codex-plugin/plugin.json` and `agents/*.toml` inside the Claude plugin → validate passes, loader unaffected.

## 3. Codex — live facts (CLI 0.155.1)

- **Install.** `codex plugin marketplace add <SOURCE>` takes "a local path, owner/repo[@ref], HTTPS Git URL, or SSH Git URL" (`--ref`); `codex plugin marketplace upgrade [NAME]` refreshes Git snapshots; `codex plugin add PLUGIN@MARKETPLACE`; `codex plugin list [--json]`; `codex plugin remove`. Cache `~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/`.
- **Claude manifests are accepted as a fallback.** A repo with only `.claude-plugin/marketplace.json` (Claude's shape, `source: "./plugins/<dir>"`) and a plugin with only `.claude-plugin/plugin.json` installed as version 7.1.0 and served its skill (`$asimov-probe2:probe-skill`, path supplied, relative read, arguments verbatim). Useful to know; not the path to build on (row 1).
- **Precedence.** With both `.codex-plugin/plugin.json` (7.0.2) and `.claude-plugin/plugin.json` (7.0.0) present, Codex installed 7.0.2 — the Codex overlay wins.
- **Tolerance.** A plugin folder also containing `.claude-plugin/`, `agents/*.md`, `agents/*.toml`, `commands/`, `hooks/` installed without complaint.
- **Command migration.** Installing main's plugin (legacy manifest) produced `.codex-plugin/migrated-command-skills/source-command-persona-list/` only; the five commands above 4,000 bytes were dropped without a message. Re-probed against Codex's source 2026-09-30 (§8): the drop has two independent causes — `$ARGUMENTS` in the body and size — and the migrated skill is invoked as `$asimov-plugin:source-command-persona-list`, not `persona-list`.
- **Skill invocation.** `$asimov-probe:probe-skill "hello codex"` in the prompt invoked the namespaced plugin skill; Codex supplied `<path>…\skills\probe-skill\SKILL.md</path>`; `references/probe.txt` was read relative to it; the arguments arrived verbatim.
- **User-only skills.** `policy.allow_implicit_invocation: false` removed the skill from the model's list (also inside a spawned agent); explicit invocation unaffected. With `true`, sub-agents see and invoke it.
- **Skill roots seen.** Plugin cache; `~/.agents/skills/<name>` (user-level).
- **Custom agents.** A TOML in the repo's `.codex/agents/` was *not* loaded in an untrusted project (the model could list the file but `spawn_agent` offered no `agent_type`; a one-run `-c projects.<path>.trust_level="trusted"` override did not change that). The same TOML in `~/.codex/agents/` gave `spawn_agent` an `agent_type` parameter with `Available roles: probe-agent, default, explorer, worker`; the agent spawned by name, ran on the parent's model (`gpt-5.6-terra-eu`), and **invoked the visible plugin skill itself** (`$asimov-probe:probe-skill`, path + relative read + arguments). Passing the skill as a spawn item (`items: [{type: "skill", name, path}]`) also worked, with and without `agent_type`. Passing the agent name as `model` fails (`Unknown model 'probe-agent'`). `--enable multi_agent_v2` renames the tools to `collaboration.*` and adds `task_name`/`fork_turns`; no other change.
- **Plugin hook.** The plugin's Claude-format `hooks/hooks.json` SessionStart hook ran in Codex with `--dangerously-bypass-hook-trust` (`hook: SessionStart Completed`), with `CLAUDE_PLUGIN_ROOT` set to the cache path and `CLAUDE_PROJECT_DIR` unset; the model quoted the `ASIMOV-PROBE` line. Without the bypass it did not run (untrusted plugin hook).
- **`.codex/` is protected (verification run, 2026-09-29).** In a trusted repo with `-s workspace-write`, `codex exec` could write `asimov.md`, `AGENTS.md` and `documentation/index.html` but not `.codex/agents/*.toml` (`PermissionDenied … UnauthorizedAccessException`); the interactive TUI asks for approval instead. Delivering the shells from Codex is therefore an approved write. The files Codex wrote were valid UTF-8 without mojibake; `AGENTS.md` came out with CRLF line endings.
- **Windows.** Codex prefixes every PowerShell command with `[Console]::OutputEncoding = UTF8`; that fixes console output, not `Out-File`/`Set-Content` defaults. The UTF-8 file rule for writing skills stands.

## 4. Codex — documentation facts (learn.chatgpt.com/docs, developers.openai.com/plugins, openai/codex `main`)

- **Manifests.** Portable root `plugin.json` (Agent Plugins schema) is the recommended new format; `.codex-plugin/plugin.json` is the compatibility fallback; `.claude-plugin/plugin.json` and `.cursor-plugin/plugin.json` are discovered too. Legacy manifest fields: `name`, `version`, `description`, `keywords`, `skills`, `mcpServers`, `apps`, `hooks`, `interface{displayName, shortDescription, longDescription, developerName, category, capabilities, websiteURL, privacyPolicyURL, termsOfServiceURL, defaultPrompt, brandColor, composerIcon, logo, logoDark, screenshots}`, `extensions`; unknown fields ignored. Paths must start with `./` and stay inside the plugin.
- **What a plugin loads.** `skills/` (default), `.mcp.json`, `.app.json`, hooks (`hooks/hooks.json` or manifest `hooks`), `assets/`; `commands/` only via install-time migration (frontmatter `description` required, ≤ 4,000 bytes); **no `agents/` loader** — openai/codex #18988 "Allow plugins to bundle and register custom agents" is open with no maintainer reply.
- **Marketplace manifest.** Discovered names in order: `.agents/plugins/marketplace.json`, `.agents/plugins/api_marketplace.json`, `.claude-plugin/marketplace.json`, `.cursor-plugin/marketplace.json`. Entry `source`: plain `./path` string, or `{source: local|url|git-subdir|npm, …}` with `ref`/`sha`; relative paths resolve from the marketplace root; unresolvable entries are skipped. A repo marketplace is auto-discovered from cwd, its git root and `~`. Plugins are not available in the IDE extension.
- **Skills.** Codex reads `name`, `description`, `metadata.short-description` from SKILL.md; everything else is ignored. `agents/openai.yaml`: `interface.*`, `policy.allow_implicit_invocation` (default true), `dependencies.tools[]`. Invocation: `/skills` picker or `$` mention, namespaced `plugin:skill`; the model is told "Skills from this plugin are prefixed with `<plugin>:`". **No argument mechanism** — whatever else the user types is the input. Skill roots: `$CWD/.agents/skills` up to the repo root, `~/.agents/skills`, `/etc/codex/skills`, bundled, plugins (plus `~/.codex/skills` deprecated and a trusted project's `.codex/skills`). The skills list carries each skill's `SKILL.md` path; a selected skill is read in full. **Correction 2026-09-30:** the 8,000-byte truncation (`MAX_SKILL_PROMPT_BYTES`, `render.rs`) is applied in `host_prompt.rs` only when `is_agent_plugin_skill()` — skills of plugins in the portable Agent-Plugins manifest format (root `plugin.json` with `$schema`). Legacy `.codex-plugin` manifests inject the full file: Superpowers' `brainstorming/SKILL.md` in OpenAI's catalogue is 15 kB.
- **Custom agents.** Standalone TOML must define `name`, `description`, `developer_instructions`; any `config.toml` key may be added (`model`, `model_reasoning_effort`, `sandbox_mode`, `mcp_servers`, `skills.config`…); malformed files are dropped with a warning. Locations: `~/.codex/agents/` (user) and `.codex/agents/` (**trusted** project), recursively; or `[agents.<name>] config_file = …`. Resolution: file value wins; else spawn value → `[agents]` default → parent; `sandbox_mode`, `mcp_servers`, `skills.config` inherit when omitted. No preload/invoke field — `[[skills.config]]` only enables/disables a skill by path. The parent spawns with `agent_type = "<name>"`; roles are advertised in the tool description. Open bugs: #26408 (project-scoped role advertised but not spawnable; one cause fixed in #26599, a stale-roles cause reported), #40131 (symlinked role files). `/import` converts Claude agents to TOML, mapping `effort` → `model_reasoning_effort` and `permissionMode` → `sandbox_mode`, **dropping `model`**.
- **Hooks.** On by default. Sources: `~/.codex/hooks.json`, `~/.codex/config.toml [hooks]`, `<repo>/.codex/hooks.json` and `.codex/config.toml` (trusted), managed `requirements.toml`, and plugins (`hooks/hooks.json` or manifest `hooks`). "Installing or enabling a plugin doesn't automatically trust its hooks; Codex skips plugin-bundled hooks until you review and trust the current hook definition" (`/hooks`). Events: `PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, SessionStart, SessionEnd, UserPromptSubmit, SubagentStart, SubagentStop, Stop, Interrupt`. Same JSON contract as Claude Code (`systemMessage` "surfaced as a warning in the UI", `hookSpecificOutput.additionalContext`, exit 2 + stderr); `command` and `mcp_tool` handlers run, `prompt`/`agent` handlers are skipped; `commandWindows` override; `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` set for compatibility.
- **Updating.** `codex plugin marketplace upgrade [NAME]` refreshes Git marketplace snapshots (also run by a startup thread when plugins are enabled — source, undocumented); no per-plugin update command (`add | list | marketplace | remove` only); new skills appear in a new session. `codex plugin list --json` exposes `pluginId, name, marketplaceName, version, installed, enabled, source, installedPath`. How a `local`-source cache copy is refreshed from the CLI is undocumented (remove + add works).
- **Custom prompts.** Deprecated (`/prompts:<name>`, `$1..$9`, `$ARGUMENTS`); replacement: skills.
- **Windows.** Native PowerShell (`pwsh` → Windows PowerShell → `cmd.exe`), `-NoProfile -Command`; UTF-8 console prefix only; no guidance on file encoding.
- **Models.** Documented today: `gpt-6-sol` (start here, effort `medium`), `gpt-6-luna` (fast, `high`), `gpt-6-astra` (`low`); `gpt-5.6` Sol/Terra/Luna "remain available during the rollout"; `gpt-5.5` retires from Codex 2026-10-14. Effort vocabulary `low | medium | high | xhigh | max | ultra`, model-dependent. An organisation's provider catalog may lag (this machine: `gpt-5.6-*-eu` only) — one more reason the toolkit should not name models.

## 5. What this means for the design (input to D101 v2)

1. **One folder, one manifest per tool, no build step — the Superpowers layout.** `plugins/asimov-plugin` keeps `.claude-plugin/plugin.json` and gains a small `.codex-plugin/plugin.json` (`name`, `version`, `description`, `skills: "./skills/"`, `hooks`, optional `interface`); the repo root keeps `.claude-plugin/marketplace.json` and gains `.agents/plugins/marketplace.json` (`source: "./plugins/asimov-plugin"`). Both pairs are hand-written and tiny. CI checks that the two plugin manifests agree on `name`/`version`/`description`, that both marketplace entries name the same plugin and path, and that `version` changed whenever `plugins/asimov-plugin/**` changed (row 9).
2. **Skills are the only shared layer.** Every user-facing command becomes a skill; `commands/` is retired (Codex migrates only a command without `$ARGUMENTS`, `{{ }}` or `@file` that renders under 4 kB — one of main's six, §8). `/asimov-init` and `/asimov-update` are user-only in both tools (row 4). Role skills stay model-visible — a user-only skill cannot be preloaded (Claude Code) or invoked by a sub-agent (Codex) — so "only via the shell" is prose in `asimov.md`/`AGENTS.md`, not a flag. Codex passes no arguments to skills, so a conversation skill states that its target (a D101 path, a persona name) is whatever the prompt names, and asks when the prompt names none; Claude Code's `$ARGUMENTS` then just arrives as part of the prompt. Not a functional loss.
3. **Skill-relative paths replace `${CLAUDE_PLUGIN_ROOT}`; the 8 kB cap is a watch item.** Shared artefacts stay under `artifacts/` and are referenced from a skill as `../../artifacts/…`, which both tools resolve from the base directory they supply. Codex truncates a SKILL.md at 8,000 bytes **for plugins in its portable Agent-Plugins manifest format** (corrected 2026-09-30, see §4); with a legacy `.codex-plugin` manifest the full file is injected, and files the skill then reads with tools are never truncated. Eight skills are above the cap once the six commands are skills too (the five writing entry points, the two `artifact-*` skills, `role-code-reviewer`; sizes in D101-codex-support §6.8), so they would be cut if the plugin ever moved to the portable format. Decision 2026-09-30 (cka): skills stay single-file; the split is taken if and when the plugin adopts the portable format. CLAUDE.md hard rule 11 records the cap as a watch item.
4. **Agents inherit the session model.** Remove `model:` from the `.md` shells; TOML shells stay model-less. A deliberate pin is a separate shell (or a spawn-time override the orchestrator is told to make).
5. **Codex agents: TOML shells, spawned by name.** Each `agents/<name>.md` gets a sibling `agents/<name>.toml` in the plugin (ignored by both loaders) whose `developer_instructions` say "invoke `$asimov-plugin:<role-skill>` first". `/asimov-init` copies the TOMLs into the product repo's `.codex/agents/` (trusted project) and `/asimov-update` refreshes them; the orchestrator spawns with `agent_type`, authorised by the delegation flow in `AGENTS.md`. Fallback the flow can name: spawn a generic agent with the role skill as a `skill` item (works without any TOML). Baley's read-only: `sandbox_mode = "read-only"` in its TOML (DOCS).
6. **Update guidance from one hook — deferred (cka, 2026-09-29: all hook work waits; backlog).** For this task the guidance lives in the README and in `/asimov-update`'s own output; the hook below is the recorded design for later. A plugin `SessionStart` hook (`hooks/hooks.json`, the plugin-hook format both tools document; a Node script that finds the plugin root from its own path and the repo from the event's `cwd`, no tool-specific variables) compares `plugin.json` version with the stamp `/asimov-init` writes into `asimov.md` and prints the three steps for the tool it runs in: (1) update the plugin — Claude Code `/plugin marketplace update asimov-marketplace`, Codex `codex plugin marketplace upgrade asimov-marketplace`; (2) `/asimov-update`; (3) Claude Code `/reload-plugins` or a new session, Codex a new session. In Codex the hook runs only after the user trusts it once in `/hooks`; `/asimov-init` says so. `/asimov-update` prints the same guidance itself.
7. **Windows/Codex writes are PowerShell writes.** The UTF-8 file rule goes into every skill that writes files.
8. **Personas in Codex.** Codex reads repo skills from `.agents/skills/`, Claude Code from `.claude/skills/`. `/persona-new` writes the same skill to both folders (cka, 2026-09-29); `/persona-list` reports a pair that has drifted, and `/asimov-update` can re-sync from the Claude copy.

## 8. Re-probe 2026-09-30 — asking Codex to run main's commands

Question from the review of PR #18: is it correctly understood that Codex does not support commands, and what happens when someone tries to run one? Setup: main's plugin (77e2283) installed **unchanged** — `commands/`, `agents/`, `skills/`, Claude manifest only — from a local marketplace into Codex CLI 0.155.1; a throwaway .NET repo; `codex exec`, approval never, repo reset between runs. Every earlier Asimov install was removed first: the first attempt had been answered by the generator-era `asimov-plugin-codex` still installed from an old test marketplace — when `$asimov-plugin:asimov-init` resolved to nothing, the model ran *that* plugin's `asimov-init` skill instead. Probe logs: `cmdprobe-*.log` in the session scratchpad.

**The rule, from the source** (`codex-rs/core-plugins/src/command_migration.rs` and `command_migration/plugin.rs` on `main`): at install, a `commands/*.md` becomes a skill named `source-command-<name>` if it has a frontmatter `description`, the name is at most 64 characters, the body contains none of `$ARGUMENTS`, a `$1`-style placeholder, `{{…}}`, a `!\`` shell injection or an `@file` reference, and the rendered skill is at most 4,000 bytes (`MAX_MIGRATED_COMMAND_SKILL_BYTES`). Anything else is skipped with a bare `continue` — no log line, no message. Of main's six commands, five carry `$ARGUMENTS` (and run 8–30 kB); `persona-list` carries none and is 3.4 kB. The migrated file keeps the body verbatim under a *Command Template* heading, `${CLAUDE_PLUGIN_ROOT}` included — Codex substitutes nothing.

**Install result:** `.codex-plugin/migrated-command-skills/source-command-persona-list/SKILL.md` — and nothing else from `commands/`.

| # | Prompt | Codex | The model | Outcome |
|---|---|---|---|---|
| 1 | list the plugin's skills | ten skills plus `source-command-persona-list` | — | no `asimov-init`, `d101-*` or `persona-new` exists |
| 2 | `$asimov-plugin:asimov-init` | no such skill; **no error** — the text is handed to the model | "Investigating missing skills": listed the plugin cache (its path is visible in the skill list), found `commands/asimov-init.md`, read it with PowerShell and followed it | a correct write plan (main's version: `CLAUDE.md` only), stopped for `yes`; nothing written |
| 3 | `/asimov-init` | same | found and read the same file, then only announced what it would do | one sentence, no plan |
| 4 | "Run the Asimov setup command asimov-init" | same | looked for a CLI | *"not installed or available on this system's PATH"* |
| 5 | `$asimov-plugin:persona-list` | no such skill (the migrated one is `source-command-persona-list`) | read the migrated skill and the persona skills from the cache | correct roster |
| 6 | `$asimov-plugin:d101-review` | no such skill | read `artifact-d101-gap-review` and `commands/d101-review.md` from the cache | correct opening ("no D101 candidates") |
| 7 | `$asimov-plugin:source-command-persona-list` | the migrated skill | followed it | correct roster |

**Reading.** Codex supports no commands, and it raises no error for a missing one. What looked like support is the model rummaging in the plugin cache, whose path the skill list reveals: it varies run to run (2 vs 3 vs 4), fails without a message, and hands the model Claude-specific text — `$ARGUMENTS`, `${CLAUDE_PLUGIN_ROOT}`, `@` imports, `model:`. Rolling the six entry points back to `commands/` would leave a Codex user with `source-command-persona-list` as the only supported entry point and no way to run `asimov-init`, so no `.codex/agents/` delivery and no agents either. Confirms §1 row 3 and §5 item 2: the entry points are skills.
