In Codex the same entries are skills of the plugin: `$asimov-plugin:d101-feature-design`, `$asimov-plugin:d101-review`, and so on; `asimov-init` is always the user's call, in both tools.

**Two runs, not one.** `/d101-feature-design` works to two bars. The first run settles requirements and the business design, writes the file with §6 _Technical design_ marked open and a list of what is outstanding, and then stops. Open the file, read it, iterate on §2–§5 — then run the command again against that file to add §6. `/d101-review` reads the phase from the document, then offers and runs the reviews it calls for — the gap check against the matching bar (§8a while §6 is open, §8b once written) plus the persona reads (below).

The rendered D101 carries two chips in its top bar: **phase** (`Business design` → `Full design`, yours to move) and **status** (`Draft` → `Approved`, the business approver's, normally only after §6 exists because the estimate depends on it).

**Read the design as its reader, too.** Beyond the bar check, a **persona review** reads a D101 (its §2/§4, plus §6 for a feasibility reader) _as one of its intended readers_ and reports where it talks to its author instead — the reader's-eye complement to the gap check, not a substitute; run both. `/d101-review` offers these persona reads alongside the gap check, or invoke a reader directly by name (`review as <name>`). Standard readers ship with Asimov; `/persona-list` shows the whole roster and `/persona-new` authors a reader specific to this repo. Reach for one before taking a design to a real reviewer.

### Delegation flow — Build → Test → Review

This flow applies to **prompt-driven tasks** — the user asks the orchestrator directly to do something (bugfix, small feature, other change), with no specification files involved. When the user instead hands the orchestrator specification files to follow, a separate spec-driven delegation flow applies (not yet written).

Delegating only the build step is **not** automatically task completion — the orchestrator must still run the post-build test-impact check below, and consider whether to ask about a fuller test pass or a review.

1. **Build** — delegate the implementation to the builder that matches the file type (`giskard-the-dotnet-developer` for `.cs`, `daneel-the-angular-developer` for `.ts`/`.html`/`.css`). For a task spanning both stacks, delegate each part to its builder.
2. **Post-build test-impact check (automatic, narrow)** — once the builder reports done, the orchestrator checks whether tests already exist for the code that changed and whether the change could plausibly break one or more of them. If so, delegate to `calvin-the-test-author` with explicit instructions to **only update the existing tests directly impacted by the change** — Calvin must not add new tests in this step. Skip this step when there are no existing tests touching the changed code.
3. **Ask about a full testing pass** — for a prominent change (see below) or a new feature, ask the user whether they want a full testing pass (new/extended coverage, not just fixing impacted tests). Only delegate to `calvin-the-test-author` for new test authoring if the user agrees. For small/targeted changes, don't ask unless the user brings it up.
4. **Ask about review** — for a prominent change or a new feature, ask the user whether they want `baley-the-code-reviewer` to review the full changeset. Review is never auto-scheduled as part of the plan — it only happens if the user opts in. For small/targeted changes, don't ask unless the user brings it up.

**Prominent vs. small** — the judgment call behind steps 3 and 4: a _prominent_ change touches multiple files, adds a new public API/endpoint/component, or is a new feature; a _small_ change is a targeted bugfix, a config tweak, or a localized single-file/single-line edit.

If `baley` (when run) flags findings, summerize the found fails and flags and ask the user before looping back to the relevant builder (and `calvin` if the fix affects covered behaviour).

**Exceptions** (inline edits are fine and the chain does not apply): config files (`.csproj`, `appsettings.json`, `CLAUDE.md`, etc.), plan files, and single-line mechanical fixes (e.g., changing one `using` alias).

## L3 working agreement

- **Reviewer ≠ author** — nobody approves their own design, spec, or code.
- **No phase starts until the previous is approved** — above all, coding waits for an approved spec.
- **A gap found later is a bug earlier** — fix the earlier artifact and re-run the phase.
