S102 — Task spec

One per task. The exact brief a fresh build agent receives: sized for one sitting, checkable afterwards by a validator that never saw the conversation. assess

What it holds

  • Intent, traced to the D101 requirement it serves.
  • Files it creates, modifies and tests. Exact paths; also the set it owns. Nothing else is touched.
  • Interfaces it consumes and produces, by exact name, so neighbouring tasks agree before either exists.
  • Behaviour as scenarios a test is written from; constraints as musts, must nots, preferences and escalation triggers.
  • Steps, test first, with the code inline where the task is transcription. Acceptance criteria a validator can run.

The bar

Buildable blind. A competent builder with no conversation history, only the repo, the D101 and this file, builds it and knows when it is done. No placeholders. The builder never edits what it does not own; a conflict is a stop and a report, not a fix.

Where it comes from, where it goes

Normally one of several under an S101. A bug fix from the board skips the design and the plan and gets a single S102. Giskard, Daneel and Calvin build from it; the planned validator checks the code against its acceptance criteria. The document model →
