The builder it is written for, as its whole brief. The reviewer, as part of the plan. The build run, when it runs the done-when against the code.

The line

The spec fixes what: the scope, the public names and signatures, the behaviour and the check. The builder owns how: every method body, every private name, every test. A body in a task spec is a transcript, not a brief. That line is the specification contract; the S102 is its task part, the S101 its plan part.

What it holds

  • A header copied from the plan: role, tier, what it comes after, the design ids it traces to. Plus three machine-read lists: the files it owns, the names it consumes, the names it produces. Names only; the signatures live once, in the plan.
  • Intent: one or two sentences, in the design's words. The reason, never the recipe.
  • Behaviour as Gherkin scenarios a test can be written from, every rule with its failing case. Or one line saying the task adds none, and what its check is instead.
  • Done-when: a named test that passes, a build that is green, a command and its output. Described, never written.
  • Constraints and stops specific to this task: musts, must nots, what to mirror, and when the builder stops and reports instead of deciding. The global ones are inherited, never repeated.
  • Out of scope: what a builder might think belongs here and does not, with the task that owns it.

Five sections, no steps, no code block but Gherkin.

The bar

Buildable blind. A competent builder with no conversation history, only the repo, the design, the plan and this file, builds it and knows when it is done. It never makes a decision the spec owns, and makes every decision the builder owns. No placeholders. The builder never edits what it does not own; a conflict is a stop and a report, not a fix.

Validated blind

The model that wrote the spec has the conversation in its head and fills the gaps from memory. So a fresh reader checks it instead.

  • Write, then check. Each task spec goes to a fresh read-only subagent as soon as it is written. Ten fixed checks, one row each, no verdict.
  • Fail, then rewrite. A failed check sends the spec back; the rewrite is checked again.
  • Three fails, or a design gap, stop the run. A spec that fails three times, or a finding that points at the design rather than the spec, is reported, not rewritten. The design is fixed first.
  • Hard on shape, soft on content. A missing path, an unproduced name, a code block that is a body, a done-when that greps the source: fail. Whether the scenarios are the right ones: the reviewer's.

Rules

  • Names, not bodies. No method body, no private structure, no test code, no steps. A missing body is not a placeholder; it is the builder's work.
  • The check is described, not written. Never the test's code, and never a search of the source for the spec's own words.
  • No placeholders. No TBD, no handle edge cases, no similar to task 3. A decision the spec owns and left open is reported, not papered over.
  • Own your files; stop at the edge. Needing a file outside the owned set is an escalation, not a judgement call.
  • Inherit, don't repeat. Contracts, global constraints and the escalation route live in the plan. A consumed name is spelled as the plan spells it, never restated.
  • Link, don't paste. Existing types, enums and schemas by path, so the spec does not go stale when they move.

Never without a plan

A bug fix from the board skips the design document, not the plan. Its approved ticket is the design, and its plan may have one task; the task then traces to the ids the plan gave the ticket's items.
