Definition · Template · The Spec-stage D101
Read by
A reviewer who is not the author, the person directing the run, every task spec as it is written, and the build run as its control document.

What it holds

  • The task graph, once, in the YAML frontmatter: every task with its role, tier, phase, dependencies, owned files, the names it produces and consumes, and the design ids it traces to.
  • Phases with checkpoints: a state a reviewer can verify without reading code. The unit a run stops at and a revert targets.
  • Interfaces, constraints, review focus: stated once here, inherited by every task.
  • Escalation routing: what stops a builder, and who rules.
  • Coverage map: every requirement and acceptance criterion against the tasks that deliver it, both ways.
  • Assumptions: every decision taken without asking you, with the default it took.

How it is cut

  • Phase 0 is the skeleton. One task per stack writes the classes, interfaces and public methods with no bodies, compiling. The interfaces become code before anyone builds against them.
  • One phase per acceptance criterion. A slice: the work that makes one criterion pass, end to end. One builder task per stack it touches, plus one tester task.
  • The tester's test is the checkpoint. Written against the skeleton before the slice is built; red first, green when the slice is done.
  • Parallel means disjoint. Two tasks run together only if they own no common file. The skeleton is cut so each slice owns its own.

The cut, before the expansion

Nothing but this file exists when you first see the plan. /asimov-spec prints the phases, the tasks, the assumptions and the graph checks, and waits.

  • go writes and validates every task spec, then the plan, and finishes once.
  • Free text re-cuts and shows the cut again. Edit the file by hand and say read again, and it is read as the graph.
  • stop leaves the plan alone on disk. The next run opens at the same place.

The go is your call that the cut holds. It is not an approval and is recorded nowhere.

The bar

Dispatch-ready. The person or orchestrator running it can hand every task to a fresh builder, in graph order, without going back to the author. A reviewer who is not the author gives the verdict; coding does not start before it. No skill records it: ready is set by hand.

Lifecycle

  • draft → ready → in progress → done. The skill writes draft only; you set ready; the build run moves the rest.
  • Run it again after the design was refined, and the plan is updated in place, keeping every task spec that still clears its bar.
  • Run it again after a requirement or criterion changed, and the plan is rewritten with every task spec. Git keeps the old one; no superseded copy.

What it is not

  • Not the recipe. File paths, signatures, steps and test code live in the S102s.
  • Not the ledger. Which task is claimed or in a fix round lives in a gitignored run log, never in the plan.
  • Not the validation report. Findings go to a gitignored sidecar next to it; only the assumptions are plan content.

Where it comes from, where it goes

A D101 at full design produces exactly one; so does an approved ticket whose thread carries the decision, the rules, acceptance criteria and what is out of scope. Anything less is refused, and the fix goes into the D101 or the ticket. It produces one or more S102 task specs; a bug fix may get a plan of one. The document model →

Definition, template and skills exist since 2026-10-02 and have not run outside the Asimov repo. That is what assess means: use it, and expect the shape to move.
