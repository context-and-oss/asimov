S101 — Implementation plan

One per feature. Turns a gap-free D101 into an ordered, dependency-aware set of task specs, and states what every task must respect once. assess

What it holds

  • The task graph: every S102, its dependencies, its phase, the files it owns. Parallel means disjoint files and no open blockers.
  • Phases with checkpoints: a state a reviewer can verify without reading code. The unit a run stops at and a revert targets.
  • Interfaces, constraints, review focus: stated once here, inherited by every task.
  • Escalation routing: what stops a builder, and who rules.

The bar

Dispatch-ready. The person or orchestrator running it can hand every task to a fresh builder, in graph order, without going back to the author. A reviewer who is not the author gives the verdict; coding does not start before it.

What it is not

  • Not the recipe. File paths, signatures, steps and test code live in the S102s.
  • Not the ledger. Which task is claimed or in a fix round lives in a gitignored run log, never in the plan.

Where it comes from, where it goes

A D101 at full design produces exactly one. It produces one or more S102 task specs. Lives at documentation/specs/<feature>/ beside them. The document model →
