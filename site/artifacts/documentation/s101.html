S101 — Implementation plan

One per feature. The task graph a design becomes, and what every task must respect, stated once. assess

Produced by

Agents: every task spec as it is written, and the build run as its control document. People never read the file; they read the plan view it renders to in chat, at the cut, at the end of a run, and as the reviewer.

The line

The plan is the plan part of the specification contract: order, coverage, escalation, and the names tasks share, each stated once. No code anywhere in it. Signatures appear once, under Contracts; bodies, private names and tests are the builder's.

What it holds

  • The phase tree, once, in the YAML frontmatter: phases in build order, a checkpoint on each, and one line per task: id, title, role, tier, what it comes after, the design ids it traces to. Only what orders the work; files and names live in the task specs.
  • Contracts: every name one task produces and another consumes, with its signature, here and nowhere else.
  • Constraints the design imposes: one line each, verbatim, with the source. Never the conventions; the builder loads those anyway.
  • Coverage: every requirement and acceptance criterion against the tasks that deliver it, both ways. An id with no task says why.
  • Escalation: what stops a builder, and who rules.
  • Review focus: the failure modes no task's check exercises, each pinned to a task.
  • Assumptions: every decision taken without asking you, with the default it took. Last.

Six sections and a tree. No prose about the phases: the agent has the tree, the person has the view.

How it is cut

  • Phase 0 is the Foundation. The contracts as code: classes, interfaces and public methods with no bodies, compiling, one task per stack. Plus whatever every slice builds against and no slice should be first to touch. Never a slice's behaviour, however small.
  • One phase per acceptance criterion. A slice: the work that makes one criterion pass, end to end. One tester task first, then one builder task per stack it touches.
  • The tester's test is the checkpoint. Written against the Foundation before any body exists; red first, green when the slice is done. Tester before builder, in every slice.
  • A close, when the run needs one. A phase after the last slice for what ends the run and belongs to no criterion: a release, a flag flipped. Often a human task.
  • Parallel means disjoint. Two tasks run together only if they own no common file. The Foundation is cut so each slice owns its own.

The cut, before the expansion

Nothing but this file exists when you first see the plan. /asimov-spec shows the plan view: the phases with their checkpoints, one line per task, the coverage line, the assumptions, the graph checks. Then it waits.

  • go writes and validates every task spec, then the plan, shows the view once more, and finishes.
  • Free text re-cuts and shows the cut again. Edit the file by hand and say read again, and it is read as the graph.
  • stop leaves the plan alone on disk. The next run opens at the same place.

The go is your call that the cut holds. It is not an approval and is recorded nowhere.

The bar

Dispatch-ready. The person or orchestrator running it can hand every task to a fresh builder, in graph order, without going back to the author. A reviewer who is not the author gives the verdict; coding does not start before it. No skill records it: ready is set by hand.

Lifecycle

  • draft → ready → in progress → done. The skill writes draft only; you set ready; the build run moves the rest.
  • Run it again after the design was refined, and the plan is updated in place, keeping every task spec that still clears its bar.
  • Run it again after a requirement or criterion changed, and the plan is rewritten with every task spec. Git keeps the old one; no superseded copy.

What it is not

  • Not the brief. The files a task owns, its behaviour, its done-when and its own constraints live in the S102s.
  • Not the ledger. Which task is claimed or in a fix round lives in a gitignored run log, never in the plan.
  • Not the validation report. Findings go to a gitignored sidecar next to it; only the assumptions are plan content. So does every place a run had to work around the template: a finding for the maintainer, never a line in the plan.

Where it comes from, where it goes

A D101 at full design produces exactly one; so does an approved ticket whose thread meets the design contract: the problem, the decision, acceptance criteria, what is out of scope, and the rules and open questions where there are any. Anything less is refused, and the fix goes into the D101 or the ticket. It produces one or more S102 task specs; a bug fix may get a plan of one. The document model →

Definition, template and skills exist since 2026-10-02. The first real run, eleven tasks from a ticket, showed the plan narrating its phases and the task specs carrying code, so the shape was re-cut on the specification contract on 2026-10-05. That is what assess means: use it, and expect the shape to move.
