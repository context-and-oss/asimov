# CLAUDE.md — Asimov

This repo is **Asimov** — a tool-agnostic toolkit publishing the L3 workflow's AI-assisted stages to **Claude Code and Codex**. One tool-neutral source tree (`source/`) is generated by CI into a plugin per tool; slash commands, subagents, personas, advisory skills, artifact definitions and templates for the Design → Spec → Code → Review+Test stages of the L3 pipeline.

You are working *on* the toolkit. Commands and subagents *built by* the toolkit run in product repos; this repo is where their neutral sources, the generator, and the artifact contracts live.

**The one rule that shapes all work here: people edit `source/`; the generated trees (`plugins/`, `.agents/`) are gitignored on main and minted onto release tags by CI.** A change typed into a generated tree is erased by the next regeneration; a PR that tries to commit one is refused by the gate.

**Two words, kept apart (D100 §4).** A *component* is a part of the toolkit itself — a command, a subagent, a skill, a definition, a template, the generator — in source or generated form. An *artifact* is something the toolkit writes into a product repo — a D101, a persona review skill, `asimov.md` — and is what `source/artifacts/` is organised around.

## Conventions

### Document codes
- `D100` — architecture doc (system-level)
- `D101` — feature design doc
- `S101` — implementation spec (not built yet)
- `T100` — test strategy (none yet)

### L3 pipeline stages
*Intent → Design → Spec → Code → Review → Test → Approve → Deploy → Observe*. The toolkit covers the AI-assisted middle (Design through Test). See D100 §3.

### File naming
- Command sources: `source/commands/<command-name>.md` (kebab-case, slash-stripped; frontmatter `name` must equal the filename)
- Subagent sources: `source/agents/<subagent-name>.md` (kebab-case)
- Persona sources: `source/personas/persona-<slug>.md`
- Skill sources: `source/skills/<skill-name>.md` (advisory skills; `pm-` prefix for the delivery-model family)
- D101s: `documentation/features/D101-<feature-slug>.html` (kebab-case after `D101-`; authored as HTML)
- Artifact folders: `source/artifacts/<landing-place>/<artifact-slug>/` (kebab-case; the landing place is where the artifact ends up in a product repo — e.g. `source/artifacts/documentation/d101-feature-design/` for a D101, which lands in `documentation/features/`). Each folder holds the artifact's definition and template side by side
- Definitions: `<artifact>-definition.md` inside the artifact folder — the same `<artifact>` slug as the folder, so definition and template sort side by side and carry their artifact name when opened alone
- Templates: `<artifact>-template.<ext>` inside the artifact folder — the extension is the one the template renders as (`.html` for D101s and the site, `.md` for text bodies, `.svg` for diagrams). Specialised variants: `<artifact>-<variant>-template.<ext>`
- Resources: `source/resources/<kind>/` — building blocks shared across artifacts, never an artifact themselves
- Diagram templates: `source/resources/diagrams/<notation>-template.svg` (notation, not section — e.g. `state-machine-template.svg`)
- Mapping tables: `source/mappings/<tool>.md` (`claude-code`, `codex`)

The generator copies `source/artifacts/`, `source/resources/` and `source/processes/` verbatim into both plugin trees under the same relative paths, so a command reads `{{plugin-root}}/artifacts/…` and `{{plugin-root}}/resources/…`, and `pm-advisor` reads `{{plugin-root}}/processes/…`.

### Artifact maturity
Every artifact carries one level — `assess` / `trial` / `adopt` / `hold` (Technology Radar rings) — as a YAML block (`artifact`, `maturity`, `since`) at the top of its definition. The producing command reads it from the installed plugin in either tool, prints the level as one chat line before its first question (nothing for `adopt`), and never changes it. Levels move on evidence, never time: `trial` needs one artifact reviewed by a non-author, `adopt` a second repo plus a revision driven by use; rewriting the bar drops back to `assess`. D100 §4.5 mirrors the level (hard rule 11). Design: `documentation/features/D101-artifact-maturity.html`.

### Neutral frontmatter
Every command/agent/persona/skill source declares `tier` (small | medium | large) and `effort` (low | medium | high | xhigh | max) — **required; a missing designation fails generation**. Never a concrete model name in a source file (generation-enforced via the mapping tables).

### Tokens in source bodies
- `{{plugin-root}}` → `${CLAUDE_PLUGIN_ROOT}` (Claude Code) / a skill-relative path (Codex)
- `{{model-check}}` → the generated model-mismatch preamble (commands only, right after the frontmatter)
- `{{<fragment>}}` → the text of `source/commands/_<fragment>.md`, identical in both targets — prose several commands share. `{{file-io}}` (UTF-8 on both ends, byte copies, mojibake spot-check) is the first hard rule of every command; Codex has no file tools and shells out through PowerShell, whose Windows default is ANSI
- `{{designation}}` / `{{scope-guard}}` → agent bodies only: the provenance-trailer payload `<agent> (<tool>, <model>, effort <effort>)` per tool, and the twin's scope rule (empty for a default) — D101-build-subagents §6.4
- Generator tokens are `{{lowercase-kebab}}`; uppercase `{{PLACEHOLDER}}` strings are template content and pass through untouched.
- Every run-time read of a plugin file goes through `{{plugin-root}}` — never a `plugins/asimov-plugin/…` literal, which resolves in neither installed plugin.

### Dates
Always `YYYY-MM-DD` (e.g. `2026-05-21`). Never American month/day. Never relative ("last Thursday").

### Manifest names vs repo name vs prose names
- Repo: `asimov` (GitHub)
- Marketplace manifest name: `asimov-marketplace` (both tools)
- Plugin manifest names: `asimov-plugin` (Claude Code) and `asimov-plugin-codex` (Codex) — also their directory names under `plugins/`
- Friendly prose: "Asimov Plugin" (capitalised, used in headings + sentences)

## How to add a new slash command

1. Decide which L3 stage the command belongs to (Design / Spec / Code / Review + Test, or ad-hoc like `/conventions-check`).
2. Write a per-command D101 at `documentation/features/D101-<command-slug>.html` using the template. Run `/d101-feature-design` — twice: once for requirements + business design (which lands the file at phase `Business design` with §6 open), again for the technical design. Must clear both bars in `d101-feature-design-definition.md` — §8a before you move to §6, §8b before you request review.
3. Add a row to `documentation/D100-Asimov-architecture.md` §4.3 *Slash commands* (tier/effort column).
4. Author the source file at `source/commands/<command-name>.md` with neutral frontmatter (`name`, `description`, `argument-hint`, `tier`, `effort`, optional `allowed-tools`), `{{model-check}}` as the first body line, and `{{file-io}}` as the first bullet under `# Hard rules`. If the command produces an artifact, it also reads that artifact's definition and prints the maturity notice (Step 1b in the existing producing commands).
5. Run the generator locally (`cd generator && npm run generate`) and check the emitted skills in both plugin trees.
6. Test locally — see "How to test" below. Commit **source + docs only**; CI commits the generated trees.

## How to add a new subagent

Same shape as a command, but the source lives under `source/agents/<name>.md` (no `argument-hint`, `tools` instead of `allowed-tools`, no `{{model-check}}`). An agent may declare `twin: small` to be emitted a second time at the small tier as `<name>-small` — one prompt, two agents; the twin's scope rule lives once in `source/agents/_scope-guard.md` and reaches the twin through `{{scope-guard}}` (pilot: Giskard). The Output of every agent that writes files ends with the `Asimov-Built-By: {{designation}}` trailer line, and its D100 §4.4 row moves with its designation. Subagent kinds follow the Accelerate roles — *builder / tester / reviewer* (see D100 §4.4). The shared convention-overlay mechanism lives in D100 §7.2.1. Codex receives subagents as generated TOMLs (`codex/agents/` in both plugin trees) that `/asimov-init` copies into a product repo's `.codex/agents/`.

1. Cover it in a D101 — the build subagents share `documentation/features/D101-build-subagents.html`; a distinct role gets its own.
2. Add a row to `documentation/D100-Asimov-architecture.md` §4.4 *Subagents*.
3. Author `source/agents/<name>.md`, run the generator, test, commit source + docs.

## How to add a new artifact

An artifact is something a command writes into a product repo. It gets one folder under `source/artifacts/<landing-place>/<artifact-slug>/` holding `<artifact>-definition.md` (opening with the maturity block, at `assess`) and `<artifact>-template.<ext>`; a row in D100 §4.5 with the same level; and a producing command that reads both by `{{plugin-root}}` path and prints the maturity notice. Design it in a D101 first. The S101 artifact (`source/artifacts/documentation/s101-implementation-spec/`) is the next one due.

## How to add a persona review skill

A **persona review** reads a design document *as one of its intended readers* — the concrete form of `/d101-review` check 7. **Standard** personas are authored in `source/personas/persona-<slug>.md` and emitted into both plugin trees; **custom** product-specific readers are authored by `/persona-new` into the **product repo** (a concrete reader is a product entity, hard rule 8). The toolkit owns the standard (`source/artifacts/skills/persona-review/persona-review-definition.md`) and the skeleton (`source/artifacts/skills/persona-review/persona-review-template.md`). A generated persona skill is **self-contained** — it inlines the method rather than reading the definition at run-time (a skill is an authored artifact, not a re-running command, so hard rule 3 does not apply to it). Design: `documentation/features/D101-personas.html`.

## How to change a model designation

Concrete model names live **only** in `source/mappings/claude-code.md` and `source/mappings/codex.md`. The ritual (also in each table's header): change the row, regenerate, test the affected commands in both tools, land as one PR. Per-component designations are the `tier`/`effort` frontmatter in the source files. Never write a model name into a source body or frontmatter.

## How to add an advisory skill

An **advisory skill** answers questions from a body of reference material shipped in the plugin, rather than performing an action. `pm-advisor` is the first — it advises on the delivery model in `source/processes/`, which the generator ships as `processes/` in both plugin trees. It is the first member of a planned `pm-*` family.

1. Choose the family prefix (`pm-` for delivery/project-management advice) and a `<slug>`.
2. Author `source/skills/<prefix><slug>.md` with neutral frontmatter carrying `name`, `description`, `tier` and `effort` — no `argument-hint`, and no `{{model-check}}` in the body (nobody types a skill; the model activates it). The `description` is the trigger: name the topics and the phrasings that should activate it.
3. Give the body: a **navigation section** (which file to read first, how links resolve), an **intent → file routing table** over the reference corpus, and the **rules of engagement** (read before advising; recommend don't decide; stay inside the material; advisory only — never writes).
4. Reference the corpus by `{{plugin-root}}` path (`{{plugin-root}}/processes/...`), never by inlining its content (hard rule 3). A new corpus gets its own folder under `source/` and a `copyTree` line in both emitters.
5. Add a row to `documentation/D100-Asimov-architecture.md` §4.6 *Skills*. No manifest change (skills auto-discover); the generator emits the skill into both plugin trees, with the mapped model in the Claude Code frontmatter and none in Codex's (hard rule 4).
6. D101 coverage joins the family's shared D101 when that is written — not one per skill.
7. Run the generator and test locally — see "How to test" below.

## How to test the plugin locally

```
cd generator && npm install && npm run generate && npm test
```

The generate step is required before a local install — the plugin trees are gitignored on main, so a fresh clone has none until the generator runs. Then, in Claude Code:

```
/plugin marketplace add <path-to-your-clone>
/plugin install asimov-plugin          (in any product repo)
/plugin marketplace update asimov-marketplace   (to pick up changes — no auto-reload)
```

In Codex: install `asimov-plugin-codex` via Codex's plugin marketplace mechanism against the same clone.

## Hard rules

These are enforcement rules, not style preferences. Violations break the toolkit's contract.

1. **Never hand-edit or commit a generated tree.** `plugins/asimov-plugin/`, `plugins/asimov-plugin-codex/`, and `.agents/plugins/marketplace.json` are generator output — gitignored on main, committed only onto release tags by the release workflow (off-main; main is protected). Every change goes in `source/` and is regenerated. The PR gate refuses diffs that introduce generated paths.
2. **Manifest names and folder names stay in sync.** Each plugin manifest's `name` field, its `plugins/<name>/` directory, and its marketplace entry — the same string per tool. `source/toolkit.json` is where the generated ones are set; `.claude-plugin/marketplace.json` is the one hand-maintained manifest.
3. **Commands reference definitions and templates by *path*, not by inlining content.** A command's source body says "read `{{plugin-root}}/artifacts/documentation/d101-feature-design/d101-feature-design-definition.md`"; it doesn't paste the definition into the prompt. This keeps the doc-in-the-plugin as the runtime source of truth (D100 §7.4).
4. **No concrete model names outside `source/mappings/`** (and the generated trees derived from them). Source files speak `tier` + `effort`; the generator fails on a missing designation rather than defaulting.
5. **D101s mature through two bars, and each bar's verdict belongs to a different person.** *Business-complete* (`d101-feature-design-definition.md` §2.1, checked by §8a) is the **author's** call. *Gap-free* (§2.2, checked by §8b) is the **human reviewer's** (≠ author) call — except for toolkit-internal D101s, which cka authors and approves alone. Never review a `Business design` document against §8b. **Phase ≠ status:** phase (`Business design` → `Full design`) is the author's; status (`Draft` → `Approved`) is the approver's; no command ever records an approval.
6. **An accepted deviation never covers a check.** A rule of `d101-feature-design-definition.md` may be deliberately declined and recorded in the D101 (§4.9) — named rule, one-sentence reason, accepter, date. Never against a §8 check; never stops the finding being reported (`/d101-review` prints it as **Accepted**); never stored outside the D101. Design: `documentation/features/D101-accepted-deviations.html`.
7. **No drift between D100, D101s, and code/manifests.** When you change one, run a quick grep for related references in the other docs.
8. **Don't bake product-specific identifiers into definitions, templates, or command prompts.** Path conventions (e.g. `documentation/features/`) are acceptable shared conventions; product entity names are not (D100 §8.4 reusability).
9. **Reusability across products is a goal, not a hope.** When in doubt, name something generically and add an example as illustration.
10. **Path-convention fork point:** the convention `documentation/features/D101-*` is baked into `source/commands/d101-feature-design.md` (output path + listing glob), `source/commands/d101-review.md` (auto-detect glob), and `source/commands/d101-convert-to-html.md` (source glob). `asimov-init.md` shares the same `documentation/` taxonomy and adds the `asimov.md` root location, the `AGENTS.md` managed-region location, and the `<stack>` slugs. The `D101-<slug>.review.md` sibling-file convention (`d101-feature-design-definition.md` §4.10) is shared by `d101-review.md` (writer) and `d101-feature-design.md` (reader + deleter). A fork that uses a different layout changes the literal in *all* of these source files — they must stay in lockstep. Intentionally not a config. A second fork point is the corpus path `processes/`: baked into `source/skills/pm-advisor.md` (`{{plugin-root}}/processes/…`) and into the vault's export target, which must write to `source/processes/`; the corpus never names its own location.
11. **A maturity level and its D100 mirror move in the same commit.** The `maturity`/`since` block in an artifact's definition is the source; the *Maturity* column in D100 §4.5 is the mirror. Change one, change the other, and name the evidence for a promotion in the commit message.
